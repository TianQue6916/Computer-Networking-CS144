<span style="color:#2471a3;">**[section]**</span> <span style="color:#00838f;">**Background（背景）：Wireshark 是一个检查网络接口上所收发分组的工具。**</span>它有两种模式：Capture（捕获）与 Open（打开）。Capture 模式实时显示当前进出该接口的分组流，愿意的话还可以把它们保存为 pcap 文件；Open 模式则用于检查此前某次捕获所保存的 pcap 文件。

如果想同时查看两个 pcap 文件，我找到的最好办法是启动两个 Wireshark 实例——例如在 Mac 上运行：

```
open -n /Applications/Wireshark.app
```

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> Wireshark 的"抓包过滤器"（capture filter）与"显示过滤器"（display filter）是两种作用点完全不同的机制，练习 2 和练习 3 都会用到。前者在抓包路径上就做筛选，被过滤掉的分组根本不会进入记录——适合高流量环境下只保留感兴趣的流量；后者是对已经完整记录下来的 pcap 文件做事后查询——适合分析阶段反复试探、随时换条件重筛。这与你调试程序时的两条路径同构：CSAPP 教的 gdb 断点像抓包过滤器，在事件发生的现场就拦截；事后翻看日志像显示过滤器，代价是先把全部数据存下来。pcap 文件本质上是"带时间戳的逐分组记录"，你在 Lab 5 调试 webget 时用 `tcpdump -w` 存出来的就是这种格式。观察工具的一个基本权衡由此浮现：越早过滤越省资源，但丢掉了事后反悔的余地；越晚过滤越灵活，但存储与处理成本越高。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> traceroute 的原理堪称"把路由器的报错机制改造成测量工具"的典范：发送方故意把探测分组的 TTL（生存时间）依次设为 1、2、3……每一台路由器把 TTL 减到 0 时会丢弃该分组，并向源主机回送一个 ICMP "TTL 超时"（Time Exceeded）报文——源主机正是靠收集这些报文，逐跳还原出通往目的地的路径。这与你在 Lab 6 要实现的"TTL 减到 0 就丢弃"的逻辑是同一枚硬币的两面：路由器只负责规规矩矩地减一并报错，测量的智能全部放在发送端。用 6.042J 的图论语言说，路径长度就是从源到目的地经过的边数，traceroute 相当于沿一条实测路径逐点采样。注意输出里每一跳有三个时延值——那是三次独立探测各自的往返时延（RTT）样本，既用于估计时延，也顺带展示了时延的波动。

注：pcap 中的第 1–4 号分组可以忽略，它们属于另一次通信。
