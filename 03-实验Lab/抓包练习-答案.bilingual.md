### <span style="color:#2471a3;">**[exercise]**</span> <span style="color:#c0392b;">**Pcap 2: SMTP（捕获文件 2：SMTP）**</span>

说明：打开 `smtp.pcapng`，其中包含一段与 lab 0 中类似的 SMTP 会话捕获记录。

作答时请使用 Wireshark 的分组编号（"No." 列）来标识分组。

为了让 TCP 序列号/确认号更容易理解，请把 Wireshark 设置为相对第一个分组显示这些编号：`Wireshark -> Preferences -> Protocols -> TCP`，勾选 "Analyze TCP sequence numbers"（分析 TCP 序列号）和 "Relative sequence numbers"（相对序列号）。

**1. What port does the SMTP server run on?（SMTP 服务器运行在哪个端口？）**

> <span style="color:#2471a3;">**[solution]**</span> 25。

**2. What port does the client run on?（客户端运行在哪个端口？）**

> <span style="color:#2471a3;">**[solution]**</span> 51319。

**3. What protocol does SMTP run on top of?（SMTP 运行在什么协议之上？）**

> <span style="color:#2471a3;">**[solution]**</span> TCP。

**4.**
**a. Which packet represents the telnet request?（哪个分组对应 telnet 请求？）**
*Hint: you won't see the word "telnet" explicitly - but remember that the telnet request initiates a connection over the protocol you identified in (3).（提示：你不会看到 "telnet" 这个词本身——但请记住，telnet 请求是在你在第 (3) 问确定的协议之上发起连接的。）*

> <span style="color:#2471a3;">**[solution]**</span> 第 1 号分组。

**b. Which flag in the packet identified in (a) tells the SMTP server that this is the beginning of the connection?（在 (a) 确定的分组中，哪个标志位告诉 SMTP 服务器这是连接的开始？）**

> <span style="color:#2471a3;">**[solution]**</span> SYN（同步位）。

**c. Which packet contains the 220 response from the SMTP server?（哪个分组包含 SMTP 服务器的 220 响应？）**

> <span style="color:#2471a3;">**[solution]**</span> 第 4 号分组。

**5.**
**a. In which packet does the client first acknowledge the 220?（客户端在哪个分组中首次确认 220？）**

> <span style="color:#2471a3;">**[solution]**</span> 第 5 号分组。

**b. What is the ACK number of the packet acknowledging the 220 (i.e. the packet identified in b)?（确认 220 的那个分组的 ACK 号是多少？）**

> <span style="color:#2471a3;">**[solution]**</span> 50。

**c. You should see that the ACK number is one more than the length of the 220 response's payload, meaning the client had received one byte in addition to the 220 by the time it acknowledged the 220. What data was in the byte the client received before the 220?（你应能看到 ACK 号比 220 响应载荷的长度多 1，说明客户端在确认 220 时，除了 220 之外还多收到了一个字节。客户端在 220 之前收到的那个字节里是什么数据？）**

> <span style="color:#2471a3;">**[solution]**</span> SYN。多出来的那个字节正是服务器发来的 SYN——虽然它不是"数据"，但 TCP 规定 SYN 消耗一个序列号。

**d. Notice that the sequence number of the packet acknowledging the 220 is 1, meaning the client had already sent one byte by the time it acknowledged the 220. What data was in the byte the client sent before the 220?（注意确认 220 的那个分组的序列号是 1，说明客户端在确认 220 之前已经发送了一个字节。客户端在 220 之前发送的那个字节里是什么数据？）**

> <span style="color:#2471a3;">**[solution]**</span> SYN。同理，这是客户端自己发出的 SYN，它占用了客户端序列号空间里的第 0 号。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 为什么 SYN 会消耗一个序列号？回忆你在 Lab 2–4 实现 TCP 时处理过的规则：序列号数的是"字节流中的字节"，但 SYN 和 FIN 这两个控制位也需要被对端可靠地确认，于是协议规定它们各占一个序列号——SYN 占第 0 号，第一个数据字节从第 1 号开始。这样"220 响应的载荷长度 + 1 = ACK 号"就顺理成章：多出来的 1 正是服务端的 SYN。这个设计把连接建立与断开也纳入了同一条确认体系，不必另设"连接确认报文"。CSAPP ch11 讲套接字编程时，把这些细节都藏在 connect/accept 之下；而你亲手实现过 TCP 之后就会明白：三次握手里每个标志位的序列号语义都经过了如此精确的安排，甚至攻击者伪造的序列号（如经典的序列号预测攻击）也要利用这些规则。

**6. Wireshark has flagged packets 15 and 17 as duplicates. Which packets do they duplicate?（Wireshark 把第 15、17 号分组标记为重复（duplicate）。它们重复的是哪些分组？）**

> <span style="color:#2471a3;">**[solution]**</span> 第 15 号分组重复的是第 14 号（序号/确认号/长度完全相同；Wireshark 在 SEQ/ACK Analysis 部分也会直接告诉你这一点）；第 17 号分组重复的是第 16 号。

**7. Notice that this pcap only contains packets involved in the email conversation, even though the computer that sent the email had lots of other network traffic going on at the same time. That's because the capture was created using the capture filter "tcp port smtp". In addition to capture filters, Wireshark also has display filters, which narrow down the packets displayed. For instance, we can filter out TCP packets with no payload, leaving only the packets containing the client's requests and the server's responses. Type this into the display filter box below the toolbar: "tcp.len > 0". How many packets are displayed when this filter is applied?（注意这个 pcap 只包含参与邮件会话的分组，尽管发邮件的计算机同时还有大量其他网络流量。这是因为抓包时使用了抓包过滤器 "tcp port smtp"。除了抓包过滤器，Wireshark 还有显示过滤器（display filter），可缩小显示的分组范围。例如，我们可以滤掉没有载荷的 TCP 分组，只留下包含客户端请求与服务器响应的分组。在工具栏下方的显示过滤器框里输入 "tcp.len > 0"。应用该过滤器后显示多少个分组？）**

> <span style="color:#2471a3;">**[solution]**</span> 19 个。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 同一跳出现多个应答主机，说明源到目的地之间存在多路径（multipath）：有多条代价相近的路由，流量被分散到不同路径上——现代骨干网常用等价多路径（ECMP）机制，按分组首部的哈希值把流量摊到多条等价路径上以提升总吞吐。用 6.042J 的图论语言说：最短路并不一定唯一，图中若存在多条等长最短路，不同的探测分组就可能走上不同的那条。这也解释了为什么 traceroute 的输出并不可靠地表征"一条固定路径"——它更像对路径分布的一次抽样。由此还能引出一个概率论视角：每次探测是对"分组所走路径"这个随机变量的一次抽样，多跑几轮 traceroute 并统计各跳主机出现的频率，就能估计出流量在多条路径之间的分配比例。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 亲手用时间戳相减验证 traceroute 报告的 RTT，是理解"往返时延如何测得"的最好方式：源主机看不到对方的时钟，它能依赖的只有自己的本地时钟——发出时刻减去收到 ICMP 应答的时刻，就是一个 RTT 样本。这个测量把双向传播时延、沿途每台路由器的排队时延（queuing delay）与处理时延都算在内，因此会随网络负载波动。回想你在 Lab 3 实现 TCPSender 时如何维护超时重传定时器（RTO）：用滚动平均与偏差去估计 RTT，本质上就是对一个带噪声的随机变量做期望的在线估计——这正是概率论里估计量的思路。本题用第 74 号与第 63 号分组的时间戳相减得到约 12 ms，与 traceroute 报告值吻合，说明这些测量在毫秒精度上是一致的；这也侧面印证了 ICMP 应答由"真正转发过探测分组的那台路由器"产生，而不是被网络路径上的其他设备代答。
