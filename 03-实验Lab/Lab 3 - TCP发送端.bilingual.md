### <span style="color:#c0392b;">3 Lab 3：TCP 发送端（The TCP Sender）</span>

TCP 是一种在不可靠数据报之上可靠地传输**一对**流量控制字节流（每个方向一条）的协议。TCP 连接由两方参与，每一方同时扮演两种角色：自己出站字节流的"发送端"（sender），以及对端入站字节流的"接收端"（receiver）。这两方被称为连接的"端点"（endpoints），或"对等方"（peers）。

本周你将实现 TCP 的"发送端"部分：它负责从一个 ByteStream（由发送侧应用创建并写入）读取数据，并把字节流切分为一系列出站 TCP 报文段（segment）。在远端，TCP 接收端把这些报文段（指那些真正到达的段——它们未必全都到得了）转换回原始字节流，并把确认（acknowledgment，ACK）与窗口通告（window advertisement）发回发送端。

你的 TCPSender 需要负责以下事项：

- 跟踪接收方的窗口（处理传入的 ackno 与 window size）；
- 在可能时填满窗口：从 ByteStream 读取数据，创建新的 TCP 报文段（必要时含 SYN 和 FIN 标志）并发送；
- 跟踪哪些段已发送但尚未被接收方确认——<span style="color:#00838f;">我们把这些段称为"未确认段"（outstanding segments）</span>；
- 当已发送的段经过足够长的时间仍未被确认时，重传（resend）这些未确认段。

**为什么要做这个？** 基本原则是：只要接收方允许，就尽量发送（填满窗口），并不断重传，直到接收方确认每一个段。<span style="color:#00838f;">这套机制称为自动重传请求（Automatic Repeat Request，ARQ）</span>。发送端把字节流切分成段并发送，发送量以接收方窗口允许为限。多亏你上周的工作，我们知道远端 TCP 接收端只要至少收到每个带序号标记的字节一次——不管顺序如何——就能重组出字节流。发送端的任务就是保证接收端至少收到每个字节一次。

> <span style="color:#7f8c8d;">**脚注 1：** 要记住，接收端可以是任何合法的 TCP 接收端实现——它不一定是你自己写的 TCPReceiver。互联网标准的价值之一，就在于它在行为可能差异很大的端点之间建立了共同语言。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 在 CSAPP ch11 里，你写 webget 时调用的 `write()` 只是把字节交给内核就返回，"可靠送达"完全藏在内核的 TCP 栈里，教材只用一句"TCP 提供可靠字节流"带过。本 Lab 就是拆开这句话：所谓可靠，具体拆成四件事——把字节流切段、给每段编上序列号、记住哪些段已发送但未确认（outstanding）、超时就把最早的未确认段再发一遍，这套循环就是 ARQ。从实现视角看，ARQ 与 CSAPP 里事件驱动的 I/O 思路一致：它不主动死等，而是被三类事件推着走——应用调 `fill_window()` 触发"尽量发新数据"，对端 ACK 到达触发"释放已确认段"，`tick()` 报时触发"检查是否超时重传"。想清楚"状态存在哪、谁来推进"，接口为什么长这样就不言自明了。把这段话和 §3.2 的四个方法一一对照，你会发现每个方法恰好对应一个事件入口。

#### <span style="color:#c0392b;">3.1 TCPSender 何时断定一个段已丢失并再次发送？</span>

你的 TCPSender 将发送一批 TCPSegment。每个段包含来自出站 ByteStream 的一段（可能为空的）子串，用序列号（sequence number）标明其在字节流中的位置，并在流的开头打上 SYN 标志、在结尾打上 FIN 标志。

除了发送这些段，TCPSender 还必须跟踪自己的未确认段，直到它们占用的序列号被完全确认。TCPSender 的拥有者会周期性地调用 TCPSender 的 tick 方法，表示时间流逝。TCPSender 负责检查自己持有的未确认 TCPSegment 集合，判断"最早发送的段"是否已悬置过久（outstanding for too long）而未获确认（即其占用的所有序列号都未被确认）。若是，则该段需要被重传（再发一次）。

以下是"悬置过久"的定义规则。你将要实现这套逻辑，它有点细节繁杂，但我们不希望你担心隐藏的测试用例故意刁难你，或者把它当成 SAT 的文字应用题来对待。本周我们会给出一些合理的单元测试，等你完成整个 TCP 实现后，Lab 4 会提供更完整的集成测试。只要你能 100% 通过这些测试，且你的实现是合理的，就没有问题。

> <span style="color:#7f8c8d;">**脚注 2：** 这些规则基于 TCP"真实"规则（RFC 6298 第 5.1 至 5.6 条建议）的简化版。这里的版本略有简化，但你的 TCP 实现仍能与互联网上的真实服务器对话。</span>

**为什么要做这个？** 总目标是让发送端及时发现段丢失并需要重发。重发前等待多长时间很重要：你不希望发送端等太久才重发（那会延迟字节到达接收端应用），但也不希望它重发一个"只要再等一会儿就会被确认"的段——那会浪费互联网宝贵的容量。

规则如下：

1. 每隔几毫秒，TCPSender 的 tick 方法会被调用一次，参数告诉它自上次调用以来过去了多少毫秒。请用它来维护一个"TCPSender 存活总毫秒数"的概念。请不要试图从操作系统或 CPU 调用任何"time"或"clock"函数——tick 方法是你感知时间流逝的唯一途径。这能保证确定性（deterministic）与可测试性。
2. TCPSender 被构造时会得到一个参数，即重传超时（retransmission timeout，RTO）的"初始值"。RTO 是重发一个未确认 TCP 段前等待的毫秒数。RTO 的值会随时间变化，但"初始值"保持不变。起始代码把 RTO 的"初始值"保存在名为 `initial_retransmission_timeout` 的成员变量中。
3. 你将实现重传定时器（retransmission timer）：一个可以在某个时刻启动的闹钟，一旦 RTO 时长过去，闹钟就会"到期"（expires）。我们强调：这种时间流逝的概念来自 tick 方法被调用——而不是获取实际的时刻。
4. 每当发送一个含数据的段（在序列号空间中长度非零）时（无论是首次发送还是重传），如果定时器未在运行，就启动它，使其在 RTO 毫秒后（按当前 RTO 值）到期。
5. 当所有未确认数据都已被确认时，关闭重传定时器。
6. 如果 tick 被调用且重传定时器已到期：
   - (a) 重传最早（序列号最低）的、尚未被 TCP 接收端完全确认的段。你需要把未确认段存储在某种内部数据结构中，以便能够做到这一点。
   - (b) 如果窗口大小非零：
     - i. 跟踪连续重传次数并加一，因为你刚刚重传了某个段。你的 TCPConnection 将利用这个信息判断连接是否已无望（连续重传次数过多）而需要中止。
     - ii. 将 RTO 的值加倍。
   - (c) 重启重传定时器，使其在 RTO 毫秒后到期（按上一步加倍之后的 RTO 值）。
7. 当接收方给发送方一个确认了新数据成功到达的 ackno（该 ackno 对应的绝对序列号大于之前任何 ackno）时：
   - (a) 把 RTO 重置回"初始值"。
   - (b) 如果发送方还有未确认数据，重启重传定时器，使其在 RTO 毫秒后（按当前 RTO 值）到期。
   - (c) 把"连续重传次数"清零。

你可能想把重传定时器的功能实现在一个单独的类里——由你决定。如果这样做，请把它加到已有文件（tcp_sender.hh 和 tcp_receiver.hh）中。

> <span style="color:#7f8c8d;">**脚注 3：** 这叫指数退避（exponential backoff）——它在糟糕的网络上放慢重传速度，避免进一步搅乱局面。我们稍后会在课上学到更多。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这套重传规则有真实出处：自适应 RTO 估计与指数退避源自 Van Jacobson 与 Michael J. Karels 1988 年的 SIGCOMM 论文《Congestion Avoidance and Control》，RFC 6298 是其工程化的简化版，所以脚注才说"能与真实服务器对话"。本课程的规则是它的教学版：去掉了 RTT 的在线估计（Jacobson 算法里的 SRTT/RTTVAR 加权平均），只保留固定初值与指数退避。从概率论视角看，"第几次重传才成功"可以粗略建模为几何分布：每次重传后段仍丢失的概率与网络拥塞程度相关，拥塞越重，密集重传越是在火上浇油。把 RTO 每轮加倍（乘性退避）能让期望重传频率随失败次数指数级下降，等价于用一行乘法代码换取拥塞时的自律——这正是后面课程"AIMD 加性增、乘性减"中"乘性减"思想的雏形。另外注意规则 1 的设计：时间只能从 tick 注入，任何系统时钟调用都会让测试不可复现，这与 CSAPP 中"让随机性可控才能调试"的经验一致。

#### <span style="color:#c0392b;">3.2 实现 TCP 发送端（Implementing the TCP sender）</span>

好！我们已经讨论了 TCP 发送端的基本工作（给它一个出站 ByteStream，把它切分成段、发给接收方，如果没能很快得到确认就不断重发），也讨论了何时断定某个未确认段已丢失、需要重发。

现在来看你的 TCPSender 要提供的具体接口。它需要处理四个重要事件，每个事件最终都可能发送一个 TCPSegment：

1. **`fill_window()`（填充窗口）**：TCPSender 被要求填满窗口：它从输入 ByteStream 读取数据，并以 TCPSegment 的形式尽可能多地发送字节，前提是还有新字节可读且窗口有空间。你要保证发送的每个 TCPSegment 都完整落在接收方窗口之内。让每个段尽量大，但不能超过 `TCPConfig::MAX_PAYLOAD_SIZE`（1452 字节）给出的值。可以用 `TCPSegment::length_in_sequence_space()` 方法统计一个段占用的序列号总数。你的 TCPSender 维护一个名为 `next_seqno` 的成员变量，保存从零开始的出站绝对序列号。每发送一个段，就把 `next_seqno` 增加该段的长度，这样你就知道下一个段该用什么序列号。
2. **`ack_received()`（收到确认）**：从接收方收到一条确认消息，告知窗口新的左边缘（= ackno）与右边缘（= ackno + window size）。TCPSender 应检查自己的未确认段集合，移除其中已被完全确认的段（即段内所有序列号都小于 ackno 的段）。如果窗口腾出了新空间，TCPSender 可能需要再次填充窗口。若 ackno 看起来无效——即它确认的是发送方尚未发送的数据——此方法返回 false。
3. **`tick()`（时间流逝）**：时间已流逝；TCPSender 将检查重传定时器是否到期，若到期则重传序列号最低的未确认段。
4. **`send_empty_segment()`（发送空段）**：TCPSender 应生成并发送一个在序列号空间中长度为零的 TCPSegment，且其序列号被正确设置为 `next_seqno`。当拥有者（你下周要实现的 TCPConnection）想发送一个空的 ACK 段时，这很有用。这类不携带数据、不占用序列号的段不需要被当作"未确认段"跟踪，也永远不会被重传。

要完成 Lab 3，请查阅完整接口文档：https://cs144.github.io/doc/lab3/class_tcp_sender.html ，并在 tcp_sender.hh 与 tcp_sender.cc 文件中实现完整的 TCPSender 公共接口。我们预计你会想添加私有方法和成员变量，可能还需要一个辅助类。

> <span style="color:#7f8c8d;">**脚注 4：** 重要的是，这个重传决定不必查看接收方窗口：该段首次发送时位于窗口内，且尚未被确认，所以它现在仍在接收方窗口内。接收方不应"收缩"窗口右边缘——你可以假定右边缘保持不变或向右移动。</span>

#### <span style="color:#c0392b;">3.3 常见问题与特殊情况（FAQs and special cases）</span>

<span style="color:#2471a3;">**[question]**</span> **我该怎么"发送"（send）一个段？**

答：把它压入（push）`segments_out` 队列。对你的 TCPSender 而言，只要压入这个队列就算发送完毕。很快拥有者就会来弹出它（通过公共访问器方法 `segments_out()`）并真正发送。

<span style="color:#2471a3;">**[question]**</span> **等等，我怎么既"发送"一个段，又把同一个段作为未确认段跟踪起来，以便之后知道该重传什么？难道我不必给每个段做一份拷贝吗？那不浪费吗？**

答：当你发送一个含数据的段时，你大概会把它压入 `segments_out` 队列，同时在某个数据结构里保留一份拷贝，用于跟踪可能需要重传的未确认段。这其实并不怎么浪费，因为段的有效载荷（payload）是以引用计数的只读字符串（一个 Buffer 对象）存储的。所以不必担心——它并不会真的拷贝 payload 数据。

<span style="color:#2471a3;">**[question]**</span> **在收到接收方的 ACK 之前，我的 TCPSender 应把接收方窗口大小默认成多少？**

答：一个字节。

<span style="color:#2471a3;">**[question]**</span> **接收方告诉我它的窗口大小是 0 字节。我该就此卡住、再也不发任何数据吗？**

答：不。如果接收方告诉你窗口为 0 字节，请像保存其他窗口通告一样保存这条信息，因为它对 §3.1 描述的重传行为有影响。但到了要填窗口的时候，就把窗口大小当作 1 字节。<span style="color:#00838f;">这叫零窗口探测（zero window probing）——周期性地探测接收方，看它自上次通告以来是否腾出了新的窗口空间。</span>最坏的情况不过是接收方忽略你这个 1 字节的段。

> <span style="color:#7f8c8d;">**脚注 5：** 在更接近生产级别的 TCP 实现中，零窗口探测行为要更复杂一些，但也复杂不了太多。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 零窗口探测与你在 CSAPP ch11 体验过的阻塞读写在协议层是同一枚硬币的两面。当你不调 `read()` 时，接收缓冲区被填满，对端 TCP 就只能通告窗口为 0；而发送端应用调 `write()` 后数据滞留在发送缓冲里，谁也不能动——如果双方恰好都在等对方，连接就死锁了。TCP 的解法不是引入新的同步机制，而是让发送端周期性发一个 1 字节的小段去"戳"一下接收方：若对方腾出了空间，就会用新窗口通告回应，数据流动恢复；若没有，也只是浪费一个几乎不占序列号空间的探测段。这里的实现要点是"保存 0 但按 1 填充"：窗口为 0 的通告必须原样记录（它决定超时重传语义），而填充逻辑把 0 钳位到 1。你可以把它类比成 CSAPP 里用非阻塞 I/O 或轮询打破阻塞的做法——不优雅，但简单、正确、够用。

<span style="color:#2471a3;">**[question]**</span> **如果一个确认只部分确认了某个未确认段，我该怎么办？我该试着把已被确认的字节裁剪掉吗？**

答：真实的 TCP 发送端可以这么做，但在本课程中不需要这么讲究。把每个段当作整体未确认，直到它被完全确认——即它占用的所有序列号都小于 ackno。

<span style="color:#2471a3;">**[question]**</span> **如果我发送了三个分别包含 "a"、"b"、"c" 的段，它们一直得不到确认，之后我可以在一个包含 "abc" 的大段里重传它们吗？还是必须逐个重传每个段？**

答：再说一次：TCP 发送端可以这么做，但在本课程中不必讲究。只需逐个跟踪每个未确认段，当重传定时器到期时，把最早的未确认段再发一次即可。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这两条 FAQ 的"不要裁剪"规则，其实是把问题整形成用最简单的数据结构就能解的形状。既然每个段要么整体 outstanding、要么整体确认，那么"最早的未确认段"永远在队列队首：用 `std::deque`（或 `std::queue`）存未确认段，重传定时器到期时取 `front()` 即为应重传的段，`ack_received()` 时从队首逐个弹出所有已完全确认的段，都是 O(1) 均摊操作。对比你在 CLRS 中学过的：若允许按字节裁剪，你就需要按序列号组织的更复杂结构（支持区间删除与合并），复杂度与出错面都会上升。课程约束下的正确策略是：识别出这个不变量——"队内序列号连续递增、队首最早"——并用断言守住它，这正是 Lab 0 反复强调的防御式编程（defensive programming）。写 §3.2 维护 `next_seqno` 时，同样的思路也适用。

<span style="color:#2471a3;">**[question]**</span> **空段要不要存进我的"未确认"数据结构、必要时重传？**

答：不要——应当被当作未确认段跟踪、可能被重传的，只有那些携带数据的段，即占用一定序列号长度的段。空 ACK 不需要被记住，也不需要重传。

### <span style="color:#c0392b;">4 开发与调试建议（Development and debugging advice）</span>

1. 请在 tcp_sender.cc 文件中实现 TCPSender 的公共接口（以及任何你想要的私有方法或函数）。你可以在 tcp_sender.hh 中为 TCPSender 类添加任意私有成员。
2. 编译后可以用 `make check_lab3` 测试你的代码。
3. 请重读 Lab 0 文档中"使用 Git"一节，并记住让代码保持在其发布时的 Git 仓库的 master 分支上。做小的提交，写清楚"改了什么、为什么改"的好提交信息。
4. 请努力让你的代码对将按代码风格评分的 CA（课程助理）可读。为变量使用合理清晰的命名约定。用注释解释复杂或微妙的代码片段。使用防御式编程——显式检查函数前置条件或不变量，任何出错之处都抛出异常。在设计中使用模块化——识别共同的抽象与行为，并尽可能将其抽出。成块的重复代码和巨大的函数会让你的代码难以读懂。
5. 也请遵守 Lab 0 文档描述的"现代 C++"风格。cppreference 网站（https://en.cppreference.com ）是极好的资源，不过做这些实验你不需要任何高深的 C++ 特性。（有时你可能需要用 move() 函数来传递不可拷贝的对象。）
6. 如果你遇到了段错误（segmentation fault），那说明真的出了问题！我们希望你用一种让段错误极其罕见的安全编程风格来写代码（不用 malloc()、不用 new、不用指针、在不确定处写抛异常的安全检查等）。尽管如此，调试时你可以用 `cmake .. -DCMAKE_BUILD_TYPE=RelASan` 配置 build 目录，启用编译器的"消毒器"（sanitizers）来检测内存错误与未定义行为，并在其发生时给出漂亮的诊断。你也可以使用 valgrind 工具。也可以用 `cmake .. -DCMAKE_BUILD_TYPE=Debug` 配置并使用 GNU 调试器（gdb）。记住这些设置只用于调试——它们会显著拖慢程序的编译与执行。要回到"Release"模式，最可靠/最省心的办法就是删掉 build 目录重建一个。
