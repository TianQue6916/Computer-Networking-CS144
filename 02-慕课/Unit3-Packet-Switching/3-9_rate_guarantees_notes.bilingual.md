本讲从一次输出队列（output queue）的特写动画开始：把注意力聚焦到分组交换机的某个输出端口上，观察各输入端口的分组在这里排队、离开。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：FIFO 队列是一场"自由竞争"</span>

队列里是一场自由竞争（free for all）。如果有很多流（flow）经过这个队列，它们将按 FIFO（先进先出）顺序离开：谁发送得最多，谁就获得最高的速率。如果存在一个非常贪吃的大流（hog），一个小流可能被完全挤出去。这会鼓励坏行为——对一条流来说最优的策略，就是尽可能快地发送、把所有其他流都挤出去。这不太友好……激励设计很糟糕。

再设想有些流量非常紧急——例如控制流量，或某路重要的视频流量。FIFO 没有任何区分重要性的手段。它的规则只是：如果你先到、且队列里还有空间，你就是最重要的分组。

对共享这个队列的每条流的速率，我们说不出任何有意义的东西。注意：<span style="color:#00838f;">如果一个分组成功进入了队列，它需要等待的最大时间是 $B/R$</span>（缓冲区大小 $B$ 除以链路速率 $R$）——这个观察我们稍后会用到。

🎥 *CS144 教授在视频中解释: "谁发送最多的包实际上将获得这个输出链路的最高使用率……如果流量大到惊人，通过一点流量很容易被完全挤出"*（字幕来源：048 - p47 3-9 Packet Switching - Principles Rate guarantees.zh.srt）

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这一页其实是一堂微型的激励设计课：FIFO 给了每个用户"多发送多受益"的激励，理性个体必然贪吃，最终所有人都受害——这就是经典的公地悲剧（tragedy of the commons）在网络里的样子。网络设计者有两种对症药方：一是在交换机内部改调度算法（本讲后面从严格优先级到 WFQ 正是这条线），二是在端系统上改行为规范——后续单元的 TCP 拥塞控制（AIMD 加性增、乘性减）就是让"贪吃的流自动退避"，两条线互补。另外记牢 "$B/R$ 是已入队分组的最大等待时间" 这个小结论：缓冲区最多 $B$ 个比特，队列以 $R$ 的速率排空，最坏也就等 $B/R$——3-10 计算时延保证时会直接拿它当积木。这提醒我们读讲义时要留意这类"顺手给出、后面回收"的结论，它们往往是体系的前后呼应。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 4：本讲目标</span>

本节视频将讨论：如何给某些流比其他流更高的优先级；以及如何给每条流一个不同的服务速率。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 5~6：严格优先级队列</span>

设想我们把输出端口上的单个 FIFO 队列换成两个优先级队列（priority queues）：一个高优先级队列和一个低优先级队列。分组到达时，我们根据它的重要性决定放进哪个队列。然后——因为是严格优先级（strict priority）——规则是：永远先服务高优先级队列；<span style="color:#00838f;">只有当高优先级队列为空时，才服务低优先级队列。</span>

后果是：高优先级流量"看不见"低优先级流量——完全不受其影响，就好像高优先级流量独享了一张私有网络。严格优先级相当常用，如今大多数交换机和路由器都支持它。

决定一个分组进哪个队列的常用办法，是在首部里标记它的优先级。例如 IP 首部有一个叫 ToS（Type of Service，服务类型）的字段，可以在里面标记分组的优先级。它可用于：VIDEO（视频）流量 > Email；Control（控制）> DATA（数据）；或金卡用户 > 银卡用户。这对某些场景没问题，但它会饿死（starve out）低优先级流量——所以只有当高优先级流量总量比较小时才使用它。如果高优先级流量可能完全霸占链路，我们就不想用这个方案。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 严格优先级是"用饥饿换低时延"的极端交易：高优先级队列时延与低优先级流量无关（这正是它对 VoIP、网络控制报文有价值的原因），代价则是低优先级可能无限期挨饿。什么时候可以接受？讲义给出的判据很实用：当且仅当高优先级负载占比"合理地小"——你可以粗算一下：若高优先级流的聚合速率占链路的 $\rho$，低优先级分组的等待就大致被拉长到 $\frac{1}{1-\rho}$ 倍，$\rho\to 1$ 时任何调度都救不了。用你概率论的直觉说，这与 M/M/1 里时延随利用率 $\rho$ 爆炸是同一个现象（ps_queue_props 会给出公式）。ToS 字段今天演化成了 DSCP（ differentiated services 码点），云厂商区分"批量同步流量"与"交互式 SSH 流量"用的就是它——课堂概念与生产系统之间的距离，比你想的近得多。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 7：加权队列</span>

于是，我们可能想要这样的方案：让一个队列里的流量比另一个队列里的流量权重更高——例如，上队列的流量以另一个队列**两倍**的速率被服务。我们可以把它推广到有 $n$ 个队列、每个队列各有自己的速率的情形。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 8：实现难点——分组变长</span>

实践中怎么做到？如果所有分组等长，那很简单：每轮依次从第 1 个队列服务 $\dfrac{w_1}{\sum_i w_i}$ 个分组，再从第 2 个队列服务 $\dfrac{w_2}{\sum_i w_i}$ 个，如此往复。这很好，但真实分组是**变长**的——可能短到 64 字节，也可能长达几千字节，即相差 2~3 个数量级。要防止长分组挤占短分组，显然必须把分组长度考虑进去。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 9：按比特轮转与重组</span>

办法一：按**轮（round）**进行，每轮给每个队列 $i$ 服务至多 $w_i$ 个比特。这样它们就得到了正确的加权服务。然后，用一个队列把所有碎片重新拼装成完整分组再发送出去。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 10：WFQ——"假装"逐比特服务的聪明办法</span>

更巧妙的办法：<span style="color:#00838f;">"假装"我们对每个分组逐比特服务，算出如果真这么做它将在何时服务完毕，然后按这个"假想完成顺序"来真实地服务分组。</span>

具体做法（非常简洁聪明）：

- 定义一个**轮（round）**为"访问并服务完每一个队列"所需的时间；
- 每一轮中，给队列 $i$ 服务 $w_i$ 个比特；
- 所有计算一律以**轮数（round number）**为坐标。

当分组 $k$ 到达时：

```math
F_k \;=\; \max\!\left(F_{k-1},\ \text{now}\right) \;+\; \frac{L_k}{w_k}
```

其中 $L_k$ 是分组长度，$w_k$ 是它所属流的权重（讲义记号；严格说是该流自己的权重 $w_i$）。然后按 $F_k$——即**完成轮（finishing round）**——的顺序服务各分组。

三个很好的性质：1. 完成时间可以在分组**到达时刻**就被确定；2. 分组按完成时间的顺序被服务。这种方法称为加权公平排队（Weighted Fair Queueing，WFQ），或分组化广义处理器共享（Packetized Generalized Processor Sharing，PGPS）。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> WFQ 的核心戏法值得用一句话戳破：它把"连续流体模型"（每个流同时获得 $w_i/\sum w_j$ 比例的带宽，像倒水一样）当作参照系，让真实世界里不可分割的分组**按照自己在流体模型中的完成时刻排队**。$F_k=\max(F_{k-1},\text{now})+\frac{L_k}{w}$ 这个递推式你应该感到眼熟：它与 CLRS 里动态规划的递推结构同型——当前事件的最优标记由"前一个事件"与"现在"取 max 后再加上本步代价，$\max$ 项处理的正是"队列空转后重新开始计时"的情形。它是如何解决变长问题的？因为按"假想完成轮"排序，一个 1500 字节的长分组虽然真实发送要占线很久，但它只按自己的 $L/w$ 占用一个排队次序，不会像朴素轮询那样把排在后面的短分组整体拖后。这个算法由 Demers、Keshav、Shenker 于 1989 年提出（FQ 一文），Parekh 与 Gallager 在 1993 年证明了它在漏桶约束下有严格的时延界——正是 3-10 时延保证的数学地基。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 11：完成轮 → 完成时间的偏差与长期速率保证</span>

在时间轴上画出"完成轮（finishing round）→ 完成时间（finishing time）"的示意：按轮数算出的完成时刻与真实完成时刻之差，记为 $\Delta$，对系统中**每一个**分组都满足

```math
\Delta \;<\; \frac{L_{\max}}{R}
```

（$L_{\max}$ 为最大分组长度，$R$ 为链路速率）。这意味着从长期看，$\Delta$ 会被摊薄（amortized），每条流的速率就是

```math
r_i \;=\; \frac{w_i}{\sum_j w_j}\,R
```

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 12~13：结束</span>

本讲结束（图示总结 slide，文字极少）。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "$\Delta\lt L_{\max}/R$、长期被摊薄"这句总结，本质上是给 WFQ 开出了一张速率保单：逐个分组看，真实服务顺序与理想流体模型有偏差，但偏差被一个常数上界封顶——分组再长，最多"拖欠"一个最大分组的发送时间；只要时间轴拉长，偏差在平均中消失，每条流稳定拿到 $r_i=\frac{w_i}{\sum_j w_j}R$。你可以把它理解成概率论大数定律的确定性版本：不依赖随机性，靠"偏差有界"这一条就能保证长期平均精确收敛。这张保单为什么重要？因为 3-10 的时延保证逻辑是"知道每流服务速率的下界 $r_i$ + 缓冲区上界 $B$ ⇒ 排队时延上界 $\frac{B}{r_i}$"——WFQ 恰好提供了那个下界。于是这一讲与下一讲合成一条完整的推理链：调度算法（机制）→ 速率下界（性质）→ 时延上界（保证）→ 端到端承诺（应用）。
