### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 2：本讲大纲</span>

本视频将给出传播时延（propagation delay）与分组化时延（packetization delay）的若干有用定义，并用它们推出一个分组端到端时延（end-to-end delay）的表达式。我还会讲排队时延（queueing delay），以及它如何让端到端时延变得不可预测。最后，我将解释为什么不可预测的端到端时延意味着 YouTube、Skype 这类应用需要使用播放缓冲区（playback buffer）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：传播时延</span>

我们从传播时延的定义开始。<span style="color:#00838f;">传播时延是一个比特的信息以传播速度 $c$ 走过一条链路所需的时间。</span>它只由链路长度 $l$（本例中）和比特传播速度 $c$ 决定，表达式就是 $d_{prop} = \dfrac{l}{c}$。我们用变量 $c$，是因为在我们关心的大多数链路里，传播速度接近光速。例如，在一对双绞线里，比特大约以 70% 光速传播；在光纤里则稍微慢一点。在本讲的大部分例子中，我们假设比特以 $2\times10^8$ m/s 传播——足够接近了。

注意：<span style="color:#00838f;">传播时延不依赖链路的数据速率（data-rate）。</span>链路跑 1 kb/s 还是 10 Gb/s 都无所谓——传播时延只是每个比特的传播速度和线缆长度的函数。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "传播时延与速率无关"是最容易被忽视却最重要的一条，值得用一个物理图像钉死：链路像一根注满比特的管道，传播时延是"一个比特从管子这头流到那头"的时间，由管长和流速（光速的一个比例）决定；而数据速率决定的是"每秒能往管子里塞进多少个比特"——两个完全独立的维度。CSAPP 里有个帮助你建立尺度的说法：光在一个纳秒里走约 30 cm，所以信号穿越 10000 km 的太平洋往返一次至少要上百毫秒，这是物理定律给的硬下界，任何协议优化都动不了它。由此还能推出一个常见混淆点：把 $l/c$（传播）和 $p/r$（传输/分组化）搞混——前者是"路上花的时间"，后者是"上车花的时间"。如果一段 100 km 链路带宽从 1 Mb/s 升级到 1 Gb/s，传播时延一动不动，但传输时延缩小 1000 倍；反过来把服务器搬到更近的机房，降的是传播时延。CDN 的本质就是缩短 $l$。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 4：分组化时延</span>

另一个有用的定义是分组化时延（packetization delay）。<span style="color:#00838f;">它是从分组的第一个比特被放上线路，到最后一个比特被放上线路所经历的时间。</span>它由我们能把比特放上线路的速度——即数据速率（data-rate）$r$——决定。如果链路跑 1 kb/s，我们每秒能往线路上放 1000 个新比特；如果跑 10 Gb/s，每秒能放 100 亿个。

链路的数据速率由"能把比特挤得多紧"决定。例如，一条 1 Gb/s 的链路每纳秒放一个比特上线。是什么限制了链路的数据速率，我们会在后面关于物理链路的视频里看到。

注意：<span style="color:#00838f;">分组化时延只是分组长度和数据速率的函数</span>：$d_{trans} = \dfrac{p}{r}$。链路多长、比特沿线跑多快，都与它无关。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 5：两种时延合流</span>

接下来我们看如何用这两种不同类型的时延，确定端到端时延——即一个分组从源穿过网络到达目的地所需的时间。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 6：端到端时延的定义</span>

<span style="color:#00838f;">端到端时延是从我们把第一个比特放上第一条链路起，直到分组的最后一个比特到达目的地为止的时间。</span>我们可以把路径上每一条链路的传播时延与分组化时延加起来，算出端到端时延。在图示的例子里，分组要穿越 4 条链路：先算第一个比特到达第一台交换机的时间，再算最后一个比特到达第一台交换机的时间，然后对路径上每条链路重复这一过程。总体端到端时延的表达式如下（由讲义上下文整理）：

```math
t_{\mathrm{e2e}} \;=\; \sum_{i=1}^{4}\left(\frac{p}{r_i}+\frac{l_i}{c}\right)
```

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 7：逐跳时间线与存储转发</span>

现在仔细看看细节。我把链路和交换机拉伸成一条单路径，把网络其余部分去掉。这是一张时间线图，显示比特和分组如何沿链路行进：第一个比特从 A 到 S1 需要 $l_1/c$；分组的最后一个比特比第一个比特晚 $p/r_1$ 被发出，所以到 $l_1/c + p/r_1$ 时，整个分组已到达 S1。

互联网路由器是我们所说的"存储转发（store-and-forward）"分组交换机：它们要等整个分组到齐，才查地址、决定下一跳发往哪里。它们本可以在看到首部之后就开始转发、不等整个分组到齐——这叫"直通（cut-through）交换"。但互联网路由器一般不这么做。在后面的视频和一些习题里我们会看到直通分组交换机的例子。

回到我们的例子：路由器先存储、再转发分组。在 S1 到 S2 的链路上，第一个比特花 $l_2/c$ 到达 S2，最后一个比特晚 $p/r_2$ 秒到达。如此继续直到分组到达 B。端到端时延表达式把路径上所有时延分量加了起来。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "存储转发"是理解本单元一切时间公式的钥匙：交换机必须收完整个分组才能转发它，于是路径上每台交换机都为这个分组独立贡献一份 $p/r_i$ 的传输时延，$N$ 跳就有 $N$ 份。这立刻引出一个反直觉的推论（3-5 会正面推导）：同样 100 个比特，切成一个 100 bit 的大分组要走完 $4$ 份 $p/r$，切成 4 个 25 bit 的小分组则各跳的传输时延变成 $25/r$，且小分组可以像流水线一样在不同链路上并行前进——省下的就是"最后等整包收齐"的那部分。这正是 6.006/CSAPP 里流水线（pipelining）思想在网络上的翻版：总时间由"最慢一级"和"流水级数"共同决定。至于直通交换（cut-through），它牺牲了差错检测的完整性（没等 CRC 校验就转发），换来更低的每跳时延，数据中心交换机里确实有用；你将在习题里算它的账。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 8：排队时延——唯一的随机项</span>

好了，我还没有告诉你完整的故事。分组交换的特点是：你的分组要和别的用户的分组共享链路。当若干分组同时到达、都想去 S2 到 S3 的链路时，其中一些分组就必须在路由器的队列（queue，或称分组缓冲区 packet buffer）里等待。我们说 S2 到 S3 的链路发生了拥塞（congested），因为有很多分组排队等着走这条链路。分组缓冲区帮助我们避免丢包：缓冲区越大，等待穿过链路的分组越不容易被丢弃。分组缓冲区是分组交换的基础——如果没有缓冲区，那么每当两个分组同时到达、都想走同一条链路，我们就得丢弃一个。

分组缓冲区改变了端到端时延的表达式。如果我们的分组到达时队列里已有分组，它就必须排在缓冲区里那些先到的分组后面。默认情况下，互联网路由器的分组缓冲区是 FCFS（先进先出），即分组按到达顺序被发送。所以如果我们前面排着 3 个分组，就必须等 3 个分组化时延才轮到自己出发。考虑沿途每个分组交换机处的排队时延之后，改进的端到端时延表达式为（由讲义上下文整理）：

```math
t_{\mathrm{e2e}} \;=\; \sum_{i=1}^{4}\left(\frac{p}{r_i}+\frac{l_i}{c}\right) \;+\; \sum_{i=1}^{4} d_{q,i}
```

要记住非常重要的是：<span style="color:#00838f;">排队时延是不可预测的</span>——它取决于网络中其他用户发送的流量。对我们而言，排队时延是一个随机变量（random variable）。它是端到端时延表达式里唯一的随机变量——其余一切都是确定性的。

如果你不信端到端时延不可预测，我们来实测。我将用一个被广泛使用的工具 "ping" 测量我的计算机与互联网上其他计算机之间的端到端时延。ping 实际测量的是 RTT（往返时延），即两个方向上的端到端时延之和。你自己的电脑上也有 ping 命令，可以照着我接下来做的测量自己重复一遍。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "排队时延是表达式里唯一的随机变量"这句话其实是整个本单元（乃至整个网络数学）的分界线：它把时延劈成"确定性部分"（$\sum p/r_i + \sum l_i/c$，可精确计算、可物理改进）和"随机部分"（$\sum d_{q,i}$，只能建模与测量），3-4 的播放缓冲区、3-5 的确定性队列模型、ps_queue_props 的 M/M/1，全都建立在"如何驯服这个随机项"上。你已经学过概率论前 7 章，这里正该把随机变量、期望、方差的概念搬进来：确定性部分决定时延的均值水平，排队时延决定它的方差与尾部。ping 是最朴素的测量工具，它发 ICMP 回显请求并计时——CSAPP 第 11 章里你见过 ICMP 与 IP 同层封装的关系；注意 ping 测的是 RTT（去加回两程），去程与回程的排队通常不对称，所以 RTT 的波动是两个方向随机性的叠加。后面两页实验会看到：均值之上，方差才 real-time 应用的生死所在。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 12：Stanford → 清华实测</span>

我重复了这个实验，从 Stanford 到中国的清华大学，约 10,000 km 之遥。不出所料，RTT 值大得多，因为传播时延高得多。但注意 RTT 样本的方差也大得多——范围从约 320 ms 一直到 500 ms 以上。这个方差来自我的 ping 分组在网络上遇到的其他用户的分组：我的分组与他们的分组在沿途路由器的缓冲区里相遇，我的分组要等多久，取决于我的分组到达时恰好有多少别的分组在那里排队。约 200 ms 的波动范围意味着，可变的排队时延几乎占了整体端到端时延的一半。
