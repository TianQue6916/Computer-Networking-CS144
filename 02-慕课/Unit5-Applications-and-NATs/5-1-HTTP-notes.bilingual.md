### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 1：HTTP（HyperText Transfer Protocol，超文本传输协议）</span>

超文本传输协议（HyperText Transfer Protocol，HTTP）是现代互联网（Internet）的基石之一。它最初的用途是传输文档，而如今它的用途远不止于此：比如从 Netflix 这类公司流式传输媒体，或者通过浏览器下载并运行的脚本（scripts）来驱动各种网页应用。本节将解释 HTTP 背后的基本概念模型，并给出一些用于分析其性能的解析工具。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 2：HyperText（超文本）</span>

HTTP 的全称是 HyperText Transfer Protocol——那么什么是超文本（HyperText）？超文本是一种文档格式，它允许你在文档中嵌入格式信息与内容信息。每当你下载一个网页，你下载的就是一份超文本（hypertext）文档。与许多其他文档格式（如 Microsoft Word 或 PDF）不同，超文本全部是 ASCII 文本：查看文档源码时，一般不会出现普通文本编辑器无法显示的字符。

以维基百科（Wikipedia）上 HTTP 历史页面的节选为例："History"（历史）这个词用更大的字体显示，有一些链接显示为蓝色，还有一张嵌入的图片，以及一些让页面更易读的格式细节（比如 History 下方的横线）。

而在底层，文档看起来是这样的——这就是浏览器为显示该页面而下载的超文本。所有格式信息都包含在尖括号（angle brackets）内。例如 `<h2>` 表示这是一个标题，应以更大的字号显示。你可以看到 "History" 这个词位于格式标记之外——正如你所见，这个片段里的 "History" 被显示为标题。所以从最基础的层面看，超文本文档就是一个纯文本文档，浏览器根据这些特殊的格式控制符（称为标签，tags）来显示它。例如，超文本链接（hypertext link）只是一个格式标签，它的含义是"点击这个标签内的内容时，应加载这个 URL"。完成这件事的是 A 标签——参见第 227 行处 HTTP V0.9 链接的 A 标签示例。点击那个链接后，浏览器会跳转到 URL `http://www.w3.org/ pub/` 等地址。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：超文本不止是格式——嵌入资源</span>

但超文本有一点超越了"格式"本身：用超文本可以把文档或文件嵌入到其他文件中。在这个维基百科页面上，最简单的例子就是图片。图片的比特并不存储在这份超文本文档里——那会破坏"人类可读的 ASCII 文本"这一性质。相反，超文本提供了一种机制，可以在文档中说"加载另一个文档，并把它放在这里"。看第 220 行——你会看到一个图片标签（IMG tag）。IMG 标签的含义是"从这个 URL 加载图片并显示在这里"。当浏览器为该维基百科页面加载超文本时，它会看到这样的标签，并自动请求这些标签引用的文件。所以当你加载页面时，浏览器会自动请求图片并显示它。

除了图片之外，网页还可以引用各种各样的资源：其他页面、样式表（style sheets）、脚本（scripts）、字体（fonts）等等。看一个例子：请求《纽约时报》（New York Times）的网页，并用浏览器的开发者工具（developer tools）观察这引发的所有请求。可以看到，浏览器请求了大约 20 份文档，从超文本到图片再到广告。

这揭示了超文本的一个极其重要的性质：**请求一个文档可能导致请求更多文档**。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 4：World Wide Web（HTTP）客户端与服务器</span>

（本 Slide 为图示：Client（客户端）通过 Internet（互联网）与 Server（服务器）相连，展示 HTTP 的请求/响应模型。）

在 HTTP 中，客户端（client）打开一条到服务器（server）的 TCP 连接，并向它发送命令。最常见的命令是 GET（请求一个页面）。HTTP 被设计成一种以文档为中心的程序间通信方式。例如，在浏览器里输入 `http://www.stanford.edu/`，浏览器会打开一条到服务器 `www.stanford.edu` 的连接，并对站点根页面发送 GET 请求。服务器收到请求后，检查请求是否有效、用户是否有权访问该页面，然后发回响应。每个响应都关联一个数字状态码。例如，服务器对 GET 回以 `200 OK`，表示请求被接受，响应的其余部分就是文档数据。对 `www.stanford.edu` 而言，`200 OK` 响应中会包含描述 Stanford 主页的超文本。此外还有其他类型的请求，如 PUT、DELETE 和 INFO，以及其他响应，如 `400 Bad Request`。

与超文本本身一样，HTTP 全部是 ASCII 文本：它是人类可读的。例如，一个对《纽约时报》的 GET 请求的开头形如 `GET / HTTP/1.1`；一个成功请求的响应开头形如 `HTTP/1.1 200 OK`。

但基本模型很简单：客户端通过向连接写入数据来发送请求，服务器读取请求、处理它，并向连接写入响应，客户端随后读取响应。客户端读到的数据可能促使它再发出更多的 GET 请求。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 5：HTTP 请求格式（HTTP Request Format）</span>

（本 Slide 为格式图：首行为"request method（请求方法）+ 空格 + URL + 空格 + version（版本）"，其中白色方框表示空格，左箭头表示回车（carriage return，回到行首），下箭头表示换行（newline，换到新的一行）；随后是 headers（首部）——每行一个"header field name（首部字段名）+ value（值）"；然后是一个空行（blank line）；最后是 body（消息体）。）

HTTP 请求长这样。第一行是 ASCII 文本，写明方法（method，如 GET）、该方法的 URL，以及所使用的 HTTP 版本。图中白色方框代表空格：方法与 URL 之间有一个空格，URL 与版本之间也有一个空格。左箭头表示回车——即"回到行首"，下箭头表示换行——即"换到新的一行"。例如在前面请求那个 URL 的例子中，方法（method）是 GET，URL 是 `fullduplex/index.html`，版本很可能是 HTTP/1.1。

第一行（请求行）之后是零个或多个首部（headers）。每行一个首部，每个首部行以首部字段名开头，后跟值。

首部之后是一个空行，随后是消息体（body）。

等等——为什么请求会有消息体？请求的 body 是什么？对于 GET 方法（请求页面）而言，body 是空的。但 HTTP 支持其他方法，例如 POST（发送数据），比如填写表单并提交时就用它。POST 请求通常有消息体。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 6：HTTP 响应（HTTP Response）</span>

（本 Slide 为格式图：首行为"version（版本）+ 空格 + status code（状态码）+ phrase（短语）"，随后同样是 headers、空行与 body。）

HTTP 响应看起来类似。第一行包含 HTTP 版本、状态码（status code）以及与该状态码关联的短语（phrase），例如 `200 OK` 或 `404 Not Found`。之后是零个或多个首部、一个空行，以及响应的消息体。

看看对前面那个 GET 请求的响应长什么样：它是一个 304——表示该网页自浏览器把它放入缓存（cache）以来未被修改过。现在清空浏览器缓存，再次请求该页面：请求中没有 Modified-Since 首部，于是响应是 `200 OK`。

Firefox 的开发者工具让你能看到请求/响应对，但看不到它们的实际格式。为此，用一个简单得多的办法：使用 telnet 程序连接 web 服务器。Telnet 打开一条 TCP 连接：它把你键入的内容写入套接字（socket，套接字），并把读到的内容打印出来。于是 telnet 到 `sing.stanford.edu` 的 80 端口，键入 `GET /fullduplex/index.html HTTP/1.0`。

大量 HTML 返回了。滚动到顶部，可以看到 HTTP 响应 `200 OK`，带有一堆首部、一个换行，然后是消息体——页面的 HTML。`Content-Length` 首部告诉你消息体有多长。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 7：HTTP 小结</span>

- HTTP 是现代互联网的基石应用层协议
- 文本协议（text protocol），人类可读
- 请求/响应（request/response）API
- 以文档为中心（document-centric）

HTTP 是现代互联网的基石协议。虽然它最初以文档为中心、用于抓取页面和文档，但如今它的用途远不止于此。例如，"文档"可以是浏览器作为应用的一部分执行的脚本。不过，请求 URL 并接收响应的基本模型依然成立。HTTP 的一大优点是它是人类可读的文本。你可以亲手键入一个 HTTP 请求并阅读响应——正如前面 telnet 到 80 端口所演示的那样。建议你自己动手玩一玩：用浏览器的开发者工具观察都请求了什么，并进一步了解协议的细节。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> HTTP 是纯文本协议这一点，与你在 CSAPP 第 11 章写过的 echo 客户端/服务器是同一种世界观：套接字（socket）里进出的本来就是字节流，"协议"只是对字节流如何解读的约定。CSAPP 的 homework 里你解析过 echo 协议的简单文本行，而 HTTP 把这个思路推到极致——请求行、首部、空行、消息体，全部可以用 `read()`/`write()` 手工拼出来，telnet 到 80 端口手打 `GET / HTTP/1.0` 就是活证据。这也解释了为什么 HTTP 能成为"基石"：文本协议调试零门槛（Wireshark 或 nc 就能看懂每个字节），任何语言的标准套接字 API 都能直接实现，不需要专门的序列化库。对比二进制协议（后面 BitTorrent 的对等协议就是二进制的），文本协议浪费一些字节换来的是极其低的理解与实现成本。HTTP/1.0 的"一个请求一条连接"模型也值得记住：它是后面两页时延分析的全部前提，也是 HTTP/1.1 引入 keep-alive 的动因。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 8：HTTP/1.0</span>

- 打开连接（open connection）
- 发出 GET（issue GET）
- 服务器在响应后关闭连接（server closes connection after response）

以上就是协议的基本内容：请求、响应。HTTP/1.0 非常简单：想请求一个文档的客户端打开一条连接，发送一个 GET 请求；服务器以状态码（如 `200 OK`）、文档作为响应，并在响应完成后关闭连接。如果客户端想请求第二个文档，就必须打开第二条连接。

当 Web 还主要是文本、顶多带一两张图片时，这种做法完全够用。人们手写网页，把所有格式都手工放进去。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 9：HTTP/1.0 速度——参数设定</span>

- 时延（latency）：50ms
- 请求大小：1 个完整分段（full segment）
- 响应大小：2 个完整分段（即慢启动窗口的大小）
- 分段打包时延（packetization delay）：10ms（请求与响应），链路全双工（full duplex）
- 最大打开连接数：2，连接拆除（teardown）瞬时完成

下面走一遍加载到底需要多长时间。先做几个简化假设：客户端与服务器之间的时延（latency）为 50 毫秒；一个 HTTP 请求恰好装满一个完整 TCP 分段（segment）；响应是 2 个完整分段——正好是一个较小的初始慢启动（slow start）拥塞窗口的大小，这样就不用操心窗口增长的细节。一个完整分段的打包时延（packetization delay）为 10ms，因此请求的打包时延是 10 毫秒，应答是 20 毫秒。最后假设：不含数据的 TCP 分段（如三次握手的 SYN/SYN-ACK 和 ACK 分组）打包时延为零，连接拆除瞬时完成，并且最多可以同时打开 2 条连接。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 10：HTTP/1.0 速度——Case 1：加载单个页面</span>

- 时延：50ms
- 请求大小：1 个完整分段；响应大小：2 个完整分段（慢启动窗口大小）
- 分段打包时延：10ms（请求与响应），全双工
- 最大打开连接数：2，拆除瞬时完成
- Case 1：单个页面（Single page）

继续推导。补充假设：web 服务器可以立即响应，没有处理时延；链路是全双工（full duplex）的，即一个节点可以在同一条链路上同时接收和发送——这意味着请求的打包时延不会影响响应的打包时延。

来看第一种情形：加载单个页面，需要多长时间？

第一步是发送 SYN 的时延：50ms；然后是 SYN-ACK 的时延：又一个 50ms。收到 SYN-ACK 后，客户端可以发送三次握手的 ACK，紧跟其后发出请求（ACK 与请求一起发送）。请求的打包时延是 10ms，所以这一步耗时 60ms（20ms 传播到服务器 + 请求在 ACK 之后打包 10ms + ……实际按事件序列累计）。服务器随后把响应发回来，响应的打包时延是 20ms，这一步耗时 70ms。

各步骤：
1. SYN：客户端发出 SYN，传播 50ms 到达服务器；
2. SYN-ACK：服务器回以 SYN-ACK，传播 50ms 返回客户端；
3. ACK/请求：客户端发送三次握手的 ACK 与 GET 请求。请求打包时延 10ms，加上 50ms 传播，共 60ms；
4. 响应：服务器发送响应（2 个分段），打包时延 20ms，加上 50ms 传播，共 70ms。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 11：Case 1 结果——230ms</span>

- Case 1：单个页面，共 230ms
- SYN：50ms，SYN-ACK：50ms，ACK/请求：60ms，响应：70ms

总时延为 50ms + 50ms + 60ms + 70ms = $50 + 50 + 60 + 70 = 230$ 毫秒。

注意其中 ACK/请求一步的构成：请求打包 10ms 与传播 50ms 串行相加（$10 + 50 = 60$ms），因为完整分段必须先"发上链路"（打包/序列化），最后一位再经过 50ms 传播才能到达服务器；响应一步同理：$20 + 50 = 70$ms。

（本 Slide 为图示：重复展示 Case 1 的时间线汇总——SYN 50ms、SYN-ACK 50ms、ACK/请求 60ms、响应 70ms，总计 230ms。）

单个页面在 HTTP/1.0 下耗时 230ms，其中 100ms 花在三次握手上，130ms 花在请求与响应上。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 13：Case 2：加载含 2 张图片的页面</span>

- 时延：50ms；请求大小：1 个完整分段；响应大小：2 个完整分段（慢启动窗口大小）
- 分段打包时延：10ms（请求与响应），全双工
- 最大打开连接数：2，拆除瞬时完成
- Case 2：加载 2 张图片的页面
  - 第 1 步（页面）——建立连接：100ms，请求/响应：130ms
  - 第 2 步（图片）——100ms，请求/响应：？

来看一个更复杂的例子：一个页面要加载 2 张图片。

把它拆成两步。第一步，客户端请求页面；第二步，客户端用 2 条连接分别请求两张图片。

第一步耗时与单页面例子相同：建立连接 100 毫秒，请求与响应 130 毫秒。

第二步要复杂一点。记住，虽然有两条独立的 TCP 连接，它们共享同一条链路——这意味着一个请求的打包时延会影响另一个。建立两条连接需要 100 毫秒。但两个请求/响应交换需要多久才能完成？

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 14：Quiz（随堂测验）</span>

- 时延：50ms；请求大小：1 个完整分段；响应大小：2 个完整分段（慢启动窗口大小）；分段打包时延：10ms（请求与响应），全双工
- Case 2：加载 2 张图片的页面
  - 第 1 步（页面）——建立连接：100ms，请求/响应：130ms
  - 第 2 步（图片）——100ms，请求/响应：？

这是一道随堂测验：给定两条并行请求共享同一条链路，以及上述参数，这一对请求/响应交换需要多长时间？

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 15：测验答案——150ms，总计 250ms</span>

（本 Slide 为时序图：蓝色线段表示客户端到服务器的分段，红色线段表示服务器到客户端的分段。时间轴标注：SYN 与 SYN-ACK 在 0–100ms 之间完成；ACK 于 170ms 处；request 1（请求 1）与 request 2（请求 2）先后发出；response 1a、response 1b、response 2a、response 2b 依次排队发出；标注时刻有 50ms、100ms、150ms、160ms、220ms、230ms、250ms。）

答案：需要 150 毫秒，因此总计 250 毫秒。图中蓝色线段是客户端发往服务器的分段，红色是服务器发往客户端的分段。SYN/SYN-ACK 交换耗时 100 毫秒。第一个请求经 60 毫秒到达（50ms 传播 + 10ms 打包），此刻是 160 毫秒，服务器可以开始发送响应，它把 2 个响应分段排入队列。当第一个响应分段正从链路上发出时，服务器收到第二个请求，又把 2 个响应分段排入队列。这意味着从第一个请求到达算起，响应需要再花 90 毫秒才能全部到达。第二个请求额外的打包时延被响应的排队所掩盖（masked）。

核对：两条连接的握手在时间上完全重叠（$100$ms），两个请求的打包在客户端共享出链路（$10 + 10 = 20$ms），服务器端的 4 个响应分段必须串行打包（$4 \times 10 = 40$ms），再各自传播 50ms——请求与响应的排队相互错开，最终从握手开始到最后一响应到达为 $100 + 150 = 250$ms。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 16：Case 2 结果——480ms</span>

- 时延：50ms；请求 1 个完整分段；响应 2 个完整分段；打包时延 10ms；全双工；最大连接数 2，拆除瞬时
- Case 1：单个页面，230ms
  - SYN：50ms，SYN-ACK：50ms，ACK/请求：60ms，响应：70ms
- Case 2：加载 2 张图片的页面：480ms
  - 建立连接：100ms，请求/响应：130ms
  - 建立连接：100ms，请求/响应：150ms

汇总：Case 1 单页面 230ms；Case 2 为 230ms + 100ms（两条图片连接的握手）+ 150ms（图片的请求/响应）$= 480$ms。也就是说，加载一个只多两张图片的页面，耗时翻了一倍还多——HTTP/1.0 的每连接一个请求模型的代价由此可见。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 17：Quiz（第二组参数）</span>

给定以下参数，HTTP 1.0 加载这些页面需要多长时间？

- 时延：20ms
- 请求大小：1 个完整分段
- 响应大小：2 个完整分段，初始拥塞窗口（initial congestion window）为 10 个分段
- 分段打包时延：5ms（请求与响应）
- 最大打开连接数：2，拆除瞬时完成
- Case 1：单个页面
- Case 2：加载 5 张图片的页面

这是一道随堂测验。对 Case 2，请仔细思考请求与响应可能如何重叠。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 18：第二组测验答案——95ms 与 380ms</span>

- Case 1：单个页面，95ms（$20\text{ms} + 20\text{ms} + 25\text{ms} + 30\text{ms}$）
- Case 2：加载 5 张图片的页面，380ms（$95 + 95 + 95 + 95$ms）

Case 1 的答案是 95ms：建立连接 40 毫秒（SYN 20ms + SYN-ACK 20ms），ACK/请求 25 毫秒（打包 5ms + 传播 20ms），响应 30 毫秒（打包 $2 \times 5 = 10$ms + 传播 20ms），总计 95ms。

Case 2 的答案是 380 毫秒。加载初始页面需要 95 毫秒。随后加载图片 1 需要 95 毫秒。图片 1 完成时，图片 3 开始加载；与此同时图片 2 已在途（in flight），所以这一轮也是 95 毫秒。图片 3 完成时又过了 95 毫秒，图片 2 也已完成，图片 4 在途。最后一轮再花 95 毫秒加载图片 5。总计 380 毫秒。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 19：Case 2 时序图详解</span>

（本 Slide 为时序图：起始于 95ms，两条连接各自进行三次握手（SYN/SYN-ACK/ACK），随后 request 1（135ms 发出）、request 2（140ms 发出）相继到达服务器（图中标注 165ms），response 1a、response 1b、response 2a、response 2b、response 3a、response 3b、response 4a、response 4b 在服务器端排队串行发出；时间轴标注有 95ms、115ms、135ms、140ms、155ms、160ms、165ms、185ms、190ms、200ms、230ms、240ms、255ms 等时刻。）

用图来看看发生了什么。这幅图从第一个初始页面请求之后开始，展示客户端请求图片的过程。从 95 毫秒起步：两条连接开始三次握手，有一对 SYN/SYN-ACK 交换。40 毫秒之后，即 135 毫秒时，客户端发出请求 1；接着在 140 毫秒发出请求 2。

请求 1 在 165 毫秒到达服务器（含 20 毫秒时延与 5 毫秒打包时延的影响）。服务器开始发送响应：它刚发完响应的一个分段 1a，第二个请求就到达了，第二个请求的响应分段被排入队列，将在响应 1b 之后发出。

响应 1b 在 190 毫秒到达客户端。此时客户端开启一条新连接（通过三次握手）。注意这花了多长时间：客户端在 190 毫秒时请求第三张图片——恰好是第一个请求开始后的 95 毫秒。因为第二个请求是并行进行的，客户端不必等它完成就可以开始第三个请求；而当第三个请求完成时，会立即开始第五个请求。所以这三轮每轮只花 95 毫秒。如果请求 6 张图片，那么最后一轮将花 105 毫秒。

仔细看这幅图直到你理解为止：请求因排队而延迟发出时，会进一步延迟响应；响应因排队而延迟发出时，又会进一步延迟请求。随着时间推移，这让请求与响应自然地拉开间距，从而降低排队时延。同时，因为有多个操作并行进行，它们可以相互掩盖彼此的时延。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 20：结论——并行的价值</span>

如果你琢磨一下这些数字就会发现：并行请求多个资源并不比请求单个资源慢多少。会多出一些打包时延，但在今天的大多数网络里，打包时延只占总时间的很小一部分。单个请求无法填满网络容量，但许多请求也许可以。然而 HTTP/1.0 只允许每条连接一个请求。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这一整套时延分析的方法论值得单独复盘，因为它正是第三单元排队模型知识的直接应用：总时延被拆成传播（propagation）、打包/传输（packetization）与排队（queuing）三部分，逐事件在时间轴上累加。你在 3-4 节见过的"最后一位到达时刻 = 发送开始 + 打包 + 传播"在这里反复出现；而两条连接共享链路后，打包时延从"可忽略的串行项"变成了"必须逐段排队的服务时间"——这本质上是把链路看成一个速率为 $1/10\text{ms}$ 的单服务台队列。概率论的视角还能更进一步：Case 2 里"并行掩盖时延"的现象，本质是两条流的服务时间错峰，使服务器队列的到达间隔被自然拉开；若用泊松过程（Poisson process）刻画请求到达，排队时延的期望会随利用率 $\rho = \lambda/\mu$ 急剧上升，这正是 M/M/1 排队系统里 $W = 1/(\mu - \lambda)$ 的定性体现。把 230ms、480ms、380ms 这三个数亲手从时间轴上推出来一遍，比背十遍公式都管用。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "每条连接一个请求"最大的隐性代价其实在拥塞窗口上。注意 Slide 9 的设定：响应恰好是"2 个完整分段，即初始慢启动窗口的大小"——这个假设本身就点破了问题：HTTP/1.0 每开一条新连接，TCP 的拥塞窗口（congestion window，cwnd）都从零重新爬坡，上一条连接辛苦探测到的网络容量信息全部作废。第四单元讲过慢启动是指数增长，但如果每个数据对象只有 2 个分段大，窗口永远停在起点附近，TCP"用丢包探测瓶颈带宽"的机制根本没有施展空间。这正是下一讲 HTTP/1.1 keep-alive 的核心动机：复用连接不仅是省掉 100ms 握手，更是让 cwnd 有时间长大到能吃满带宽。现代浏览器并行开 6 条连接的做法，可以看作在这个权衡上的折中——用并行性弥补单流窗口增长不足，代价是加剧了网络内的聚合突发。讲义最后一句"单个请求填不满网络，但许多请求也许可以"就是在预告这一点。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 超文本"请求一个文档引出更多文档"的性质，是理解 Web 性能问题的第一性原理。浏览器拿到 HTML 后要解析出 IMG、CSS、JS 引用并继续请求，这使得"加载一个页面"实际是深度不确定的请求树遍历。CS144 后面的 lab 里你会实现的应用层逻辑（如 4.1 节的网页代理）恰好工作在这个往返流的正中间：代理要替客户端向服务器发起请求，再转发响应——你在 CSAPP ch11 写的 echo 服务器是"一问一答就断"，而代理必须处理"一个响应引出下一批请求"的链式行为，这正是本页 Slide 4 所述模型的工程化。另外注意 304 Not Modified 这个状态码体现的缓存协议设计：客户端用条件请求首部声明"我手上已有版本"，服务器只需回答"变没变"，就能省掉整个消息体的传输。缓存有效性协商后来成了 HTTP/1.1 与 CDN 的基石，本讲只展示了它最原始的形态。
