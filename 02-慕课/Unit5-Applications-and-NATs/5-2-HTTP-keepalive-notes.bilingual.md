### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 1：HTTP/1.1 Keep Alive</span>

本节讲 HTTP/1.1 中一项非常重要的优化——Keep Alive（保持连接）首部（header）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 2：回顾 HTTP/1.0</span>

- 打开连接（open connection）
- 发出 GET（issue GET）
- 服务器在响应后关闭连接（server closes connection after response）

HTTP 是一个基本的请求/响应协议。HTTP/1.0 非常简单：想请求一个文档的客户端打开一条连接，发送一个 GET 请求；服务器以状态码（如 `200 OK`）和文档作为响应，并在响应完成后关闭连接。客户端若想请求第二个文档，必须再打开一条连接。

当 Web 还主要是文本、顶多带一两张图片时，这种做法完全够用。人们手写网页，手工嵌入所有格式。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：回顾 HTTP/1.0 的速度分析</span>

- 时延：50ms
- 请求大小：1 个完整分段；响应大小：2 个完整分段（慢启动窗口大小）
- 分段打包时延：10ms（请求与响应），全双工
- 最大打开连接数：4
- Case 1：单个页面，230ms
  - SYN：50ms，SYN-ACK：50ms，ACK/请求：60ms，响应：70ms
- Case 2：加载 2 张图片的页面：480ms
  - 建立连接：100ms，请求/响应：130ms
  - 建立连接：100ms，请求/响应：150ms

回顾前面分析 HTTP/1.0 的结果：加载单个页面需要 230 毫秒，而加载一个带两张图片的页面耗时是它的两倍还多。大量时间花在了打开连接上——如果能一次请求更多文档，本可以快得多。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 4：HTTP/1.0 的问题</span>

- 打开连接
- 发出 GET
- 服务器在响应后关闭连接
- **打开很多连接很慢**
- **许多传输都很小，TCP 窗口没有机会增长**

所以 HTTP/1.0 的做法可能非常浪费：客户端把大量时间花在打开连接上。此外，TCP 拥塞控制窗口没有机会增长，因为每条连接的窗口都是全新的。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 5：HTTP/1.1 的新首部</span>

- 为请求新增 Connection 首部
  - `keep-alive`：告诉服务器"请保持这条连接打开，我还会请求更多内容"
  - `close`：告诉服务器关闭连接
  - 服务器随时可以忽略
- 为响应新增 Connection 首部
  - `keep-alive`：告诉客户端连接将保持打开
  - `close`：告诉客户端连接即将关闭
- 为响应新增 Keep-Alive 首部
  - 告诉客户端连接可以保持打开多久

HTTP 通过给请求和响应增加几个首部来解决这个问题。请求可以包含一个 Connection（连接）首部，告诉服务器：客户端希望这条连接在响应之后保持打开还是关闭。服务器可以自行决定，但客户端可以给出提示。例如，如果请求的是一个基本文本文件，就没有理由保持连接打开——文本文件不会引用其他待加载的资源。

响应中包含一个 Connection 首部，告诉客户端服务器最终的决定。如果服务器决定保持连接（keep-alive），那么 Keep-Alive 首部会告诉客户端连接可以保持多久。此后，客户端就可以在同一条连接上继续发送请求；它当然也可以按需打开更多连接，但不再必须这么做。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 注意这套设计的分寸感：Connection 首部只是**提示（hint）**而非命令——"The server can always ignore"（服务器随时可以忽略）。这是协议设计中典型的最小承诺原则：客户端表达偏好，服务器保留决定权，双方各自向后兼容。对比 CSAPP ch11 里你写的 echo 服务器：那里连接生命周期由"客户端关写端（`shutdown(SHUT_WR)`）、服务器读到 EOF"决定，是隐式的；HTTP/1.1 把它变成显式的带内信令（in-band signaling），用首部字段协商连接策略。Keep-Alive 首部携带超时时间的设计也很务实：服务器不能为每个客户端永久保留套接字（socket，套接字），文件描述符是有限资源，所以必须声明"我会为你保持 N 秒"。从 CSAPP 的视角看，这相当于服务器进程对每个已连接描述符设定了回收策略，避免太多并发连接耗尽描述符表。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 6：HTTP/1.1 速度——数量级对比</span>

- 时延：50ms
- 请求大小：1 个完整分段；响应大小：2 个完整分段（慢启动窗口为 30 个分段）
- 分段打包时延：1ms（请求与响应）
- 最大打开连接数：2
- 页面需要加载 11 张图片

- HTTP/1.0 速度：1,421ms
  - 页面：建立连接 100ms，请求/响应 103ms
  - 11 张图片：6 轮 ×（每轮建立连接 100ms + 请求/响应 103ms）
- HTTP/1.1 速度：326ms
  - 连接建立：100ms
  - 页面请求/响应：103ms
  - 图片请求/响应：123ms

事实证明这是一个巨大的改进。来看一个比之前更贴近实际的情形：打包时延只有 1 毫秒，页面需要加载 11 张图片。今天的浏览器通常打开多于 2 条连接，但同时加载的资源也多于 11 个——为了简单起见，我们保持这些数字较小。分析方法与 HTTP/1.0 那一节完全相同。慢启动窗口足够大，因此永远不会触发拥塞控制。

对 HTTP/1.0 来说，这需要 1,421 毫秒。一共七轮：第一轮请求页面，耗时 203 毫秒（100ms 握手 + 103ms 请求/响应）；接下来 6 轮每轮请求 2 张图片（最后一轮只有 1 张），每轮各花 203 毫秒。总计 203 + 1218 = 1.421 秒。

对 HTTP/1.1 来说，只需要 326 毫秒！建立连接花 100 毫秒，请求页面再花 103 毫秒。而请求 11 张图片只花 123 毫秒——其中第一个请求 51 毫秒（$50 + 1$ms），11 个响应 72 毫秒（50 毫秒传播时延 + 22 毫秒打包时延，$11 \times 1\text{ms} \times 2 = 22$ms）。几乎快了四倍，因为这些请求可以在同一条连接上背靠背（back-to-back）发出，不必再打开新连接。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 数字值得核一遍：HTTP/1.0 侧 $7 \times 203 = 1421$ms（页面 1 轮 + 图片 6 轮，$100 + 103 = 203$ms/轮）；HTTP/1.1 侧 $100 + 103 + 123 = 326$ms。两个深层的性能来源要分清：其一，握手从 7 次降到 1 次，省下 $6 \times 100 = 600$ms；其二，更隐蔽的是窗口增长——本例慢启动窗口是 30 个分段，11 个响应（22 个分段）本可以在窗口内一次发出，但 HTTP/1.0 的每轮新连接把窗口永远摁在初始值。第三单元的利特尔法则（Little's law）在这里也适用：吞吐量 = 在途字节数 / 往返时延，HTTP/1.1 把"在途上限"从"单窗口 × 单请求"解放成"窗口 × 整个页面的请求队列"，分子变大、分母不变，吞吐量自然上升。还要注意一个假设细节："慢启动窗口足够大，因此永远不会触发拥塞控制"——这把分析简化成了纯时延问题，排除了拥塞窗口演化；一旦资源数量超出窗口，队列行为就会像上一讲 Case 2 那样需要逐步画时间轴。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 7：SPDY</span>

- Google 提出的加速 Web 的协议
- 请求流水线（request pipelining）
- 去除冗余首部
- 正在成为 HTTP/2.0 的基础

HTTP/1.1 已经存在了一段时间，大约从 1996 年起。最近，Google 开发了一个改进 HTTP 的新协议，叫做 SPDY（读作"speedy"）。它支持诸如请求流水线（request pipelining）之类的特性。HTTP 有时会遇到这样的问题：客户端请求资源的顺序与服务器响应的顺序相同。如果某些资源需要大量处理，这就会成为问题。设想你通过 Ruby on Rails 或 Django 之类的框架动态生成网页：数据库过载，生成页面需要一段时间；但大多数资源只是可以快速发出的图片。如果客户端先请求了慢页面，那么在收到页面之前，它收不到任何图片。如果服务器能以不同的顺序响应——比如在页面还在生成时就开始发送图片——那会好得多。

SPDY 还去除了冗余首部。打开 Wireshark 看看一些 HTTP 请求和响应：每条请求和响应里经常有大量冗余信息。如果能在会话期间只设置一次某些参数（如浏览器类型），而不是每次都发送，就能加快速度。

SPDY 已投入使用一段时间，并且正在成为 HTTP/2.0 的基础。几年之内，我估计大多数站点都会因为 HTTP/2.0 带来的速度收益而采用它，尤其是在移动设备上。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这段 2019 年课程里的"预言"如今完全可以验收了：HTTP/2 于 2015 年基于 SPDY 标准化，HTTP/3 又把传输层换成了基于 UDP 的 QUIC。但页面上埋着一个有趣的历史转折——SPDY 设想的"请求流水线"（在同一条连接上连续发请求、不等响应）在 HTTP/2 里其实被多路复用（multiplexing，多路复用）取代了，原因正是流水线有个致命缺陷：HTTP/1.1 的响应必须按请求顺序返回（队头阻塞，head-of-line blocking），第一个慢响应会卡住后面所有响应。讲义里"动态页面比图片慢"的例子就是队头阻塞的活教材。去除冗余首部的思想则在 HTTP/2 中落地为 HPACK 首部压缩。另外，"浏览器类型不必每次发送"这类观察，本质上是把跨请求不变量提取到会话层——这个模式你在 CSAPP 里也见过：与其在每个函数参数里重复传同一个值，不如放进一个结构体传指针。协议设计与应用程序设计，在这里惊人地同构。
