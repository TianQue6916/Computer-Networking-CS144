## <span style="color:#2471a3;">**[lecture]**</span> <span style="color:#c0392b;">1-3 The IP Service Model（IP 服务模型）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">聚焦网络层：IP 服务模型概览</span>

学完互联网四层模型后，我们来聚焦 network layer（网络层）。这是互联网最重要的层——对许多人来说，网络层*就是*互联网。每当我们使用互联网，都必须使用 Internet Protocol（互联网协议，IP）来收发 packet（分组）。

你会记得我们说过：每一层都向其上一层提供一种 service（服务）。要正确使用一层，就需要准确理解它提供的服务是什么。因此，在这段视频里我将完整走一遍 Internet Protocol 提供的服务。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">封装关系：Segment → Datagram → Link frame</span>

IP datagram（数据报）由 header（首部）和一些数据组成。当 transport layer（传输层）有数据要发送时，它把一个 Transport Segment（传输层报文段）交给下面的网络层；网络层把这个传输层报文段装进一个新的 IP datagram 里。IP 的职责是把 datagram 送到另一端。但首先，IP datagram 得先穿过第一条链路、到达第一台 router（路由器）：IP 把 datagram 交给链路层，链路层把它装进一个 Link frame（链路帧，例如一个 Ethernet packet）里，送往第一台路由器。（原图逐层演示了这段嵌套/封装过程。）

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">IP 服务的四大性质</span>

IP 服务可以概括为四个性质：它在 end host（终端主机）之间发送 datagram；它是不可靠（unreliable）的，但会尽力而为（best-effort）地投递；网络不维护与这些 datagram 相关的 per-flow state（按流状态）。我们逐条来看。

**其一：IP 是一个 datagram service（数据报服务）。** 当我们请 IP 替我们发送数据时，它会创建一个 datagram 并把数据装进去。datagram 是一个依据其 header（首部）中的信息被逐个独立路由穿过网络的 packet——换句话说，**<span style="color:#00838f;">datagram 是自包含（self-contained）的。</span>** 首部里装有目的地的 IP 地址（这里缩写为 IP DA，IP destination address）。每台路由器上的转发决策都基于 IP DA。首部还含有 IP 源地址（IP SA，IP source address），说明包从哪里来，这样接收方才知道该把回应发到哪里。datagram 在网络中从一台路由器到下一台路由器、逐跳（hop-by-hop）地被路由，从 IP 源地址一路走到 IP 目的地址。路由器如何工作我们后面再学，现在只需知道：每台路由器里都有一张 forwarding table（转发表），告诉它与给定目的地址匹配的 packet 该发往哪里。路由器并不知道完整路径——它只是用目的地址去查转发表，把 packet 沿着通往最终目的地的路径转发到下一跳（next hop）。就这样一跳接一跳、一步一步，packet 只凭 datagram 里的目的地址走完从源到目的地的全程。

你常会听到"IP datagram 的路由就像邮政系统投递信件"这个类比。这是个好类比。在邮政系统里，我们把一封写好目的地地址的信投进邮筒，信就被（在我们看不见的地方）从一个分拣局到另一个分拣局地逐站投递，直到抵达收件地。寄件人和收件人都不——也不需要——知道信件在邮政系统或 datagram 在互联网中所走的路径。IP 服务模型提供的服务包含"把数据路由到目的地"这件事本身。

**其二（可能出人意料）：IP 是不可靠的（unreliable）。** IP 不承诺 packet 一定会被送到目的地：它们可能迟到、乱序，或者永远到不了。packet 甚至可能在途中被复制一份——比如被一台行为异常的路由器复制。要记住的关键点是：**<span style="color:#00838f;">IP 不可靠、不作任何保证。</span>**

**其三：但它不会无缘无故地任意丢弃 datagram**——前提是你相信网络有"心情"这回事。IP 确实承诺：只在必要时才丢弃 datagram。例如，路由器中的 packet 队列可能因为 congestion（拥塞）被塞满，迫使路由器丢掉下一个到达的 packet。IP 不会尝试重发数据——事实上 IP 连"包被丢弃了"都不告诉源端。类似地，一个出错的转发表可能把 packet 送错目的地，或者错误地复制一份。IP 不承诺这些错误不会发生，也不在它们发生时进行检测。但 IP 确实承诺：只在必要时才犯这些错。

事实上，IP 的 datagram 服务非常像基础邮政服务：普通邮政不承诺信件准时送达，不承诺你连续几天寄出的两三封信按寄出顺序到达，甚至根本不承诺一定送达（除非你为更贵的端到端保送服务付钱）。

说到底，IP 是一种极其简单、极小化的服务。它完全不维护与某次通信相关的任何状态。**<span style="color:#00838f;">我们说一种通信服务是 connectionless（无连接的），因为它不先建立与该通信相关联的端到端状态。</span>** 换句话说，当你进行一个持续几分钟、由许多 IP datagram 组成的 Skype 通话时，IP 层对这次通话一无所知，只是把每个 datagram 各自独立地路由，彼此互不相干。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 🎥 *McKeown 在视频中解释： "它提供了一种尽力而为的交付服务，没有保证"*（字幕来源：003 - p2 1-2 The four layer Internet model.zh.srt）。best-effort（尽力而为）这个词组要当成一个技术术语而不是敷衍话来记，它精确的含义是两条承诺的合取：① 不保证投递（unreliable）——丢、乱序、迟到、重复都可能发生；② 但丢弃只发生在"必要时"（如拥塞导致缓冲区满），而不是任意丢弃。你可以用概率论的语言把它形式化：IP 对单个 packet 的投递既不是确定性事件也不是条件于"发送成功"的必然事件，而是一个成功概率 $p < 1$ 的伯努利试验；TCP 的重传机制本质上是把这个单次成功率提升到 $1-(1-p)^n$（$n$ 为重传次数上限）的复合试验。为什么 $p<1$ 也能构建全球基础设施？因为大数定律保证了宏观上的稳定：大量独立的丢包事件在统计上可预测、可被端系统的重传机制补偿。注意 ①② 的分工暗藏一个深刻的设计判断：网络保证"不任意使坏"（可信），但不保证"必然成功"（不可靠）——把"可靠"这个价值更高、也更应用相关的属性留给端点去做。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">为什么 IP 服务被设计得这么简单？四条理由</span>

你可能在想：IP 服务为什么要做得如此简单？毕竟它是整个互联网的地基——互联网上的每一次通信都（必须）使用 IP 服务。鉴于互联网如此重要，把 IP 做成可靠的岂不更好？毕竟我们说过，大多数应用想要的正是可靠的字节流通信服务。

IP 服务模型被设计得如此简单，有以下几个理由。

**1. 让网络保持简单、愚蠢（dumb）且极小化。** 更快、更精简，建设和维护成本更低。当时的信念是：如果网络保持简单、特性和要求很少，packet 就能以极低成本非常快地被投递。其思路是：一个简单的网络可以用专用硬件跑得非常快；而且网络由散布各处的大量路由器实现，若能保持简单，它们就更可靠、维护起来更便宜、升级频率也更低。

**2. 端到端原则（end-to-end principle）：凡可能，就把功能实现在端主机上。** 在通信系统设计中，有一条著名的原则叫 end-to-end principle（端到端原则）：如果一项功能*能够*正确地实现在端点上，那就应该实现在那里。后面的视频会更深入地研究它，其基本思想是把尽可能多的智能（intelligence）放在端点——在我们这里就是源和目的计算机。这样做有多个好处：比如确保该功能是针对应用正确实现的；而且，功能若实现在端计算机的软件里，比"焊死"在互联网的硬件里更容易演化和改进。就互联网而言，人们决定：可靠通信、拥塞控制（congestion control）这类功能应当由源和目的计算机在端点完成，而不是由网络完成。在当时这是相当激进的主张，与电话系统截然不同——后者最初建立在"终端（话机）极简、网络（电话交换机）复杂而功能丰富"的理念之上。后面的视频我们会把端到端原则作为通信系统的重要体系结构原则来研究，并看到许多它的实际例子。例如，学习传输层时我们会看到：端主机如何在不可靠的 IP 网络服务之上构建出可靠的通信服务。

**3. 允许在其上构建多种可靠（或不可靠）服务。** 如果 IP 是可靠的——也就是说丢失的 packet 会被自动重传——那它对某些服务反而不理想。例如实时应用（如视频聊天）中，重传丢失的数据可能毫无意义，因为等它到了也早已过期没用；应用更愿意显示几个空白像素，或沿用上一帧的像素。通过不提供任何可靠性保证，IP 让应用自己选择所需的可靠性服务。

**4. 能运行在任何链路层之上。** IP 对链路层的假设非常少、期望非常低：链路可以是有线的或无线的，IP 不要求链路做重传或拥塞控制。有人说过，IP 简单到对底层链路几乎无所求，你甚至可以用信鸽（carrier pigeons）跑 IP。事实上还真有一份互联网标准告诉你怎么做！（这是真的：1990 年 4 月 1 日发布的 RFC 1149《IP over Avian Carriers》。）让 IP 能跑在任何链路层上是明智的，因为互联网的诞生目的就是互联现存的网络——这也正是它被叫做 "Inter-net"（网络的网络）的原因。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这四条理由里，第 2 条 end-to-end principle（端到端原则）是理解整个互联网架构的钥匙，值得把它与电话系统的对照讲透。电话网络（1960-70 年代的 AT&T 体系）的设计是"笨终端 + 聪明网络"：话机只是个换能器，所有智能（建立电路、计费、回声消除）都埋在运营商的交换机里；互联网把这个金字塔倒过来——network dumb、endpoints smart。你可以在 CSAPP 里找到同构的取舍：CPU 硬件只提供最朴素的指令与虚拟内存机制，复杂的缓冲、缓存、连接管理全部放在软件层，正因如此 Linux 才能不断演进而 x86 指令集几十年保持兼容。第 3 条则与 6.042J 里"充分条件不必多给"的思想相通：一个只提供"最少公共承诺"的下层，才能让上层自由组合出多样的语义——可靠的 TCP、不可靠的 UDP、实时的 RTP 都共享同一个最小地基。这种"最小内核 + 可组合上层"的架构模式，你在 Unix 设计哲学（do one thing well）里已经见过一次了，这里是它在网络上的再现。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">IP 额外精心挑选的服务：五项功能</span>

除了基本的"不可靠、尽力而为、无连接的 datagram 服务"，IP 还提供了几项经过精心挑选的其他服务。IP 的设计者们非常努力地寻找平衡：既只提供让通信能工作的最低限度，又不至于简陋到根本没法用。

这里我描述五项功能；每项你都会在后面的视频里学到，所以这里不深入细节，只做简要说明，让你了解完整 IP 服务的范围。

**其一：IP 试图阻止 packet 永远循环（looping forever）。** 由于 IP 路由器把 packet 逐跳转发跨越互联网，路由器的转发表可能出错，导致 packet 开始沿着同一路径一圈圈打转。这最可能发生在转发表正在变化、暂时处于不一致状态的时候。与其试图彻底防止循环——那需要大量复杂性——IP 用一个极简单的机制来捕获并删除那些看似卡在循环里的 packet：在每个 datagram 的首部加一个 hop-count（跳数计）字段，叫做 TTL（time to live，生存时间）字段。它从一个数字（如 128）开始，每经过一台路由器就减 1；一旦减到 0，IP 就断定它一定陷入了循环，路由器便丢弃该 datagram。这是一个典型的 IP 式简单机制：它不保证循环不会发生，只是试图限制"无尽循环的 packet 洪流"给网络造成的破坏。

**其二：packet 太长时 IP 会进行分片（fragmentation）。** IP 被设计成能跑在任何链路上，而多数链路对可承载的 packet 大小有上限。例如 Ethernet 只能承载不超过 1500 字节的 packet。如果应用要发送超过 1500 字节的数据，就必须先切成 1500 字节的块再装进 IP datagram 发送。而在通往目的地的路上，一个 1500 字节的 datagram 可能需要经过一条只能承载更小包（如 1000 字节）的链路；连接这两条链路的路由器会把 datagram fragment（分片）成两个更小的 datagram。IP 提供了若干首部字段（马上会看到）来帮助路由器把 datagram 分成两个自包含的 IP datagram，同时提供端主机正确 reassemble（重组）数据所需的信息。

**其三：IP 使用 header checksum（首部校验和）来降低把 datagram 送错目的地的概率。** IP 在 datagram 首部包含一个校验和字段，以尽量确保 datagram 被送到正确的位置。如果 packet 因沿途某台路由器的错误而频繁地、意外地被送到错误地点，那会是个不小的安全问题。

**其四：当今在用的 IP 有两个版本。** IPv4——今天超过 90% 的终端主机在用，采用你熟悉的 32 位地址；由于 IPv4 地址即将耗尽，互联网正在逐步过渡到使用 128 位地址的 IPv6。IPv4 与 IPv6 的细节你会在后面的视频里学到。

**其五：IP 允许向 datagram 首部添加新字段。** 这是一把双刃剑：一方面，它允许把事后被证明重要、但不在最初标准里的新特性加进首部；另一方面，这些字段需要处理，因而要求沿途路由器具备额外功能，破坏了"简单、愚蠢、极小化转发路径"的目标。实践中，很少很少有 options（选项）字段被路由器使用或处理。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">IPv4 首部逐字段导览</span>

下面我给你看 IPv4 的 header，并解释每个字段的作用。我不需要你记住每个字段在哪里（我自己也记不全它们的位置），但我要你知道每个字段做什么——因为这能帮你理解 IP 服务模型的完整范围，把理解钉牢，让你真切体会到：**<span style="color:#00838f;">IP 做的事不多——它是一个刻意简单的服务。</span>**

这是 IPv4 header 的示意图（当今使用最广泛的首部）。我按 32 位（32 bit word）为单位画出它，"Bit 0" 最先被发送到线路上。阴影部分是 IPv4 header，其后跟的是数据。

IP header 中最重要的字段有：

1. <span style="color:#00838f;">**Destination IP address（目的 IP 地址）**</span>
2. <span style="color:#00838f;">**Source IP address（源 IP 地址）**</span>
3. <span style="color:#00838f;">**Protocol ID（协议标识）**</span>：告诉我们 data 字段里装的是什么。本质上，它让目的端主机能够 demultiplex（分用）到达的 packet，把它们交给正确的代码去处理。若 Protocol ID 的值是 "6"，就说明数据里是一个 TCP Segment，于是可以放心把 datagram 交给 TCP 代码，它能正确解析该 segment。Internet Assigned Numbers Authority（互联网号码分配局，IANA）定义了超过 140 个不同的 Protocol ID 值，代表不同的传输层协议。

- **Version（版本）**：告诉我们这是哪个版本的 IP——当前合法取值是 IPv4 与 IPv6。这里画的是 IPv4 header；IPv6 header 会在后面的视频里看到。
- **Total packet length（总长度）**：最长可达 64 KB，含首部与全部数据。
- **Time to Live（生存时间，TTL）**：帮助防止 packet 在网络中意外地永久循环。每台路由器都被要求把 TTL 字段减 1；减到 0 时路由器应丢弃该 packet。这样，当源端以固定 TTL 值发包后，一旦 packet 开始绕圈，就保证会被某台路由器销毁。
- **Packet ID、Flags、Fragment Offset**：当 packet 相对于即将发送的链路太长时，这三个字段帮助路由器按需把 IP packet fragment（分片）成更小的自包含 packet。分片机制后面的视频会讲。
- **Type of Service（服务类型）**：给路由器一个关于"这个 packet 有多重要"的提示。
- **Header Length（首部长度）**：告诉我们首部有多大——有些首部带有可选的额外字段来携带额外信息。
- **Checksum（校验和）**：对整个首部计算校验和，这样即使首部损坏，我们也不太会误把 packet 送到错误的目的地。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">总结与延伸阅读</span>

总结一下，IP 非常重要：我们在互联网上每一次收发 packet 都要用它。IP 提供的是一个刻意简单的服务——一个简单、愚蠢、极小化的服务，有四个主要特征：它跨互联网逐跳发送 datagram；服务不可靠且尽力而为（unreliable and best-effort）；没有 per-flow state（按流状态），因而协议是无连接（connectionless）的。

到这里，你应该能从容回答：IP 协议是什么、它的服务模型是什么、它如何嵌入互联网四层结构。如果你还有疑虑，建议重看本段视频和前面讲四层模型的那段。

你还会找到许多关于 IPv4 如何工作的好参考资料。任何一本好的网络教科书都会花相当篇幅解释 IP 是什么、为何如此设计。例如 Kurose 与 Ross 的《Computer Networking: A Top-Down Approach》第 6 版第 4 章；Wikipedia 上也有简要解释。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> TTL 字段是"用最小机制兜住最坏情况"的范本，值得用你学过的图论来重新审视。路由决策依赖分布式计算的转发表，而在转发表收敛之前，不同路由器的表项可能互相矛盾——用 6.042J 的语言说，此时"下一跳"函数不再指向无环的生成树，packet 沿转发函数前进就可能进入有向圈（directed cycle），永远到不了终点。要想让全网转发永远无环，需要全局一致性协议，代价极高；IP 的替代方案是承认"圈会发生"，给每个包一个最多 $N$ 跳的"生命预算"（TTL 从 64 或 128 递减到 0 就销毁），把最坏情况从"无限循环消耗带宽"压缩到"每包最多 $N$ 份拷贝的流量"。这是典型的兜底（fail-safe）设计：不防止错误发生，只限制错误的爆炸半径。同样思路也出现在你写 CSAPP 并发程序时的经验里——给 `read`/`write` 设置超时和重试上限，正是在应用层实现自己的 TTL。另外记住讲义那句关键提醒：IP 甚至不通知源端"包丢了"，所以"发现丢失"这件事完全由端系统的 TCP 凭超时（timeout）与重复确认来完成——这又一次印证了端到端原则。
