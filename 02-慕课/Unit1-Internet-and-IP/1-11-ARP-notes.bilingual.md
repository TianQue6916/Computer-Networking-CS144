# CS144: Introduction to Computer Networking（计算机网络导论，Stanford Fall 2019）

## <span style="color:#c0392b;">Address Resolution Protocol (ARP)（地址解析协议）</span>

### <span style="color:#c0392b;">Slide 1 · Address Resolution Protocol (ARP)（地址解析协议）</span>

<span style="color:#2471a3;">**[section]**</span>

<span style="color:#00838f;">**地址解析协议（Address Resolution Protocol, ARP）是网络层用来发现"与它直接相连的网络地址所对应的链路地址"的机制。**</span>换句话说，它回答的是每个设备都会问的这个问题："我手里有一个 IP 分组，它的下一跳（next hop）是这个地址——我该把它发给哪个链路地址？"

### <span style="color:#c0392b;">Slide 2 · Layers of Addresses（地址的分层）</span>

<span style="color:#2471a3;">**[section]**</span>

图示：七层 OSI 模型层叠图，旁边标注一台主机的两套身份——主机（Host）：171.67.76.65（IP 地址）；接口（Interface）：00:13:72:4c:d9:6a（以太网地址）。

需要 ARP，是因为每个协议层都有自己的一套名字和地址。IP 地址是网络层的地址，它描述一台**主机（host）**——网络层的一个唯一目的地。而链路地址（link address）描述的是一块特定的网卡（network card）——一个收发链路层帧（frame）的唯一设备。例如以太网（Ethernet）有 48 位地址；你买到的每一张以太网卡，出厂时就预配了一个唯一的以太网地址。所以 IP 地址说的是"这台主机"，而以太网地址说的是"这块以太网卡"。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 🎥 *McKeown/Levis 在视频中解释: "ARP 是必要的，因为每个协议层都有其自己的名称和地址。"*（字幕来源：020 - p19 1-11 Address Resolution Protocol (ARP).zh.srt）为什么要有两套地址？这是分层原则的必然推论：IP 层的承诺是"运行在**任意**链路层之上"——以太网、WiFi、点对点串行线、光纤……如果网络层地址直接复用以太网地址，IP 就被永久绑死在以太网上，"把许多不同网络缝合在一起"的初衷（见 IPv4 一讲）立刻破产。所以每一层保留自己的命名空间，层与层之间只靠"解析"这类粘合协议相连——ARP 正是这种粘合剂。你在 CSAPP ch11 写 socket 程序时从未见过 MAC 地址，正是因为操作系统把这套解析完全藏在了内核：你 `send()` 到一个 IP 地址，内核先查路由表确定下一跳（最长前缀匹配），再查 ARP 缓存把下一跳 IP 翻译成链路地址，最后才交给网卡发帧——两次"翻译"层层接力，应用层毫无感知。另外注意 48 位以太网地址通常烧死在网卡里（出厂即唯一），而 IP 地址是网络接入时动态赋予的：一个是"设备的身份证"，一个是"设备的门牌号"，两者生命周期也完全不同。

### <span style="color:#c0392b;">Slide 3 · Addressing Problem（寻址问题）</span>

<span style="color:#2471a3;">**[section]**</span>

图示：一个假想拓扑——节点 A（IP 192.168.0.5，以太网地址 00:13:72:4c:d9:6a）与网关（gateway）相连；网关有两块网卡（以太网地址分别为 0:18:e7:f3:ce:1a 与 0:18:e7:f3:ce:1b），另一侧连接节点 B（IP 171.43.22.5，以太网地址 9:9:9:9:9:9）。图中网关只标了一个 IP：192.168.0.1。

48 位以太网地址通常写成用冒号分隔的 6 个十六进制八位组（octet），例如源地址的 0:13:72:4c:d9:6a，或目的地址的 9:9:9:9:9:9。

有一点容易混淆：虽然链路层地址与网络层地址在协议层面完全解耦（decoupled），但在分配与管理层面它们可能并不解耦。例如，一台主机拥有多个 IP 地址非常常见——每个接口（interface）一个。这是子网掩码（netmask）概念所要求的。看这个假想的配置：中间的网关只有一个 IP 地址 192.168.0.1，却有两块网卡，一块连着目的节点 171.43.22.5，一块连着源节点 192.168.0.5。

地址 192.168.0.1 实际上只能属于这两个网络之一——源节点所在的网络。要让 192.168.0.1 与 171.43.22.5 同网，所需的掩码是 128.0.0.0——只有 1 位的掩码！但"首比特为 1 的所有 IP 地址都与 171.43.22.5 同网"显然不行——比如 192.168.0.5 就必须经过网关才能到达 171.43.22.5。

### <span style="color:#c0392b;">Slide 4 · Example Addressing（寻址示例：修正后的配置）</span>

<span style="color:#2471a3;">**[section]**</span>

图示：修正后的拓扑——网关的左接口标 IP 192.168.0.1，右接口标 IP 171.43.22.8；节点 A（192.168.0.5，00:13:72:4c:d9:6a）接左接口，节点 B（171.43.22.5，9:9:9:9:9:9）接右接口。

所以我们更常看到的是这样的配置：网关或路由器有多个接口，每个接口有自己的链路层地址（标识网卡），也各有自己的网络层地址（标识该网卡所在网络中的主机）。对这个网关来说，左接口的 IP 是 192.168.0.1，右接口的 IP 是 171.43.22.8。

链路层地址与网络层地址"逻辑上解耦、实践中却常常相关"，某种程度上是一个历史产物。互联网诞生时有许许多多链路层，而互联网想运行在**所有**这些链路层之上；这些链路层当然不会突然改用 IP 地址来取代自己的编址方案。此外，事实证明存在大量"拥有独立的链路层地址非常有价值"的场景。例如，我把一台计算机注册进 Stanford 的网络时，登记的是它的链路层地址——也就是网卡地址。

### <span style="color:#c0392b;">Slide 5 · Encapsulation（封装：一次跨网传输的字节视角）</span>

<span style="color:#2471a3;">**[section]**</span>

图示：与前两页相同的拓扑，节点 A 侧标注：IP 192.168.0.5、子网掩码 255.255.255.0、网关 192.168.0.1。

这在实践中意味着什么？假设左边的节点 A 想给右边的节点 B 发一个分组。它会生成一个源地址为 192.168.0.5、目的地址为 171.43.22.5 的 IP 分组。

节点 A 检查目的地址是否在同一网络。子网掩码告诉它：目的地址在**不同**的网络（255.255.255.0）。这意味着节点 A 需要把分组交给网关，即 192.168.0.1。为此，它发送的分组网络层目的地址是 171.43.22.5，但链路层目的地址却是**网关**的链路层地址——于是这个分组的网络层目的地是 171.43.22.5，链路层目的地是 0:18:e7:f3:ce:1a；网络层源是 192.168.0.5，链路层源是 0:13:72:4c:d9:6a。

也就是说：一个从 A 到 B 的 IP 分组，封装在一个从 A 到网关左接口的链路层帧里。分组到达网关后，网关查找下一跳，判定是节点 B，于是把这个 IP 分组装进另一个链路层帧发给 B——第二个帧的链路层方向是从网关右接口到 B。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这一页是整个 Unit 1 的"点睛之笔"：网络层目的地址与链路层目的地址**可以指向不同的节点**。 IP 首部的 destination 字段从 A 到 B 全程不变（端到端的逻辑身份），而链路层帧的目的地址每一跳都换（逐跳的物理投递）——这正是封装原则在寻址上的体现：帧是"信封"，IP 分组是"里面的信"，每经过一个邮局就换一次信封。从 CSAPP ch11 的视角看，你在 socket 层 `sendto("171.43.22.5")` 时，内核里发生的就是上面这套判断：先按子网掩码 AND 判断同网与否（1-9 讲的技能），同网则直接解析对方 MAC，不同网则解析网关的 MAC——"发给网关"从来不是 IP 层的指令，而是链路层帧头的改写。理解了这一点，你就理解了为什么默认网关（default gateway）配置错了会"上不了网"：主机的 LPM 查出的下一跳无法解析，帧根本发不出第一跳。

### <span style="color:#c0392b;">Slide 6 · Example Problem（示例问题：ARP 要解决的）</span>

<span style="color:#2471a3;">**[section]**</span>

图示：一个典型家庭/办公网络——客户端（client）与网关（gateway，IP 192.168.0.1，以太网地址 0:18:e7:f3:ce:1a）通过交换机（switch）相连，gateway 背后是 Internet（互联网）；图中一台客户端标注：以太网地址 68:a8:6d:05:85:22、IP 地址 192.168.0.5、IP 子网掩码 0xffffff00、客户端 IP 网关 192.168.0.1；另一台客户端的 IP 为 192.168.0.4 与 192.168.0.76。

于是我们来到了 ARP 要解决的问题。我的客户端知道要把分组发给 IP 地址为 192.168.0.1 的网关；但为此，它必须有与 192.168.0.1 关联的链路层地址。它怎么得到这个地址？我们需要某种方法，把第 3 层（网络层）地址映射到对应的第 2 层（链路层）地址。我们用一个叫做 ARP（地址解析协议）的协议来做到这件事。

### <span style="color:#c0392b;">Slide 7 · Address Resolution Protocol（ARP 协议的工作方式）</span>

<span style="color:#2471a3;">**[section]**</span>

- 在第 2 层与第 3 层地址之间建立映射
  - 节点缓存（cache）这些映射，缓存条目会过期（expire）
- 简单的请求-应答（request-reply）协议
  - "谁拥有网络地址 X？"
  - "我拥有网络地址 X。"
- 请求发送到链路层**广播（broadcast）**地址
- 应答发送给请求者的地址（不是广播）
- 分组格式包含冗余数据
  - 请求里携带了足以生成映射的信息
  - 使调试简单得多
- 不"共享"状态：坏状态最终会自行消亡

ARP 是一个简单的请求-应答协议。每个节点都保存一个缓存，记录自己所在网络中"IP 地址 → 链路层地址"的映射。如果某节点要向一个没有缓存映射的 IP 地址发分组，它就发出一个请求："谁拥有网络地址 X？"拥有该网络地址的节点应答："我拥有网络地址 X。"应答里带有它的链路层地址。请求者收到应答后，就能建立映射、发送分组了。

为了让每个节点都听到请求，节点把请求发往链路层**广播地址（broadcast address）**——网络中的每个节点都会收到这个帧。

此外，ARP 的结构中含有冗余数据。请求里带有请求者的网络层和链路层地址。这样一来，其他节点听到一个请求（因为是广播）时，也可以在自己的缓存里插入或刷新这条映射。节点**只**回应发给自己的请求。这意味着——假设没有人恶意构造分组——你能为另一个节点建立映射的唯一途径，就是收到那个节点发出的分组。所以如果那个节点崩溃或断开，它的状态终将随着所有缓存映射的过期而离开网络。这使 ARP 的调试和排错容易得多。

那么这些动态发现的映射能存活多久呢？取决于设备：例如某些版本的 Mac OSX 会保留 20 分钟，而某些 Cisco 设备的超时是 4 小时。其背后的假设是：这些映射不会频繁变化。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> ARP 是学习"**软状态（soft state）**"这一互联网核心设计模式的最佳标本：映射不是被显式删除的，而是靠定时器过期"自然死亡"。讲义里"bad state will die eventually（坏状态终将消亡）"这句话值得抄下来——它把一致性问题转化成了时间问题：即使主机换网卡、IP 重分配，全网最多等一个超时周期就自动收敛，无需任何撤销协议。这背后的假设是"映射变化是罕见的"（主机几分钟内不会换网卡），于是缓存 + 过期就是概率意义上的最优策略：命中率高、失效代价小。你在其他协议里会反复看到这个模式的变体：DNS 记录带 TTL、DHCP 租约（lease）、路由协议的老化计时器——全都共享"让状态自己过期，而不是费力去清理"的哲学。从第一性原理看，这也是端到端思想在状态管理上的投影：核心网络不维护任何每流状态，状态全部下沉到边缘节点并自愈。代价当然也有：ARP 请求是全网络广播，任何人都能应答——因为 ARP 报文没有认证，恶意节点可以谎称"X 归我"（ARP 欺骗/spoofing），这也是局域网中间人攻击的经典入口；冗余字段带来的"容易调试"，对应的是攻击面上的"容易伪造"。

### <span style="color:#c0392b;">Slide 8 · ARP Packet Format (RFC826)（ARP 分组格式）</span>

<span style="color:#2471a3;">**[section]**</span>

图示：RFC 826 定义的 ARP 分组格式，按 32 位一行排布：Hardware（硬件类型）、Protocol（协议类型）、Hardware length（硬件地址长度）、Protocol length（协议地址长度）、Opcode（操作码）、Source hardware address（源硬件地址）、Source protocol address（源协议地址）、Destination hardware address（目的硬件地址）、Destination protocol address（目的协议地址）、Data（数据）。灰色字段为变长，由各长度字段决定。

这是一份真实的 ARP 分组的样子。它有 10 个字段。Hardware 字段声明这个请求或应答是针对哪种链路层的；Protocol 字段声明它针对哪种网络协议；两个长度字段分别指定链路层地址和网络层地址的字节长度；Opcode 指明该分组是请求还是应答。

四个地址字段用来承载请求的内容和映射的结果。

记住：所有这些字段都按网络序（即大端）存储。所以如果我有一个值为 15 的 opcode，它在字段里会存成 $0\text{x}000\text{f}$。

ARP 的完整细节在 IETF 征求意见稿（Request for Comments, RFC）826 中。这里只走一遍简单的请求/应答交换。

### <span style="color:#c0392b;">Slide 9 · ARP Request（ARP 请求）</span>

<span style="color:#2471a3;">**[section]**</span>

图示：与 Slide 6 相同的网络拓扑（交换机、网关 192.168.0.1 / 0:18:e7:f3:ce:1a、两台客户端、互联网；客户端信息同前）。

假设我们的客户端想把分组发往更大的互联网，要经过网关——但它还没有网关的以太网地址。

客户端会生成一个 ARP 请求分组：链路层源地址是它自己的地址 68:a8:6d:05:85:22；目的链路层地址是广播地址 ff:ff:ff:ff:ff:ff（全 1）。

ARP 请求中声明：硬件类型是以太网（值为 1），协议类型是 IP（值为 $0\text{x}0800$），硬件地址长度为 6，协议地址长度为 4。Opcode 为请求（request，值为 1）。ARP 源硬件地址字段填请求者的以太网地址 68:a8:6d:05:85:22；源协议地址字段填请求者的 IP 地址 192.168.0.5。目的硬件地址字段可以随便填——它正是这个分组要去发现的东西；目的协议地址字段填客户端想查询映射的地址：192.168.0.1。客户端把这个帧发上以太网。网络中的每个节点都会收到它，并刷新自己缓存中"链路地址 68:a8:6d:05:85:22 ↔ 网络地址 192.168.0.5"的映射——如果没有，就插入一条。

### <span style="color:#c0392b;">Slide 10 · ARP Reply（ARP 应答）</span>

<span style="color:#2471a3;">**[section]**</span>

图示：与 Slide 6 相同的网络拓扑（同前：交换机、网关 192.168.0.1 / 0:18:e7:f3:ce:1a、两台客户端、互联网）。

网关看到这个请求是发给自己的 IP 的，于是生成一个应答。

与请求一样，ARP 应答声明：硬件类型是以太网（值为 1），协议类型是 IP（值为 $0\text{x}0800$），硬件地址长度为 6，协议地址长度为 4。Opcode 为应答（reply，值为 2）。ARP 源硬件地址字段填应答者的以太网地址 0:18:e7:f3:ce:1a；源协议地址字段填答案本身：192.168.0.1。目的硬件地址字段填请求的源硬件地址 68:a8:6d:05:85:22；目的协议地址字段填请求的源协议地址 192.168.0.5。

应答到底该用什么链路层地址发出，是一个可以讨论的问题。最初的 ARP 规范要求应答者发往请求者的链路层地址，也就是单播（unicast）；但如今常见的做法是广播应答，因为这样在映射需要变化时能更激进地替换各节点的缓存条目。节点还可以发送所谓的**免费 ARP（gratuitous ARP）**——去查询一个自己明知道答案（或不存在的）映射——以此在网络中宣告自己的存在。

至此我们看到了：要路由分组，就需要把网络层地址映射到链路层地址；地址解析协议（ARP）通过一次简单的请求-应答交换提供这项服务。如果一个节点要向某个 IP 地址发送（或经由它转发）分组、却没有它的链路层地址，它就可以通过 ARP 请求这个地址。
