### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 1：封面与开场</span>

拥塞控制 III：性能改进——快速重传（fast retransmit，快速重传）与快速恢复（fast recovery，快速恢复）。

**讲稿**：本讲讨论 TCP 的两项性能改进：快速重传与快速恢复。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 2：Three Mechanisms（三个机制）</span>

- **快速重传（TCP Tahoe）**：收到三重重复确认（triple duplicate acknowledgement，三重重复确认）时，不必等超时就重传缺失的报文段；只有**超时**才退回慢启动状态；
- **快速恢复（TCP Reno）**：在三重重复确认时把拥塞窗口**减半**（而不是设为 1）；
- **快速恢复（TCP Reno）**：处于快速恢复状态期间，随确认到达而"膨胀"（inflate，膨胀）拥塞窗口，让数据持续流动：
  - 每个重复确认使拥塞窗口加 1；
  - 若旧窗口为 $c$，则新窗口为 $c/2$；
  - 收到 $c$ 个确认会把窗口增大到 $3c/2$——于是还能发送 $c/2$ 个新报文段。

**讲稿**：除了拥塞避免状态、改进的 RTT 估计与自时钟之外，TCP 还有三个机制。它们通过"软化"对丢包的反应来改善 TCP 的性能。回忆 TCP Tahoe 的机制使它表现得比 AIMD 更保守：一旦丢包，TCP Tahoe 跌回慢启动状态，指数增长窗口直到 ssthresh，然后才进入加性增。第一个机制叫快速重传，属于 TCP Tahoe：当 TCP Tahoe 发送方收到 3 个重复确认（即同一确认号出现 4 次）时，它认定下一个报文段丢了，立即重传它而不等超时。假设重传成功，这缩短了发送方等到确认、推进发送窗口、发送新数据之前的延迟。但 TCP Tahoe 把三重重复确认当作一次完整丢包处理——把拥塞窗口设为 1、跌回慢启动。TCP Reno 增加了第二个算法，快速恢复，它包含两个机制。其一：当丢包由三重重复确认发现时，TCP Reno 不把拥塞窗口设为 1、不跌回慢启动，而是**减半**拥塞窗口。由于 ssthresh 本来就被设为拥塞窗口的一半，这意味着 TCP Reno 不退出拥塞避免状态。使用这个算法，TCP Reno 在没有超时的稳态下严格遵循 AIMD 策略——丢包时减半窗口（乘性减），平时加性增；只有超时才像 Tahoe 那样把窗口设为 1。其二：处于快速恢复状态时，TCP Reno 对每个重复确认把拥塞窗口"膨胀"加 1。这是为了解决"单个丢包导致 TCP 整整一个 RTT 发不出数据"的问题——它本来在等一个确认来推进发送窗口。既然每个重复确认都意味着一个报文段已成功离开网络，TCP 理论上就可以不发一言地再发一个新段而不拥塞网络。设旧拥塞窗口为 $c$：每个重复确认加 1，窗口从 $c/2$（快速恢复）一路涨到 $c + c/2$ 即 $3c/2$；这意味着对第 $c/2$ 到第 $c$ 个确认，TCP 能发送新段（窗口已经先行扩大了）。一旦收到一个**新的**确认，TCP 把拥塞窗口重置回正确值 $c/2$。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 为什么是"3 个重复确认"才行动，而不是第 1 个？这是一个假设检验的设计，可以用概率论的两类错误来理解：单个重复确认在正常乱序（分组走了一条略慢的路径）下很常见，若听到一个就重传，会把大量分组重发两遍——第一类错误（假警报）太频繁；而连收 3 个重复确认（共 4 个相同 ack）意味着接收方已经收到了这个段**后面**的 3 个段、唯独缺口没补上——在乱序深度通常不超过 2 的路径上，这几乎只能是丢失，第二类错误（漏报）极小、且等待代价可控（3 个重复 ack 比 1 个 RTT 的超时快得多）。阈值 3 不是拍脑袋：RFC 5681 将其定稿，杜邦（Dupack） threshold 在乱序普遍的高带宽网络里还需调大。你看，一个看似随意的工程常数背后，是完整的"信号与噪声"权衡——与上一讲 $r + 4v$ 里那个 4 一样，属于"用假设检验定阈值"的同一套方法论。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：TCP Tahoe（丢包时的三步动作）</span>

- 发生超时或三重重复确认（意味着有分组丢失）时：
  - 把阈值（ssthresh）设为拥塞窗口的一半；
  - 把拥塞窗口设为 1；
  - 重传缺失的报文段（三重重复确认时即快速重传）；
  - 进入慢启动状态。

**讲稿**：把这些拼起来。TCP Tahoe 在超时或三重重复确认时做三步：第一，把 ssthresh 设为拥塞窗口的一半；第二，把拥塞窗口设为 1；第三，重传缺失的报文段。前两步意味着它进入慢启动状态，指数增长拥塞窗口，直到再次遭遇丢包或达到 ssthresh。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 4：TCP Tahoe Behavior（TCP Tahoe 行为曲线）</span>

图示：窗口大小随时间的曲线，标注 duplicate acks（重复确认点，两处）与 timeout（超时点）、ssthresh 阶梯线。

**讲稿**：这张图给出 TCP Tahoe 拥塞窗口随时间变化的一个例子。窗口从 1 个 MSS 起步、指数增长。它观测到一次三重重复确认，于是窗口回到 MSS、再次指数爬升，直到达到原值的一半——此时开始加性增长；继续增长直到某段丢失、出现三个重复确认（窗口不因重复确认而增长）；随后再次跌回 1 个 MSS，按慢启动指数增长到 ssthresh，然后又开始加性增长。仔细看，两次回到慢启动时 ssthresh 是同一个值——TCP 在同一个窗口大小处转入拥塞避免。在这个简化图里，这是因为 ssthresh 按整数个 MSS 计算、两种情况都向下取整到了同一个值。注意 TCP Tahoe 并非严格按 AIMD 管理拥塞：AIMD 是管理稳态（或稳定网络）的优秀算法，但实践中 TCP 要面对宽泛得多的条件——启动、丢失成批分组的瞬时故障、可用带宽的突变。最后回忆三个问题：何时发送新数据、何时重传、何时确认。本段回答第一个：TCP 在其发送窗口——拥塞窗口与流量控制窗口的较小值——允许时发送新数据；拥塞窗口是发送方根据观测到的确认与超时维护的值。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 5：TCP Tahoe Walkthrough（TCP Tahoe 逐包演算）</span>

图示：sender（发送方）与 receiver（接收方）之间按时间轴展开的报文段与确认序列。

**讲稿**：现在逐步推演 TCP Tahoe 遭遇三重重复确认时的行为。设拥塞窗口为 8 个 MSS，某段丢失。TCP 一共会收到 7 个重复确认。在第 3 个之后，它重传缺失段，把拥塞窗口设为 1 个 MSS、ssthresh 设为 4。收到重传段的确认后，它发送 1 个新段；收到这个段的确认后，窗口涨到 2；再收到这两个段的确认后，窗口依次涨到 3、4。达到 4 后进入拥塞避免状态，此后的每 4 个确认才把窗口推进 1 个 MSS。这就是 TCP Tahoe。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 6：TCP Reno（三重重复确认时的处理）</span>

- 超时时与 Tahoe 相同；
- 三重重复确认时：
  - 把阈值设为拥塞窗口的一半；
  - 把拥塞窗口设为拥塞窗口的一半（快速恢复）；
  - 快速恢复期间膨胀拥塞窗口（快速恢复）；
  - 重传缺失段（快速重传）；
  - **停留在拥塞避免状态**。

**讲稿**：TCP Reno 在超时时与 TCP Tahoe 完全相同。在三重重复确认时，它执行快速重传、立即发送该段；不把拥塞窗口设为 1，而是减半，从而留在拥塞避免状态。对每个重复确认，它把拥塞窗口膨胀加 1，以便在重传段被确认之前就能发送新段。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 7：TCP Reno（续）</span>

**讲稿**：所以 Reno 与 Tahoe 的主要差别就是快速恢复。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 8：TCP Reno（行为曲线）</span>

图示：窗口大小随时间的曲线——两处 duplicate acks（重复确认）与一处 timeout（超时）。

**讲稿**：这是 TCP Reno 行为的图示。它从慢启动开始，直到看到三重重复确认：窗口减半、留在拥塞避免状态，并执行快速重传；随后开始用 AIMD 增长窗口。AIMD 之前的平坦段里，它用拥塞窗口膨胀发送新段——图中未画出膨胀量。第二次三重重复确认时同样处理：快速重传、窗口减半、留在拥塞避免。超时时，它把窗口设为 1、重新进入慢启动。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 9：Congestion Window Inflation（拥塞窗口膨胀的细节）</span>

- 问题：快速重传的分组要花整整一个 RTT 才能推进拥塞窗口；
- 本可以向网络注入更多分组；
- 解决方案：拥塞窗口膨胀（congestion window inflation，拥塞窗口膨胀）：
  - 处于快速恢复状态期间（尚未收到新确认），对**每个**重复确认（包括最初的 3 个）把拥塞窗口加 1；
  - 这发生在窗口减半之后（$\text{cwnd}_{new} = \text{cwnd}_{old}/2$）；
  - 最终结果：一个 RTT 后 $\text{cwnd}_{new}$ 达到 $3\,\text{cwnd}_{old}/2$，但由于还没有新确认，实际效果是发送了 $\text{cwnd}_{old}/2$ 个新分组。

**讲稿**：拥塞窗口膨胀是快速恢复的一部分。细节如下：TCP Reno 进入快速恢复时，对每个重复确认把拥塞窗口加 1。由于窗口已被减半，这意味着窗口可以涨得比原值还大，最高到旧值的 $3/2$ 倍。这意味着发送方将发送"旧窗口的一半"个新段（减去丢失的那一段），几乎恰好是遵守 AIMD 所要求的量。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 窗口膨胀是一道严格的"守恒会计题"，值得用 6.042J 的不变量思维算一遍账：网络里刚少了 $c/2$ 个分组（窗口减半的差额），快速恢复期间每来一个重复确认就证明"又有一个旧包离开了网络"，于是补发一个新包恰好维持"在途数不变"的守恒律。数一数：从 $c/2$ 膨胀到 $3c/2$ 共需 $c$ 个重复确认（含最初 3 个），期间发送的新段数为 $c/2$——旧账清零、新账启用时（收到推进缺口的新确认），窗口回落到 $c/2$，在途数严丝合缝地等于新窗口。整个过程中"进入网络的包数 = 离开网络的包数"这个不变量从未被破坏——膨胀窗口只是**账面**先行，**实际**发送严格遵守守恒。这也是为什么"膨胀/紧缩"（inflate/deflate）这对词用得如此准确：窗口变量在账面上虚涨，发送行为一分未多。CLRS 里计数排序前先算前缀和、再按位置回填的两阶段法，与这种"先记账、后发货"的结构如出一辙。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 10：TCP Tahoe FSM（TCP Tahoe 状态机回顾）</span>

图示：两状态状态机（慢启动 ⇄ 拥塞避免）：

- 慢启动：收到 ack → $\text{cwnd} \mathrel{+}= MSS$；$\text{cwnd} > \text{ssthresh}$ → 转入拥塞避免；
- 拥塞避免：收到 ack → $\text{cwnd} \mathrel{+}= \dfrac{MSS^2}{\text{cwnd}}$；
- 超时或三重重复确认 → $\text{cwnd} = 1$，$\text{ssthresh} = \text{cwnd}/2$ → 回到慢启动。

**讲稿**：回忆这是 TCP Tahoe 的状态机，两个状态：慢启动与拥塞避免。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 11：TCP Reno FSM（TCP Reno 状态机）</span>

图示：三状态状态机（慢启动、拥塞避免、快速恢复 Fast Recovery）：

- 超时 → $\text{cwnd} = 1$，$\text{ssthresh} = \text{cwnd}/2$ → 慢启动；
- 慢启动：$\text{cwnd} > \text{ssthresh}$ → 拥塞避免；收到 ack → $\text{cwnd} \mathrel{+}= MSS$；
- 拥塞避免：收到 ack → $\text{cwnd} \mathrel{+}= \dfrac{MSS^2}{\text{cwnd}}$；
- 三重重复确认 → $\text{ssthresh} = \text{cwnd}/2$（以旧窗口计），$\text{cwnd} = \text{ssthresh} + 3$ → 进入快速恢复；
- 快速恢复：收到重复确认 → $\text{cwnd} \mathrel{+}= 1$；收到新确认 → $\text{cwnd} = \text{cwnd}_{old}/2$ → 回到拥塞避免。

**讲稿**：这是完整的 TCP Reno 状态机。它增加了第三个状态——快速恢复。收到三重重复确认时，它不转回慢启动，而是转入快速恢复。在快速恢复状态，收到一个**新的**确认就转回拥塞避免，并把拥塞窗口重置为进入快速恢复时窗口的一半。超时时它与拥塞避免一样转回慢启动。收到重复确认时，把拥塞窗口加 1。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 12：TCP Reno Walkthrough（TCP Reno 逐包演算）</span>

图示：sender（发送方）与 receiver（接收方）之间按时间轴展开的报文段与确认序列。

**讲稿**：推演 TCP Reno 的行为。设拥塞窗口为 8 个 MSS，某段被丢。发送方将收到 7 个重复确认。前 3 个之后，它把窗口缩到 4、留在拥塞避免状态；随后把窗口膨胀加 3、到 7 个 MSS。第 4 个重复确认到来时窗口涨到 8 个 MSS；接下来三个确认把它推到 9、10、11 个 MSS——于是发送方可以发送 3 个新段。大约此时，发送方收到重传段的确认，其确认号把发送窗口推进到涵盖所有触发重复确认的段。此时 TCP Reno 把拥塞窗口"紧缩"（deflate，紧缩）回正确值——旧值的一半。这允许 TCP Reno 发送 1 个新段，然后等待快速恢复期间所发各段的确认。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 13：Congestion Control（全单元总结）</span>

- 健壮网络系统中最困难的问题之一；
- 基本途径：加性增、乘性减（AIMD）；
- 让"管道"保持满、提升吞吐量的技巧：
  - 快速重传（不等超时就补发丢失的数据）；
  - 拥塞窗口膨胀（不必空等一个 RTT 才继续发数据）。

**讲稿**：拥塞控制是一个非常困难的问题。回忆一下：它不是任何人预先料到的——它是早期互联网开发者与用户观察到的一种涌现行为（emergent behavior，涌现行为），为了让互联网重新可用而不得不对付它。今天 TCP 用的基本途径是 AIMD。但"究竟如何工作"有很多细节：TCP 究竟在何时、如何发送数据、重传数据、发送确认。让 AIMD 在实践中良好而稳定地运转，需要处理一大堆边界情况。今天使用的几乎所有 TCP 变体都以 TCP Reno 为核心。为适应现代网速有一些新的扩展，但当你打开与心爱网站的连接时，你的操作系统正在使用 TCP Reno——慢启动、拥塞避免、快速重传、快速恢复，一应俱全。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "涌现行为"这四个字值得从复杂度的角度咀嚼。TCP 拥塞控制不是谁设计出来的，而是**在网络规模跨过某个阈值后涌现出来的全局现象**：成千上万个只看本地信号（自己的确认与超时）的独立 agent，叠加成一个系统级的动力学过程——这与你在概率论里"局部马尔可夫性导出全局平稳分布"、在 CLRS 里"简单贪心规则导出全局最优结构"看到的是同一类惊喜：局部简单规则 + 大量相互作用 = 复杂而有序的全局行为。而且这个涌现几乎把系统带向了崩溃（1986），是反馈回路把系统重新拉回有序——工程上这叫"从涌现中学习设计"。最后的落点也很实在：这些 1990 年前的算法至今活在你的操作系统内核里——按 CSAPP 的习惯去读 Linux 源码（`net/ipv4/tcp_*.c`），你会找到 `snd_cwnd`、`ssthresh` 这些变量，本单元的一切都在那里以 C 结构体的形式运行着。
