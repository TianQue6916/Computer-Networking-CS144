### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 1：封面与开场</span>

TCP 拥塞控制 II：RTT 估计（RTT estimation，RTT 估计）、自时钟（self-clocking，自时钟）。

**讲稿**：回忆 TCP Tahoe 用三项重大改进解决了互联网遭遇的拥塞崩溃问题。上一讲讲了它如何引入拥塞窗口及慢启动、拥塞避免两个运行状态；本讲解释另外两项机制——RTT 估计与自时钟。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 2：Three Questions（三个问题）</span>

- 什么时候发送新数据？
- 什么时候发送重传数据？
- 什么时候发送确认？

**讲稿**：回忆 TCP 的实现可以归结为三个问题。第一个：何时发送新数据——TCP 的答案是用拥塞窗口在网络拥塞时限制发送。接下来回答第二个：TCP 何时重传数据？

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：Three Improvements（三项改进）</span>

- 拥塞窗口；超时估计；自时钟。

**讲稿**：事实证明，把重传超时（retransmission timeout，重传超时）估计好，对 TCP 的行为影响巨大。超时选得太长，TCP 会停在原地等确认；选得太短，TCP 又会退避得过猛、掉进慢启动状态。所以 TCP Tahoe 对超时估计做了改进。这些改进后来被证明是网络系统中估计噪声信号的好方法，学会它们对设计其他协议也有指导意义。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 4：Timeouts（超时：为什么难）</span>

- 往返时延估计对超时至关重要：
  - 太短：重传浪费容量，还会触发慢启动；
  - 太长：空闲时间浪费容量；
- 难点：RTT 高度动态；RTT 随负载显著变化。

**讲稿**：由于 TCP 会在超时时转入慢启动并重传，好的超时值至关重要。如果往返时延是常数，最优重传超时只比 RTT 大一点点即可——成功送达的分组的确认会在发送后一个 RTT 到来。但往返时延不是常数：它高度动态，且随负载显著变化——一条流发得越快，就可能开始填满沿途队列，把 RTT 推高；来自其他源的流量突发也会改变排队时延（queuing delay，排队时延）。面对所有这些噪声，我们需要一个稳健的方法来估计"等多久才认定分组已丢失"。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 5：Pre-Tahoe Timeouts（Tahoe 之前的超时估计）</span>

- $r$ 为 RTT 估计值，初始化为某个合理值；
- $m$ 为最近被确认的数据分组的 RTT 测量值；
- 指数加权移动平均（exponentially weighted moving average，EWMA）：<span style="color:#00838f;">$r \leftarrow \alpha r + (1-\alpha) m$</span>（源文本的希腊字母 $\alpha$ 在 PDF 提取中丢失）；
- 超时 $= \beta r$，取 $\beta = 2$；
- **问题出在哪？**

**讲稿**：Tahoe 之前，TCP 只跟踪一个变量 $r$——它的 RTT 估计。每收到一个新确认，就从"报文段发出到确认到达"的时间差算出一个 RTT 测量值 $m$，$r$ 是这些测量值的指数加权移动平均。若一个报文段在 $2r$ 之后仍无确认，TCP 就认定它丢了，触发重传。那么这种方法的问题是什么？根本问题在于：它假设 RTT 测量值的**方差**是其数值的一个固定比例。想象一条时延高但方差低的路径——比如一条闲置的跨洋海底链路：即使 RTT 是 80 ms、99.99% 的 RTT 都落在 80 与 81 ms 之间，TCP 也要等到 160 ms 才触发重传定时器，白白浪费了几乎一整个 RTT。反过来想象平均 RTT 20 ms 但方差极大的情形：RTT 有时高达 80 ms，尽管相当一部分分组只是"慢"，TCP 也会认定它们丢了、把拥塞窗口砍到 1 并重传它们。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> EWMA 是概率论里"在线估计均值"的最朴素形态，值得用你学过的递推语言拆解：$r \leftarrow \alpha r + (1-\alpha)m$ 等价于把历史测量按指数衰减的权重加权平均，权重总和为 1。取 $\alpha = 7/8$（经典配置）时，最近的测量占 $\frac18$ 权重，而 $k$ 轮之前的测量权重以 $(7/8)^k$ 指数衰减——估计的"有效记忆长度"是 $\frac{1}{1-\alpha} = 8$ 个样本。这与马尔可夫链里"状态只依赖上一状态"的递推结构同构，也与信号处理里的低通滤波、控制论里卡尔曼滤波（Kalman filter）的标量特例一脉相承：都是"拿新观测修正旧信念"。真正精妙的是下一页的洞察：只估计均值 $E[RTT]$ 是不够的，还必须估计方差——因为超时本质是一次假设检验（"这个分组到底丢没丢"），检验的阈值必须按分布的**离散程度**而不只是中心来设置。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 6：TCP Tahoe Timeouts（TCP Tahoe 的超时估计）</span>

- $r$：RTT 估计值，初始化为某个合理值；
- $g$：EWMA 增益（例如 0.25）；
- $m$：最近被确认的数据分组的 RTT 测量值；估计误差 $e = m - r$；
- <span style="color:#00838f;">$r \leftarrow r + g\,e$</span>；
- 方差估计：<span style="color:#00838f;">$v \leftarrow v + g\,(|e| - v)$</span>；
- 超时 $= r + 4v$；
- 重传再失败时，按指数增大超时（防极度拥塞）。

**讲稿**：于是 TCP Tahoe 把 RTT 方差的估计纳入了重传超时。它像从前一样维护 RTT 估计的指数加权移动平均，同时测量"测量值与估计值的差"即误差，并对这个方差 $v$ 也做指数加权平均。超时取 RTT 估计值加四倍方差。这样：连接的 RTT 很稳定时，超时只比平均 RTT 略大；RTT 波动很大时，TCP 会选一个大得多的超时。若重传失败（未获确认），则以指数增长的定时器再次重传——TCP 认为这意味着极度拥塞，于是通过拉大发送间隔继续它的乘性减。参数 $g$ 与 $\beta$ 经少量实验选定，对它们的微小改动相当稳健；背后没有魔法，只是实践中好用。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "超时 $= r + 4v$" 这个 4 倍系数可以直接对应到概率论：若把确认到达时间的波动近似看作正态分布（中心极限定理在"多段时延叠加"下的合理近似），$v$ 是平均绝对偏差的估计（约 $0.8\sigma$），$r + 4v \approx r + 3.2\sigma$——即按"均值加三个标准差"设阈值，落到正常波动范围之外的概率仅千分之一量级。这正是假设检验里平衡第一类错误（假警报：把没丢的当丢了，白白触发慢启动）与第二类错误（漏报：真丢了却不重传，白白空等）的阈值选择——1986 年前的 TCP 把两类错误的成本都算错了。Van Jacobson 1988 年论文里明确说这个系数不是推导出来的而是试出来的，这种"理论给结构、实验定参数"的工程方法论值得记住：$g = 0.25$ 与系数 4 至今仍在 Linux 内核的 TCP 栈里服役。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 7：RTT Estimation Improvement（RTT 估计的改进：实测对比）</span>

图示：左右两幅实测曲线（出自 Van Jacobson 与 Karels《Congestion Avoidance and Control》，经许可使用）。Tahoe 之前（Pre-Tahoe）：浅色带数据点的线是 TCP 观测到的 RTT，上方深色线是超时估计。Tahoe：超时估计紧密贴合 RTT 测量值。

**讲稿**：这是取自 TCP 拥塞控制原始论文的两幅图。两幅都画出了 TCP 观测到的 RTT（下方浅色带数据点的线）与 TCP 维护的超时估计（上方深色线）。Tahoe 之前的 TCP 非常保守：测量值与超时值之间的大间隙代表被浪费的时间——TCP 要等太久才重传；而且在第 60 个分组附近 RTT 猛增时，Tahoe 之前会不必要地重传并进入慢启动。相比之下，右侧 TCP Tahoe 的 RTT 估计紧密跟随 RTT 值。至此我们回答了第二个问题：TCP 何时重传数据？这一课的教训是：在网络协议中需要估计重传/重试定时器时，不仅要考虑观测到的往返时延，还要考虑它的**方差**。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 8：Three Questions（三个问题——第三问）</span>

**讲稿**：现在来到第三个问题：TCP 何时发送确认？

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 9：Three Improvements（三项改进——自时钟）</span>

- 拥塞窗口；超时估计；**自时钟**。

**讲稿**：事实证明答案通常是"尽可能不加延迟地立即确认"。如果 TCP 遵循这个策略，就会引出一个非常重要且强大的行为——自时钟。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 10：Self-Clocking（自时钟）</span>

- 存在瓶颈链路时，发送方收到的是**在时间上被恰当间隔开**的确认。

图示：sender（发送方）与 receiver（接收方）之间的往返路径，瓶颈链路以窄腰呈现。

**讲稿**：自时钟的含义是：如果 TCP 急切地发送确认，这些确认会按瓶颈链路的吞吐量在时间上自动间隔开来。发送方收到的确认在时间上被拉开了间隔。由于发送方一收到确认、窗口一前进就发新数据，这意味着它将**按瓶颈链路所能支撑的速率**发送报文段。这张图把该行为可视化：网络的吞吐量表现为路径的宽度，时间表现为路径在时间轴上的长度。在"胖"的高带宽链路上发送的分组耗时很短；同样的分组经过低带宽链路时，传输与排队时延更长、耗时更多。当它们从瓶颈链路出来时，速度恢复，但已按瓶颈的速率在时间上被间隔开。由于确认分组很小，且假设瓶颈不在反方向路径上，确认就会以近似其穿越瓶颈链路的速率到达发送方。这个策略还有一层额外的好处：TCP 只在收到确认（即自己的某个分组已离开网络）时才向网络注入新分组。从拥塞的角度看，这意味着 TCP 让在途分组数——即它对网络中队列与容量的占用——保持**稳定**。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 11：Self-Clocking Principle（自时钟原理与全讲总结）</span>

- **有数据离开，才放入新数据**——想防止拥塞，即网络中数据过多；
- 以收到确认为契机发送新数据；
- 急切地发送确认——这是重要信号。

**讲稿总结**：自时钟原理意味着 TCP 一收到数据分组就急切地发送确认——这是在向发送方发信号"数据已离开网络"，同时也给它提供 RTT 估计并让它为自己的传输自我节拍。总结：TCP Tahoe 引入了三大机制，使其即使在繁忙网络中也能有效管理拥塞并获得好性能。第一，引入拥塞窗口，并维护一个在慢启动与拥塞避免之间转移的类 AIMD 状态机，由状态机控制拥塞窗口的更新。第二，用指数加权移动平均与方差共同计算重传定时器，同时减少假阳性和假阴性。第三，通过急切地发送确认，让数据传输自我节拍，匹配瓶颈链路的速度。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 自时钟的核心是排队论的稳态条件 $\lambda \leq \mu$（到达率不超过服务率）：TCP 严守"一个确认回来（一个旧包离开网络）才放一个新包进去"的出入门禁，把注入速率自动钳位在瓶颈的排空速率上——队列既不无限增长（不拥塞），也不被抽干（不浪费）。妙就妙在发送方**根本不知道**瓶颈在哪、速率多少：确认流穿过瓶颈链路时被其速率"压模"成一枚时间间隔均匀的节拍器，发送方只需跟着节拍走，就自动以正确速率发送。这是端到端设计的又一范例：不测量、不发令，靠反馈回路的物理性质自动获得正确行为。概率论视角还有一层：确认到达间隔的波动通过"发一个"逐包传递到下一轮，形成自相关的时间序列——只要波动不放大，系统就稳定；这为后面快速重传一讲"为什么必须小心处理重复确认"埋下伏笔，因为任何破坏节拍（burst）的行为都会在自时钟回路里被放大。
