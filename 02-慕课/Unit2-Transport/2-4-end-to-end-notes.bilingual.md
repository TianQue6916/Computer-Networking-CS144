### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 1：标题页</span>

The End-to-End Principle（端到端原则）。

<span style="color:#7f8c8d;">（Slide 1/13）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 2：两个"端到端原则"与应用视角</span>

Nick：端到端原则在互联网的设计中占据一个非常特殊的位置。这是因为它实际上指的是**两个**不同的原则：第一个关乎正确性——如果你在设计一个联网系统时不遵循端到端原则，那么系统很可能存在缺陷、可能错误地传输数据；第二个我们称之为"强"端到端原则（"strong" end-to-end principle），它更加宽泛、更加一般化。

本页图示（Application View of the World，应用眼中的世界）：一台主机 A 上有一份文件（file），通过一条连接送往主机 B——应用视角下，A 与 B 之间就是一条搬运文件的通道。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 开场第一句就把最容易踩的坑指出来了：平时大家说"端到端原则"时，往往混用了两个强度完全不同的命题。**弱原则**是一条正确性论证："某功能若只在端点有完整信息，就必须由端点实现，网络顶多做性能增强"——它是可证明的、不带价值判断的工程论断；**强原则**是一条架构立场："凡是能与通信无关完成的，就不要放进网络"——它是关于"应该把什么放进哪一层"的设计哲学，本质上无法被严格证明，只能被长期演化结果所检验。区分这两者非常重要：看完本讲你会发现，所有"网络做了也没坏处"的例子（压缩、链路层重传）都不违反弱原则，但全都违反强原则。🎥 *McKeown 在视频中解释： "端到端原则在互联网的设计中占据了一个非常特殊的位置……这是因为它实际上指的是两个不同的原则，第一个涉及到正确性"*（字幕来源：026 - p25 2-4 End to End Principle.zh.srt）。读后面的内容时，建议每遇到一个例子就自问一次：它违反的是弱原则还是强原则？

<span style="color:#7f8c8d;">（Slide 2/13）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：例子——从一台计算机传输文件到另一台</span>

Phil：假设我们要把一个文件从一台计算机传到另一台。我们的应用在 A 与 B 之间打开一条连接，读取计算机 A 上的文件，把它写入这条 TCP 连接；B 从套接字（socket）读出数据，写入计算机 B 上的文件。网络在这个过程中做得很少：它只是把分组从 A 转发到 B。连接由 A 和 B 建立，数据由应用读和写。

本页图示：应用视角的文件传输——A 侧"磁盘（disk）→ 应用（app）"，B 侧"应用 → 磁盘"，中间是那条连接。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 7：端到端论断的原始表述（Saltzer、Reed、Clark，1984）</span>

Phil：为什么网络不多做一些？其实它有很多办法让文件传输更快：网络可以自动在 A 与 B 之间压缩分组——如果文件是纯英文文本，传输量能缩小到十分之一；网络可以重排格式或改进请求——比如 A 要向 B 传两个文件，网络可以看破这一点，把两次传输合并成一次请求；A 的文件也可能已经存储在另一台计算机 C 上，而 C 离 B 更近、更快，网络可以改从 C 而不是 A 取文件；网络还可以自动加上安全性，加密数据让坏人读不了文件——如果网络替我们做了，应用就不必操心；网络可以增加移动性支持，让计算机 A 在网络中移动时路由自动更新、分组继续流向它——有了这种支持，我们甚至能把连接跨网络迁移，比如把 Skype 视频流从手机挪到笔记本。事实证明，网络**确实**有许多能改进应用、让应用更易设计的办法。但一般而言，它不做。为什么？

> <span style="color:#2471a3;">**[definition]**</span> <span style="color:#00838f;">**端到端论断的原始表述**：所讨论的功能，只有凭借位于通信系统端点处的应用的知识与帮助，才能被完整且正确地实现。因此，把该功能作为通信系统自身的一个特性来提供，是不可能的。（有时，由通信系统提供的该功能的不完整版本，或许可作为性能增强手段而有其用处。）我们把这条论证思路称为……"端到端论断"。
> —— Saltzer、Reed 与 Clark，《End-to-end Arguments in System Design》（系统设计中的端到端论断），1984 年</span>

Nick：答案就是端到端原则。它由 Saltzer、Reed 和 Clark 在 1984 年的一篇论文中首次阐述，本课程后面你还会见到 David Clark——他会来做客座讲座。原则原文如上。换一种说法：网络确实可能做各种事情来帮忙，但它能做的也**只是帮忙**。如果系统要正确工作，端点就必须为正确性负责——没有别人拥有完成这件事所需的全部信息。网络可以帮你，但你不能依赖它。例如，想确保应用安全，就必须在应用内实现端到端的安全；网络可以附加额外的安全手段，但端到端的安全只能由应用本身正确完成。所以"把安全做成网络的一个特性、让应用从此不用操心"是不可能的。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这段 1984 年的引文值得逐句精读。第一句的限定词是"**完整且正确地**实现"——注意它不是说"网络不能做这件事"，而是说"网络做不完整、做不正确"，理由是信息论式的：这个功能所需的全部知识只存在于端点（本讲后面 MIT 的故事就是铁证）。第二句更微妙："因此，把该功能作为通信系统自身的特性来提供是不可能的"——结论是针对**作为唯一保证的特性**，而不是针对"碰一碰"：括号里专门放行"不完整版本作为性能增强"，这句话就是 Slide 12 无线链路重传的合法执照。读引文时还要注意时代背景：1984 年是 MIT 校园网与早期互联网高速成形的年代，作者 Saltzer 与 Reed 是 MIT 的教授、Clark 是 MIT 的研究员，他们讨论的"网络"正是后来互联网的原型；这份论断随后被写进了互联网的架构基因。判断一个功能该不该放网络里，用原文的两问就够：第一，它的正确性是否只依赖端点信息？第二，网络中的版本坏了/不做，端点还兜得住吗？两问都过关，才轮到讨论"要不要做"。

<span style="color:#7f8c8d;">（Slide 7/13）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 8：例子——文件传输</span>

Nick：回到两台计算机之间传文件的例子。正是这个（以及类似的）问题，促使 Saltzer、Clark 和 Reed 提出了端到端论断。你想确保文件完整、无损坏地到达。文件数据要经过源与目的地之间的若干台计算机：来自 source（源）的文件，在到达 destination（目的地）之前，会依次经过计算机 C、D、E。

本页图示在上页基础上补全：源与目的地之间的每段链路（source→C、C→D、D→E、E→destination）各有一处差错检测（error detection），传输途中每段链路上都可能发生错误（error）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 10：MIT 程序员的推理</span>

Nick：每段链路——source 到 C、C 到 D、D 到 E、E 到 destination——都有差错检测。如果一个数据分组在传输中被损坏，接收方就能检测出来并拒收该分组；发送方会弄清这个分组没有成功到达——例如通过 TCP 的确认——然后重发。于是有人会说："瞧，我知道分组在任何一段链路上都不会损坏，因为我有我的检查；既然哪段链路都不会损坏，那就不会损坏。所以只要它成功到达了 destination，就没有损坏，文件就成功到达了。"当年 MIT 的一些程序员正是这么想的：既然网络提供了差错检测，他们就假设它能检测出**所有**错误。

<span style="color:#7f8c8d;">（Slide 10/13）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 11：坏内存的教训与端到端检查</span>

Phil：这个假设被证明是错的，因为这一错误，开发者们最终损失了大量源代码。事情是这样的：传输路径上的一台计算机——比方说 D——内存出了故障（buggy memory），有时会翻转一些位。D 收到数据分组、做了检查、发现无误。

本页图示在链路检错的基础上，在计算机 D 上补画了"内存（memory）"元素——错误正是在这里、在检查**之后**发生的。

Phil（续）：D 接着把分组移进主存，此时数据被损坏了。然后它转发该分组；因为差错检测发生在**链路**上，从链路的视角看这个分组完好无损，于是顺利通过 E 的检查。链路差错检测是为**传输**错误设计的，不是为**存储**错误设计的。唯一能确保文件正确到达的办法，是执行一次**端到端**的检查：源在发送文件时附带一些差错检测信息；目的地重组文件后，检查整个文件是否有错。这是唯一能确信文件无错的办法。网络可以帮忙，但不能对正确性负责。另一个具体例子是 TCP：TCP 提供"可靠字节流"服务，但这种可靠性并不完美——仍有可能给你坏数据，例如你的 TCP 协议栈有 bug，或某处悄悄出了错。所以尽管 TCP 给你损坏数据的可能性**很小**，它毕竟存在，你需要对它送来的数据做端到端检查——如果你用 TCP 传文件，就再做一次端到端校验确认它完整到达。例如 BitTorrent 就是这么做的：用 TCP 传数据块，每个块传完后用哈希（hash）校验它是否完好。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> MIT 源码丢失的故事是"抽象泄漏"（leaky abstraction）最生动的历史案例之一：链路层"保证帧不坏"这个抽象是**有适用范围的**——它只覆盖"传输线上"的错误，而 D 机器的错误发生在"检查通过之后、存入内存之时"，恰好落在所有中间层保证的缝隙里。每个中间检查都自洽，串联起来却百密一疏，这正是"端点才有完整信息"的实证：只有 source 和 destination 知道"这个文件从头到尾应该是什么样"。这也和你在 CSAPP 中获得的经验同构：CSAPP 讲存储器层次结构时反复强调，越靠近 CPU 的存储越贵也越脆弱，系统必须自己处理位损坏——磁盘、内存、传输线各有错误模型，没有哪一层能替你的应用兜底全部。🎥 *McKeown 在视频中解释： "唯一确保文件正确到达的方法是进行端到端的检查"*（字幕来源：026 - p25 2-4 End to End Principle.zh.srt）。BitTorrent 的做法给了我们一个可迁移的工程模式：**在已有的可靠通道之上，为"你真正关心的东西"再算一次校验**——Lab 里你做完字节流重组器后，用一个高层校验（比如对重组结果整体哈希）自测，就是同一思想的最低成本实践。

<span style="color:#7f8c8d;">（Slide 11/13）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 12：例子——链路可靠性</span>

Phil：回到 TCP 与可靠性。想要端到端的可靠数据传输，就需要像 TCP 这样的端到端可靠协议。但按端到端论断的逻辑：端到端功能对**正确性**必不可少的同时，网络仍然可以包含该功能的不完整版本，作为**性能增强**。无线链路层正是这样一种性能增强。如今，有线的链路层高度可靠（除非你的线缆或接头坏了），无线链路则因种种原因不可靠：有线链路上发送的分组通常 99.999% 能成功到达下一跳，而无线链路有时只有 50% 或 80%。事实证明，TCP 在低可靠性环境下表现不佳。所以无线链路层通过**在链路层重传**来提高自身可靠性：你的笔记本向接入点（access point）发送一个分组，接入点收到后，仅仅几微秒之后就回送一个链路层确认，告诉笔记本分组已成功收到；如果笔记本没收到链路层确认，就重传，如此若干次。借助这些链路层确认，一条只有 80% 可靠性的糟糕链路可以被提升到 99% 甚至更高，让 TCP 工作得好得多。没有链路层的帮忙，TCP 也能**正确**工作——可靠地传数据；但链路层的帮忙极大改善了 TCP 的**性能**。这就是端到端原则：要让某件事正确，就必须端到端地做；中间可以做事来帮忙、作为性能改进，但如果你不依赖端到端，那么迟早会出错。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 无线链路重传是"性能增强"分支的标准范例，而且这里的收益可以用你概率课上学的独立试验模型算出来：设单次发送成功率 $p$，链路层独立重传直到成功，则最终成功率是 $1-(1-p)^k$（$k$ 为最大重传次数）——以 $p=0.8$、$k=3$ 代入就是 $1-0.008=99.2\%$，正是讲稿说的"80% 提到 99% 以上"的量级。但请注意代价的另一面：重传抬高了**时延的方差**——多数包一次就过，少数包要等两三轮，尾时延（tail latency）被拉长。强端到端的批评者会指出：链路层做这个决定时，**假设了**"上层宁要低丢包、不怕多等几毫秒"——对 TCP 文件传输这假设成立，但对宁可扔掉旧帧也要发新帧的实时协议（如某些语音/视频应用）就不成立，可它们被 WiFi 的重传机制"绑架"了。这个矛盾正是下一页"强端到端原则"的核心论据，也预告了 Unit 4 的一个主题：不同流量对"丢包 vs 时延"的偏好不同，任何固定在中间层的策略都会让一部分流量不高兴。

<span style="color:#7f8c8d;">（Slide 12/13）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 13："强"端到端原则（RFC 1958）</span>

> <span style="color:#2471a3;">**[definition]**</span> <span style="color:#00838f;">**"强"端到端原则**：网络的职责是以尽可能高效、尽可能灵活的方式传输数据报；其他一切事情都应当在边缘完成…… —— 摘自 RFC 1958（"Architectural Principles of the Internet"，互联网的架构原则）</span>

Nick：端到端原则还有第二个版本，写在 IETF 的 RFC 1958《The Architectural Principles of the Internet》中，我们称之为"强"端到端原则。它比第一个版本更强：第一版说的是某功能**必须**在端点（边缘）实现，但同时也可以在中间实现一份来改进性能；强原则则说**不要**在中间实现，只许在边缘实现。强原则的理由是灵活性与简单性。如果网络为了帮端点而实现了某项功能，它就在**假设**端点在做什么。例如，无线链路层用重传提高可靠性、好让 TCP 工作得更好时，它假设了"重传增加的时延是值得的"——这并不总成立：还有不看重可靠性的其他协议，它们可能宁可发一个新的、不同的分组，也不愿重发旧的；但因为链路层已经内置了可靠性增强，这些协议只能被迫接受。这会、而且确实已经构成了对创新与进步的阻碍：当各层开始按照"上下层会怎么做"的假设来加入优化时，重新设计各层就越来越难。以 WiFi 为例：它是一个假设了网络层与传输层某些行为的链路层；如果你发明一个新的传输层或网络层协议，它多半也得反过来迁就 WiFi 的行为才能跑得好——如此一来，网络设计就钙化（calcified）了，变得极难改变。从长期设计与网络演化的角度看，强端到端论断价值巨大。张力在于：就短期设计与性能而言，网络工程师和运营者常常不遵循它。于是随着时间推移，网络越跑越好，却越来越难改。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "钙化"这个比喻值得展开，因为它解释了互联网架构几十年来最核心的路线之争：一个层一旦为了优化上层而"记住"了上层的假设，它就从**通用**变成了**特化**——WiFi 假设上层是 TCP（丢了会重传、怕乱序），于是对不重传的新协议表现为"多余的等待"；中间盒假设应用是 HTTP，于是新协议换个端口就常常被防火墙拦截。强原则本质上是在为**未来的未知协议**买保险：今天少做一点优化，明天就多一条活路。这与你在 CSAPP 里体会过的抽象价值完全同构——系统调用接口几十年来保持稳定，正是因为它"什么都不假设"，应用才能从单核演进到多核而不改一行代码。注意讲稿结尾点出的"张力"：强原则是**长期演化**的立场，弱原则是**当下正确性**的底线，现实工程（如 WiFi 重传）往往遵循弱原则而违反强原则——这不是谁对谁错，而是短期性能与长期灵活性的经典权衡。你自己写系统时也会遇到它：函数库里要不要为已知的调用方加缓存？想清楚这个例子，就理解了这对原则的全部分歧。
