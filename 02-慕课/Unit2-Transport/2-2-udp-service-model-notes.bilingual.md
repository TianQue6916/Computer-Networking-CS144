### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 1：UDP——用户数据报协议</span>

在这个视频中，你将学习第二个传输层协议——UDP，用户数据报协议（User Datagram Protocol）。使用 UDP 的应用不需要 TCP 那种有保证的交付服务：要么因为应用以自己的私有方式处理重传，要么因为应用根本不需要可靠交付。UDP 比 TCP 简单得多——这也是本视频短得多的原因。UDP 所做的全部事情就是：取来应用数据，构造一个 UDP 数据报（UDP datagram），然后交给网络层。UDP 数据报标明数据在另一端应交付给哪个应用。基本就这些。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "简单得多"不是偷懒，而是一次自觉的抽象取舍：UDP 头部只有 4 个字段、8 个字节，而 TCP 头部有十多个字段、通常 20 字节起步，还不算建立连接、维护状态机、重传计时这些运行时开销。从 CSAPP 的角度看，UDP 就是 `SOCK_DGRAM` 那条代码路径：`sendto()` 一次调用发完一个数据报，没有 `connect()`、没有流控、没有内核重传——内核在 UDP 这条路上几乎是"直通"的。这种薄抽象的价值在于把控制权交还应用：如果应用自带的逻辑已经能容忍丢失（比如实时语音宁可丢一帧也不能等重传），那 TCP 那套可靠性就纯属多余的税。记住这个"最简传输层"的样子，等你看完 TCP 的全部机制之后回头看 UDP，会发现它其实是"传输层可以做得多简单"的对照组。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 2：封装与 UDP 头部的四个字段</span>

一如我们所期待的，UDP 数据报被封装在 IP 数据报的数据字段中。UDP 提供的服务非常简单——从 UDP 头部字段之少就能看出来：TCP 有十多个头部字段，UDP 只有 4 个。

1. **源端口（source port）**：标明数据来自哪个应用。如果远端要回复，它会把回复数据报的目的端口填成这个端口号，让回复能找到回到正确应用的路径。
2. **目的端口（destination port）**：标明数据在另一端主机上应交付给哪个应用。UDP 的端口号与 TCP 的端口号作用相同——把到达的分组引导给正确的应用进程。
3. **16 位长度字段（length）**：以字节为单位指定整个 UDP 数据报的长度——头部加数据。其值至少为 8，因为那是 UDP 头部自身的长度。
4. **UDP 校验和（checksum）**：使用 IPv4 时是可选的。如果发送方不包含校验和，该字段填全零；如果使用 UDP 校验和，就对 UDP 头部与数据计算。实际上，UDP 校验和的计算还包括 IPv4 头部的一部分（如图所示）：计算范围包括 IP 源地址、目的地址，以及取值为 17 的协议号（protocol ID）——17 表示这个 IP 数据报承载的是 UDP 数据。

你可能会问：为什么 UDP 校验和要包含 IP 头部的一部分——这难道不违反层间的清晰分离吗？是的，确实违反。打破分层原则、借用下层信息的理由是：这让 UDP 层能够发现那些被送到了错误目的地的数据报。总结：UDP 头部很小，因为它向应用提供的服务非常简单——它只是一个简单的消息协议，把数据从一台主机上的应用发出去，至于能否交付到远端主机上的应用，不作保证。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 校验和覆盖"伪首部"（pseudo-header）这件事是分层教学里最经典的"违规案例"，值得与 tcp-header 讲义里 TCP 的做法对照着记：两者都把 IP 源/目的地址和协议号卷进校验计算。🎥 *McKeown 在视频中解释： "你可能想知道为什么 UDP 校验和包括 IP 头部的一部分，这不违反层之间的清洁分离吗？哦是的，确实如此"*（字幕来源：024 - p23 2-2 UDP service model.zh.srt）。为什么设计者明知违规还要违规？因为否则会出现一类无法检测的错误：IP 首部里的地址字段如果在校验之前就被损坏——比如在路由器内存里翻了一位——分组会被投递到错误的主机，而端到端的 UDP 校验和（只覆盖 UDP 头和数据）毫无察觉，数据安静地进了别人的进程。把 IP 地址卷进来后，"送错地方"这类错误会暴露。这里能提炼出一条一般规律：**分层是组织复杂度的手段，而每一层的差错检测边界决定该层能对哪些错误负责**——UDP 的设计者选择让自己也对"投递正确性"负责，哪怕付出违反分层的代价。这个主题在 2-4 端到端原则里会被推到极致。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：端口号与分用</span>

UDP 的端口号与 TCP 的端口号工作方式相同。如果主机 A 上的进程 1 要向主机 B 上使用端口 177 的进程 1 发送数据，数据会被放入一个目的端口为 177 的新 UDP 数据报；主机 A 加上自己的源端口号，以便任何回复都能送回 A 上的进程 1。数据报被封装进 IP 数据报发往主机 B；主机 B 剥出 UDP 数据报，把数据定向给进程 1。

把 UDP 仅仅看作一种**分用**（demultiplexing）机制是有益的：把到达的 UDP 数据报流拆分开，送到正确的进程。事实上，有人因此戏称 UDP 为"用户分用协议"（User Demultiplexing Protocol）——这基本上就是 UDP 做的全部事情。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "User Demultiplexing Protocol" 这个玩笑其实点破了 UDP 的本质——它对 IP 层唯一真正的增值就是把"主机到主机"细化为"进程到进程"。你可以对照 CSAPP 里的实现来理解：内核收到 IP 数据报后查协议号（17 = UDP），剥出 UDP 头，再用目的端口查 UDP 套接字表找到对应的 socket，把数据挂到它的接收缓冲区上——这一整套动作就是分用。也正因如此，UDP 套接字之间的区分规则比 TCP 宽松得多：TCP 套接字按完整五元组精确匹配（所以一台 Web 服务器能同时挂成千上万条连接），而 UDP 套接字（未 `connect()` 时）只按"目的端口"匹配——两个不同的客户端发来的数据报会落进同一个 socket，应用必须自己在数据里写明"我是谁"。对比 2-1 里 TCP 的五元组唯一标识，你就明白"UDP 无连接"在实现层的真正含义：**没有连接状态可供区分对端**，分用粒度只能粗到端口。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 4：UDP 服务模型总表与典型用户</span>

总结 UDP 的服务模型，它具有表中所示的三个性质。

**第一，无连接（connectionless）的数据报服务。** <span style="color:#00838f;">不建立连接，因为不需要——全部信息都自含（self-contained）在数据报中。</span>这意味着分组可能以任意顺序到达；如果应用在意按序交付，就得自己对数据重新排序。

**第二，UDP 是不可靠（unreliable）的交付服务。** 它不发送任何确认来告知数据是否到达对端，也没有检测数据报缺失的机制。如果整个数据报在途中被丢弃，UDP 既不会通知应用，也不会要求源端重传。不过，应用可以选择自己再次请求数据——本质上是在 UDP 之上自建重传机制。早期版本的 NFS（网络文件系统，network file system）正是这么做的：它们决定不用 TCP 的滑动窗口，而是在应用内部自建了一套。

UDP 听起来应该非常像 IP 层提供的服务。没错——UDP 几乎只是 IP 层之上的一层薄包装，外加把到达数据引导给对端正确应用的手段。那么我们为什么还需要 UDP？它是给那些不需要可靠交付的应用用的，比如简单的请求-响应（request-response）应用。DNS——互联网用来把主机名（hostname）解析为 IP 地址的域名系统——使用 UDP，因为整个请求完全装在一个 UDP 数据报里。你稍后会学到 DNS 的工作原理，现在只需知道：如果我们发送一个携带主机名的 DNS 请求，DNS 服务器会回复一个可用于向该主机发送 IP 数据报的 IP 地址。请求成功时，用 UDP 轻量而快速——查询前无需建立连接；请求失败时，它会超时并被重发。这让 DNS 在绝大多数时候既简单又快。DHCP（动态主机配置协议，Dynamic Host Configuration Protocol）同样使用 UDP：DHCP 帮助新加入网络的主机获知自己的 IP 地址——你的笔记本连上 WiFi 时多半就在用 DHCP。我们稍后会深入学习 DHCP，现在只需知道它也是请求-响应型应用，把一个自含的请求装在一个 UDP 数据报里。网络时间协议（NTP，Network Time Protocol）也出于同样的原因使用 UDP。

另一些应用使用 UDP 是因为它们对重传、拥塞控制、按序交付有自己特殊的需要。少数实时音视频流服务使用 UDP。这已经比过去少见得多，因为如今大多数 HTTP 上的音视频流改用了 TCP。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> NFS 在 UDP 之上自建可靠性的故事，其实是端到端原则（下一讲的主角）提前登场：文件系统语义要求"写入成功 = 数据真正落盘"，这个正确性承诺无论如何都得由端点自己兑现，所以"用 TCP 还是自建重传"只是**实现位置**的选择，而不是"要不要可靠"的选择。NFS 团队宁可自建，是因为想要比 TCP 滑动窗口更贴合自己读写模式的窗口策略——这预告了 2-4 的结论：网络中间层提供的可靠性只能算性能增强，不能算正确性保证。另外注意本讲结尾那句"如今大多改用 TCP"的历史判断：它之后互联网又演化出了新的平衡——UDP 之上的 QUIC 协议（HTTP/3 的底层）把重传、加密、拥塞控制全部搬回用户态应用侧实现，恰好走的就是 NFS 式的"自建"路线，只是做得更彻底。学完 2-4 再看 QUIC 的取舍会觉得非常自然：既然可靠性责任本来就在端点，那把它放进内核还是用户态，就成了纯粹的性能与演进灵活性之争。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 5：总结</span>

总结：UDP 在应用进程之间提供一种更简单的、数据报式的交付服务。
