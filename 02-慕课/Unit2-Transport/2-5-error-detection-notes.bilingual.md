### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 2：为什么需要差错检测</span>

网络并不完美，运行网络的主机也不完美。它们会引入错误，而网络要正常运行，就必须能检测出这些错误。例如，假设路径上的某台路由器有一个坏内存单元，有时会翻转分组中的某一位。设想被翻转的是"信用卡应扣金额"的最高位——我们必须能检测出发生了错误，才能不把损坏的数据当作正确数据接受。如今的网络普遍使用三种差错检测算法：校验和（checksum）、循环冗余校验（cyclic redundancy code，CRC）与消息认证码（message authentication code，MAC）。它们的特性差异非常大，理解这些差异很重要！笔者（讲稿作者）真的在 IETF 会议上见过有人不了解这些差别；不了解的话，你可能做出糟糕的协议决策或错误的分析。

本页图示（Error Detection，差错检测的结构）：对一段数据（Data）计算差错检测信息（ED），然后**附加**或**前置**到数据上。例如：以太网（Ethernet）在尾部附加 CRC；传输层安全协议（TLS）在尾部附加 MAC——TLS 与以太网都有"尾部"（footer，跟随在有效载荷之后的协议信息），CRC 与 MAC 就放在那里；而 IP 把校验和**前置**，放在 IP 首部里。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 本讲全部内容可以用一个信息论框架统一起来：差错检测就是"把 $n$ 比特的数据**蒸馏**成 $c$ 比特的摘要"，接收方重算摘要比对即可。由鸽笼原理，$2^n$ 种消息映到 $2^c$ 种摘要（$c \ll n$），必然大量碰撞——任意两条消息碰巧共用同一 ED 的概率约为 $2^{-c}$。所以"用多少比特"直接决定"检测能力的天花板"，这是三种方案共享的物理预算；它们真正的差别在于**碰撞按什么模式分布**：校验和的碰撞有规律（两位错互相抵消就漏检），CRC 把碰撞模式设计得极不规律（对特定错误类别给出确定保证），MAC 则故意把碰撞模式搞得完全不可预测（防的是人不是噪声）。用你概率课的语言说：三者的差别不是"检测概率大小"的一维排序，而是错误分布假设不同——对随机硬件错误，CRC 的保证最强；对**故意构造**的错误，前两者形同虚设，只有 MAC 可信。带着这个框架往下读，每个算法的每条"保证"都能对号入座。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：三种差错检测方案总览</span>

- **校验和（Checksum）**：把分组中的值累加（用于 IP、TCP）。
  - 非常快，即使在软件里计算也便宜。
  - 不太稳健（not very robust）。
- **循环冗余校验（Cyclic redundancy code，CRC）**：计算一个多项式的余数（用于以太网）。
  - 比校验和更昂贵（如今很容易，硬件中更容易）。
  - 防护：任何 2 位错误、任何长度 $\le c$ 位的突发错误、任何奇数个错误。
- **消息认证码（MAC）**：数据的密码学变换（用于 TLS）。
  - 对恶意修改稳健，但对（随机）错误不然。
  - 若算法足够强，任意两条消息有 $2^{-c}$ 的概率得到相同编码。

校验和是三种常用差错检测算法中的第一种：把分组里所有的数据加起来，TCP 和 IP 用的就是它。校验和的优点是非常快、计算便宜，即使在软件里也如此——互联网早期一切都跑在软件里时，这一点非常宝贵。它的主要缺点是差错检测保证相当弱：虽然能抓住很多随机错误，但只需 2 个比特错误就可以骗过它——如果两位错误恰好互相抵消，比如一位错误使校验和加了 32、另一位减了 32，校验和就发现不了。所以校验和能抓住很多错误，但它对"会抓住哪些错误"的保证非常弱。

第二种是循环冗余校验（CRC）。CRC 的计算比校验和昂贵得多，但也稳健得多。它计算一个多项式的余数——几分钟后会展示这是什么意思、如何工作。以今天的处理器，这很容易做，在硬件里更容易做。以太网和许多链路层用的就是它。从某种意义上说，TCP 与 IP 之所以"敢"用校验和，正是因为链路层用了 CRC。<span style="color:#00838f;">一个 $c$ 位长的 CRC 可以检测：任何 1 位错误、任何 2 位错误、任何单个长度不超过 $c$ 位的突发错误（burst）、以及任何奇数个错误。</span>所以它提供的保证远强于校验和。

最后一种是消息认证码（MAC）。MAC 把分组与某些秘密信息结合，生成一个值。理论上，只有持有秘密的人才能生成或校验 MAC。所以如果你收到一个分组且其 MAC 正确，你就有相当把握：计算这个 MAC 的计算机持有秘密。只要我没有秘密，要为某个分组生成正确的 MAC 就极其困难，坏人也就无法轻易伪造新分组。事实上，若 MAC 算法足够强，那么给定一个分组及其 MAC，我对"翻转一位后 MAC 会变成什么样"得到的信息是**零**。因此消息认证码对恶意修改稳健。消息认证码用于传输层安全协议（TLS）——你安全浏览网页（https）时用的就是它。

但 MAC 对抓差错其实并不在行。如果我翻转分组中的一位，改变后的分组有 $2^{-c}$ 的概率得到**相同**的 MAC！笔者见过有人在讨论差错纠正时犯这个错误，以为 MAC 和 CRC 一样好用——不是的！16 位 CRC 保证我能检测长度不超过 16 位的突发错误；16 位 MAC 只保证我以很高的概率——99.998%，即每 65,536 次中 1 次漏检——检测到比特错误。这个概率很高，但想想你光是看这个视频就收到了多少分组……

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 4：IP 校验和——反码算法</span>

- IP、UDP 与 TCP 使用**反码**（one's complement）校验和算法：
  - 把校验和字段置 0，把分组中所有 16 位字累加；
  - 把进位加回去：0x8000 + 0x8000 = 0x0001；
  - 翻转各位（0xc379 变为 0x3c86）；除非和为 0xffff，此时校验和记为 0xffff；
  - 校验时：把整个分组（含校验和）加总，结果应为 0xffff。
- 优点：快，容易计算与校验——其动机来自最早的软件实现。
- 缺点：差错检测能力差——只保证检测单比特错误；能检测出其他错误，但实际保证既弱又复杂。

先讲校验和。IP、UDP 与 TCP 用反码校验和：用**反码算术**（one's complement arithmetic）累加分组——这是某些老式计算机使用的一种二进制算术版本，如今大多数机器用补码（two's complement）。算法很简单：先把分组的校验和字段置零；然后把分组中每个 16 位字加起来；每当和超过 65,535 需要进位时，把进位位加回去——例如 60,000 加 8,000 等于 68,000，即 68,000 $-$ 65,535 $+$ 1，等于 2,466。把整个分组加完后，翻转和的所有位，作为分组的校验和。校验时，把包括校验和在内的整个分组加起来，结果应为 0xffff。有一个边界情况：如果算出的校验和恰好是 0xffff，校验和字段**不**写 0，而是写 0xffff——因为在 IP、UDP 与 TCP 中，校验和字段为 0 表示"没有校验和"。就这些！这个算法用几行 C 代码就能写出来：快、易算、易校验，只需把分组的字节加起来。鉴于早期互联网实现大多是软件，这一点非常有用。缺点是它实在不够稳健：虽然确实能检测大量随机错误，但它能给出的保证非常弱——实践中只能承诺抓住单比特错误。不过它工作得挺好，因为链路层替我们做了大量重活。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "反码算术"直接接上了你在 CSAPP 第 2 章打下的地基：反码（one's complement）就是"按位取反表示负数"的方案，有两个补码没有的麻烦——0 有两种表示（0xffff 与 0x0000 都是零）、且加法要回卷进位。这里"把进位加回去"的步骤正是回卷（end-around carry）：$2^{16}$ 在这个算术体系里与 1 同余，所以 0x8000 + 0x8000 = 0x10000 回卷成 0x0001，与 6.042J 数论里"模 $m$ 意义下 $2^{16} \equiv 1$"的视角完全一致——校验和本质上是在 $\bmod\ 2^{16}-1$（对反码加法）的剩余类里做求和。为什么早期互联网选这么"古怪"的算术？讲稿一句话点破：动机来自最早的软件实现——回卷加法无需处理溢出分支、寄存器来回一趟就完事，在当初那些没有硬件乘法器的机器上极其廉价。这是"协议设计迁就实现成本"的绝佳标本：校验和弱得只保证单比特错，却因为快而活到了今天——它敢这么弱，靠的是链路层 CRC 兜底。**每一层按自己便宜的方式检测自己关心的错误**，这个分账逻辑在 Slide 10 会正式总结。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 5：循环冗余校验（CRC）</span>

- 循环冗余校验（CRC）：把 $n$ 位数据蒸馏为 $c$ 位，$c \ll n$。
  - 不可能检测所有错误：$2^{-c}$ 的概率另一分组的 CRC 恰好相同。
- CRC 的设计目标是检测特定形式的错误：比校验和更强。
  - 任何奇数个位错误的消息；
  - 任何 2 位错误的消息；
  - 任何单个长度 $\le c$ 位的突发错误。
- 链路层通常使用 CRC。
  - 硬件中计算快（细节稍后讲）；
  - 可以增量计算；
  - 对物理层的突发错误有很好的检测能力。

链路层干的"重活"靠的就是循环冗余校验（CRC）。CRC 的想法是：取 $n$ 位源数据，以某种方式蒸馏成 $c$ 位差错检测数据，$c$ 远小于 $n$。例如，一个 1500 字节的以太网帧只带 4 字节、32 位的 CRC；USB 与蓝牙使用 16 位 CRC。当然我们不可能检测出**所有**错误：随便给一个别的分组，其 CRC 与给定分组相同的概率是 $2^{-c}$——例如用 8 位 CRC，全部分组空间里有 1/256，即约 0.4%，与任意给定分组的 CRC 相同。但 CRC 比校验和强：它能保证检测出任何奇数个错误的分组、任何 2 位错误的分组、以及任何单个长度不超过 $c$ 位的突发错误。除这些之外的错误不能保证检测到，但实际效果也不错——例如 16 位 CRC 无法**保证**检测出同一分组中相距很远的两个 3 位突发错误，但很可能检测出来。链路层通常用 CRC，因为它相当稳健，而许多链路层恰恰容易遭受突发错误，CRC 的突发检测能力正对路；它也不难在硬件里快速计算，而且可以随着分组的读写**增量**计算。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 6：插叙——CRC 的数学基础</span>

- 循环冗余校验（CRC）：把 $n$ 位数据蒸馏为 $c$ 位，$c \ll n$。
- 使用**多项式长除法**（polynomial long division）：
  - 把消息 $M$ 看作系数为 0 或 1 的多项式（尾部补 $c$ 个零）。
    - 例：$M = 10011101 = x^7 + x^4 + x^3 + x^2 + 1$。
  - 用一个 $c$ 次的**生成多项式**（generator polynomial）$G$，系数同样为 0 或 1。
    - 出于令人恼火的历史原因，最高次项（恒为 1）要补在前面——例：$G = 1011 = x^4 + x^3 + x + 1$；USB（CRC-16）$= \texttt{0x8005} = x^{16} + x^{15} + x^2 + 1$。
  - 用 $G$ 去除 $M$，余数即 CRC：所以要精心挑选 $G$！
- 把 CRC 附加到消息 $M$ 上：$M' = M + \text{CRC}$。用 $G$ 做长除法除 $M'$，余数为 0。

CRC 如何工作？它用多项式长除法把 $n$ 位蒸馏成 $c$ 位：把消息的各比特看作多项式 $M$ 的各次系数——某位是 0，对应项就不出现；某位是 1，对应项就出现。例如消息 10011101 就是 $x^7 + x^4 + x^3 + x^2 + 1$，因为该消息的第 7、4、3、2、0 位被置位。计算 CRC 时还要用一个**生成多项式**，它由 CRC 算法规定。例如 USB 使用的 CRC-16 算法，其生成多项式是 $x^{16} + x^{15} + x^2 + 1$。出于令人恼火的历史原因，生成多项式的位表示比它的次数短一项：最高次项恒为 1，于是 CRC-16 的生成多项式虽含 $x^{16}$ 项，却写作 0x8005。计算 CRC 时，把消息 $M$ 补上与 CRC 长度相同的零，再除以 $G$，余数就是 CRC，附在消息后面。校验 CRC 时，把"消息 + CRC"除以生成多项式 $G$，余数为零则通过。数学细节不展开，但结论是：它可以非常快、非常高效地在硬件里实现。CRC 算法的强度取决于你挑了哪个生成多项式 $G$：这方面已有很多研究，存在许多具备上述差错检测性质的好选项；若你自己随手挑一个生成多项式，可就不一定能得到同样的检测强度了。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 多项式除法听着唬人，其实你在 6.042J 数论里已经握有全部工具：把每个字节序列看成系数属于 $\{0,1\}$ 的多项式，所有加减法都按**模 2** 进行——不进位、不借位，加法与减法同为异或（XOR）。于是"除以 $G$ 取余"就是普通的长除法把减法换成异或，CRC 的全部代数性质都来自这个"系数模 2 的多项式环"与整数模运算的平行结构：余数相同的消息校验等价、$M'$ 恰好是 $G$ 的倍数所以余零、以及"精心挑选 $G$"对应数论里"精心挑选模数"的老传统。为什么这套代数能换来"奇数个错全抓"这样的硬保证？单看一个例子：若 $G$ 含有 $(x+1)$ 因子，则任何奇数个位错误所对应的多项式在 $x=1$ 处取值恒为 1，不可能被 $(x+1)$ 整除——所以余数必非零、必被发现。这就是"选对 $G$，随机错误就掉进设计好的筛孔"的代数机制。工程上还有一条妙处：除法是流式的，每来一个字节就能滚动更新余数，所以硬件用一个移位寄存器加几个异或门就能算 CRC——以太网线卡上那颗几毛钱的芯片，每秒执行的就是这套除法。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 7：消息认证码（MAC）</span>

- 消息认证码（Message Authentication Code，MAC）。
  - 不要与媒体访问控制（Media Access Control，也叫 MAC）混淆！
- 用密码学方法生成 $c = \text{MAC}(M, s)$，$|c| \ll |M|$。
  - 拿到 $M$ 与秘密 $s$，可以验证 $c = \text{MAC}(M, s)$；
  - 没有 $s$，极难生成正确的 $c$；
  - 极难造出 MAC 恰为 $c$ 的另一条消息 $M$；
  - $M + c$ 的组合意味着对方多半持有秘密（或者是重放！）。
- 密码学意义上强的 MAC 意味着：翻转 $M$ 的一位，会令新 $c$ 的每一位都以随机的方式变为 1 或 0（不泄露任何信息）。
  - 作为差错检测器不如 CRC！
  - 但能保护你免受对手的破坏。

第三种、也是网络中最常见的最后一种差错检测算法，是消息认证码（MAC）。与 CRC 一样，MAC 背后有深厚而丰富的数学：有好算法也有坏算法，所以你一般应当使用现成方案而不是自己发明。所幸标准通常会指定用什么 MAC；虽然上世纪 90 年代末有些标准挑过糟糕的算法，但如今安全的重要性足以让所有人都依赖少数几种被充分研究过的方案。消息认证码使用密码学——一门研究秘密的数学。大多数 MAC 的想法是：双方共享一个秘密 $s$，它只是一组随机生成的比特（随机，所以难以猜出）。要计算消息认证码 $c$，就把 MAC 算法作用在消息 $M$ 与秘密 $s$ 上。MAC 算法的性质是：如果你没有 $s$，那么为消息 $M$ 生成正确的 $c$ 极其困难；此外，要造一条 MAC 恰好等于 $c$ 的消息 $M$ 也极其困难。所谓"困难"是指：最好的办法也只剩下穷举——拥有 $M$ 与 $c$ 几乎不提供任何关于 $s$ 的信息。这意味着，如果你收到一条消息 $M$ 且其 MAC 正确，就说明生成该消息的计算机多半持有秘密（或者有人重放了那台计算机生成的消息）。因为目标是对 $s$ 保密，密码学意义上强的 MAC 有一个有趣的性质：改动 $M$ 的一位，就会得到一个全新的 $c$，$c$ 中任何一位是 0 还是 1 看起来都是随机的。如果不这样，攻击者就可能拿一条消息、翻转一位（比如改个金额），而且不太难地造出正确的 $c$。这意味着 MAC 实际上**没有任何差错检测保证**：翻转一位后，新消息完全可能撞出同一个 MAC！消息认证码非常有用，但首先是安全机制：用同一个机制同时获得差错检测与安全固然高效而美好，但它的安全属性决定了其差错检测能力不如其他方案。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 把 MAC 与 CRC 放在信息论框架下对比，一切就清晰了：CRC 的设计目标是让"错误→校验失败"**必然**发生（对承诺的错误类别），它巴不得校验关系有结构；MAC 的设计目标恰好相反——让"消息→校验值"的映射**毫无结构**，攻击者翻一位、猜校验值都得不到任何帮助，这就是密码学里说的雪崩效应（avalanche effect）。于是出现一个反直觉的结论：**随机性最强 ≠ 检错最强**。MAC 漏检单比特错误的概率是 $2^{-c}$（每 65,536 次 1 次，对 16 位而言），而 CRC 对承诺类别是零漏检——为什么？因为 CRC 的"强"来自数学保证，MAC 的"概率"来自把碰撞均匀摊到整个空间。这一点直接呼应 Slide 2 注里的框架：错误分布假设不同，答案就不同——对付**噪声**用有结构的 CRC，对付**对手**用无结构的 MAC。另外注意首条 bullet 的提醒：网络课里两个 MAC 并存（消息认证码与媒体访问控制），读文献时靠上下文区分。最后一句"或者是重放！"也埋了个伏笔：MAC 只证明"这条消息出自持有秘密者之手"，不证明"它是刚发的"——防重放还需要序列号或时间戳，这正是后面 TCP 序列号机制的又一个用途。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 9：随堂测验（重复页）与解答</span>

本页与 Slide 8 为同一道测验（同一表格，此处不再重复）。下面讲评答案。

> <span style="color:#2471a3;">**[solution]**</span>
>
> 来对答案。**单比特错误**：两种校验和都能检测——记住，这是校验和保证能检测的错误之一；两种 CRC 同样能检测单比特错误；MAC 则**不能保证**检测单比特错误——出于安全设计，新 MAC 有可能恰好与旧 MAC 相同，所以无法保证。事实上，MAC 不能保证检测**任何**列中的错误：MAC 这一整行全部填 No。**2 位突发**：校验和不能保证检测两位错误，两列都填 N；而 CRC 保证能检测长度不超过自身长度的位错误突发——2 位短于 8 位也短于 16 位，所以两种 CRC 都能检测 2 位突发（都填 Y）。相应地，**9 位突发**：8 位 CRC 不能保证，16 位 CRC 能——8 位 CRC 填 N，16 位 CRC 填 Y。**相距 100 位的两位错误**：结果表明这些算法都**不能保证**检测，全填 N。
>
> 看着这张矩阵，你可能觉得差错检测是浪费——这些算法承诺的太少了！但"保证"（guarantee）是一个极强的词。16 位校验和虽然不能**保证**抓住 9 位突发，但它抓到的概率很高；同样，16 位 CRC 检测相距 100 位的两位错误的概率也非常高。实践中，高概率往往就够用了：如果故障罕见，那你只是偶尔才需要动用更昂贵的手段去恢复。这也意味着实践中你往往会部署**多层**差错检测：链路层用 CRC 检测，IP 用校验和检测，TCP 用校验和检测，最后应用常常还有自己的差错检测——层层叠加之后，错误漏网的概率变得极低极低。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这张矩阵最好的读法是竖着读出每种算法的"人格"：校验和只敢对单比特错举手表；CRC 对"2 位错、短突发、奇数个错"三类稳举 Y，多的不敢承诺；MAC 一行全 No——不是它差，而是它的设计目标（认证）根本不包含检测保证。而横着看最后一列还有一层深意：为什么"相距 100 位的两位错"连 CRC 都不敢保证？因为突发保证只覆盖**密集**错误，稀疏分布的多位错的漏检组合方式太多，任何 $c$ 位的余数结构都堵不完。最后讲稿引向的方向值得展开成一句方法论：**保证覆盖工程**。"保证"是免费保险的下限，"高概率"才是日常运行的真实水平；工程实践不追求单层完美，而是让多层相互独立地失败（链路 CRC 抓线上错误、IP/TCP 校验和抓穿网错误、应用哈希抓端系统错误），漏网概率就变成各层漏检概率的乘积——用概率论的话说，假设各层独立，总漏检率是逐层相乘的 $2^{-c_i}$ 量级，小到可以忽略。这个"廉价层叠加优于单层昂贵保证"的思想，和 2-4 的端到端检查完全连贯：端到端校验就是最上面那一层。

<span style="color:#7f8c8d;">（Slide 9/10）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 10：三种方案总结——每一层都有自己的差错检测</span>

- **校验和**：把分组中的值累加（IP、TCP）。
  - 非常快，即使在软件里计算也便宜。
  - 不太稳健。
- **循环冗余校验（CRC）**：计算一个多项式的余数（以太网）。
  - 比校验和昂贵（如今容易，硬件中容易）。
  - 防护：任何 2 位错误、任何长度 $\le c$ 位的突发、任何奇数个错误。
- **消息认证码（MAC）**：数据的密码学变换（TLS）。
  - 对恶意修改稳健，但对（随机）错误不然。
  - 若算法足够强，任意两条消息有 $2^{-c}$ 的概率得到相同编码。
- **每一层都有属于自己的差错检测：这正是端到端原则！**

至此我们见过了三种差错检测方案。校验和快而便宜，但不够稳健，用于 IP 与 TCP。循环冗余校验强得多：如今在硬件里容易计算，且能检测大范围的错误；以太网这类链路层通常用 CRC。第三种是消息认证码（MAC）：为安全而设计，但也能用于差错检测；由于安全优先，它对恶意修改非常擅长，对（随机）错误的检测则不算特别好。数据差错检测是端到端原则的绝佳例证——事实上正是它最初启发了这条原则：一个层要确保自己通信的数据正确，唯一的办法就是做端到端的检查。以太网需要确保自己的帧无错才能正确解析，所以有 CRC；IP 需要确保自己的分组无错才能正确解析，而 IP **不能**依赖以太网替它把关——以太网卡或驱动可能在检查之后引入错误——所以它必须在网络层做自己的端到端检查；TLS 用 MAC 是又一个例子，而且格外有意思：TLS 的差错检测需求与 IP 或以太网截然不同——它要的是**安全**，所以必须提供属于自己的、端到端的差错检测方案，因为这是确保需求得到满足的唯一办法。
