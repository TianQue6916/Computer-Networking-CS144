### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 1：TCP——传输控制协议</span>

在这个视频中，你将学习 TCP——传输控制协议（Transmission Control Protocol）——提供给应用的服务。互联网上超过 95% 的应用都在使用 TCP。TCP 之所以几乎被普遍使用，是因为它提供了几乎所有应用都想要的可靠、端到端的双向字节流服务。

<span style="color:#7f8c8d;">（Slide 1/15）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 2：TCP 是传输层的例子——数据的封装之旅</span>

TCP 是传输层（transport layer）的一个例子。当应用程序调用 TCP 时，它把一些想要交付到另一端的字节交给 TCP；TCP 把这些字节放进一个 TCP 分段（TCP segment），然后接手后续工作。TCP 把分段交给 IP 层，IP 将其封装（encapsulate）进 IP 数据报（IP datagram），并加上 IP 地址。IP 数据报再被交给链路层（link layer），链路层构建链路帧（frame），加上链路地址——例如以太网（Ethernet）地址——然后把帧发送到线缆上。

<span style="color:#7f8c8d;">（Slide 2/15）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 3：连接——两条单向通道与两端的状态机</span>

当两个应用使用 TCP 时，它们在两端的 TCP 对等体（TCP peer）之间建立一条双向通信通道。首先，TCP 建立一条从 A 到 B 的通信通道，然后建立一条从 B 到 A 的通道。我们把这种双向通信称为"连接"（connection）。在连接的两端，TCP 各自维护一个状态机（state machine），用来跟踪连接的状况。状态机的工作方式将在单独的视频中讲解。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "连接"这个词在 CSAPP 第 11 章里你其实已经用过，只是当时没拆开看：CSAPP 里"一个连接"对应 `accept()` 返回的那个新的已连接描述符，而本讲把它的本质说透了——一条连接就是**两端内核里各自维护的状态机**加上"双向两条通道"的约定。这也解释了为什么 TCP 叫"面向连接"而 IP/UDP 不叫：IP 路由器对任何"连接"一无所知，转发完就忘；UDP 报文发出去就结束；只有 TCP 两端的内核要为这条连接持续记住状态（序列号到哪了、窗口多大、重传什么）。由此还能推出一个 CSAPP 实现视角的结论：`fork()` 处理并发 echo 服务器时，父进程 `accept()` 拿到已连接描述符后交给子进程，本质上是在进程之间共享这条连接的状态机表项——状态在内核，进程只是持有引用。记住"连接 = 两端的状态"，2-6 的 TCP 状态机就是把这些状态画成了一张图。

<span style="color:#7f8c8d;">（Slide 3/15）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 4：三次握手建立连接</span>

TCP 连接通过主机 A 和主机 B 之间的三次握手（three-way handshake）建立。首先，主机 A 向 B 发送一条消息，表明 A 的 TCP 层想与 B 的 TCP 层建立连接。这条消息叫做 SYN 消息，是 synchronize（同步）的缩写——因为 A 还随消息一并发出自己用来标识字节流中各字节的基数（base number）：如果发送"0"，字节编号就从 0 开始；如果发送"1,000"，就从 1,000 开始。随后，B 回复所谓的 SYN + ACK：B 置 ACK 是因为 B 在确认 A 的请求、同意建立从 A 到 B 的通信；同时 B 也向 A 发回自己的 SYN，表示 B 的 TCP 层也想与 A 的 TCP 层建立连接，并附带一个数字，指明反向字节流的起始编号。最后，A 回复一个 ACK，表示接受反向方向的通信请求。此时连接在两个方向上都已建立，双方可以开始互发数据。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 一个值得停下来问的问题：为什么是**三**次握手，而不是两次？从本讲的材料出发可以推导出答案的一半：握手的每一方都要**独立**声明自己的起始编号——A 的 SYN 携带 A 的基数，B 的 SYN 携带 B 的基数——而这两个"声明"还必须各被对方**确认**一次，于是最少需要 SYN、SYN+ACK、ACK 三个报文才能让"双向都同步且都被确认"。另一半原因与可靠性有关：网络会延迟、复制旧报文（2-1 后面一页正好提到分段可能在路由器缓冲里滞留很久），两次握手无法区分"新请求"与"迟到干年前的旧请求"的重复副本，三次握手让最终拍板的 ACK 由发起方在确认对方回应后才发出，旧副本无法单独复活一条连接。所以三次不是经验值，而是"双向同步 + 抗旧报文"两个约束下的最小解。🎥 *McKeown 在视频中解释： "连接在两方都已经设置完毕，他们现在准备好向彼此发送数据"*（字幕来源：023 - p22 2-1 TCP service model.zh.srt）。

<span style="color:#7f8c8d;">（Slide 4/15）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 5：字节流——TCP 眼中只有一串字节</span>

两台主机互发数据时，就像在处理一条连续的字节流。假设时间从左到右增加，A 旁边的字节流表示 A 想发给 B 的字节。这条字节流可以事先就存在——例如从描述静态网页的 HTML 文件中读出；也可以是实时生成的流——例如来自摄像机。无论哪种情况，TCP 看到的都只是一串字节。来自 A 上应用的数据被交付给 B 上的应用；A 和 B 的 TCP 层协同工作，确保字节流正确、按序地交付给 B 上的应用。

<span style="color:#7f8c8d;">（Slide 5/15）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 6：TCP 分段——最小 1 字节，最大 IP 数据报</span>

字节流由 TCP 分段（segment）承载。A 把字节流中的一段字节放进一个 TCP 分段，交给 IP 层，由 IP 交付给 B。B 的 TCP 层从中提取字节，重建字节流，交付给 B 上的应用。实践中，如果分段在路上丢失、或者 A 没收到确认（acknowledgment），同一个 TCP 分段可能需要传输多次。TCP 分段可以小到只有 1 字节——例如你在 ssh 会话中敲字符时，每个字符被单独发送，而不是等整个分段填满。数据量大时这样显然不高效，所以也可以把 TCP 分段一直填到 IP 数据报的最大尺寸。

<span style="color:#7f8c8d;">（Slide 6/15）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 7：拆除连接——FIN 与半关闭</span>

当 A 和 B 都发完数据后，它们需要关闭连接。我们说它们"拆除"（teardown）连接：互相告知要关闭了，然后两端都可以清理与状态机关联的状态。主机 A 的 TCP 层通过发送 FIN 消息来关闭连接，FIN 是 FINISH（结束）的缩写。主机 B 确认 A 不再有数据要发送，并停止从 A 接收新数据——这就关闭了从 A 到 B 的数据流。但 B 可能仍有新数据要发给 A，还没准备好关闭从 B 到 A 的通道；所以 B 发往 A 的携带 ACK 的消息可以同时携带 B 的新数据，B 想发多久都可以。稍后，B 发完数据，也发出自己的 FIN 告诉 A 可以关闭连接。主机 A 回复 ACK，确认连接关闭。两个方向都结束后，连接才被完全关闭，状态可以安全移除。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这段是"半关闭"（half-close）机制的第一次正式亮相，而它正好对应你在 CSAPP 里敲过的 `close()` 语义的一个微妙细节：`close()` 关闭的是**描述符**（这一端不再发送），并不自动意味着"对端也没有数据了"。TCP 把"我没有数据要发了"（FIN）和"我不再收数据了"（完全关闭）设计成两个独立的方向，于是出现了一方发完 FIN、另一方仍可以继续发送的状态——典型场景是客户端发送查询后关闭自己这侧，服务器把余下的大量结果发完才关闭。CSAPP 第 11 章提到过 `shutdown()` 与 `close()` 的区别：`shutdown(fd, SHUT_WR)` 只关写方向且会触发 FIN，`close()` 则受引用计数影响（fork 出的子进程持有副本时不发 FIN）——现在你知道这些系统调用各自精确地对应状态机里的哪条边了。🎥 *McKeown 在视频中解释： "这关闭了从 A 到 B 的数据流。但 B 可能仍然有新数据要发送给 A，并且还不准备好关闭从 B 到 A 的通道"*（字幕来源：023 - p22 2-1 TCP service model.zh.srt）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 8：TCP 提供的服务总表</span>

下表总结 TCP 提供的服务。前三项是 TCP 提供给应用的服务：它在两个应用之间提供可靠的字节流。TCP 用四种机制使通信可靠——换句话说，确保数据被正确交付：

1. TCP 层收到数据时，向发送方回送一个确认（ACK），让对方知道数据已正确到达。
2. 校验和（checksum）检测损坏的数据。TCP 首部携带一个覆盖首部与段内数据的校验和，用于发现分段在途中是否被损坏——例如线路上的位错误（bit-error），或路由器内部的内存故障。
3. 序列号（sequence number）检测丢失的数据。每个分段的头部携带该段第一个字节在字节流中的序列号。例如双方约定序列号从 1,000 开始，则第一段的序列号是 1,000；若该段携带 500 字节数据，下一段的序列号就是 1,500。如果某段丢失，序列号就会对不上，TCP 层由此知道有数据缺失。缺失的数据可能稍后出现——也许它绕了一条更长的路径——也可能真的丢了，此时发送方需要重传。
4. 流量控制（flow-control）防止淹没接收方。如果主机 A 远快于主机 B，A 可能发送得过快以致 B 来不及处理。TCP 用流量控制防止这种情况：接收方不断告诉发送方是否还能继续接收——具体地说，告诉发送方自己缓冲区（buffer）里还有多少空间可容纳新数据。如果 B 落后了，空间就会下降，甚至降到零；等有了空间，B 再告诉 A，A 才能继续发。

TCP 按正确顺序把数据交付给应用：数据从 A 的应用交给 A 的 TCP 时是什么顺序，从 B 的 TCP 交给 B 的应用时就是什么顺序。如果分段乱序到达，TCP 层用序列号把它们重新排回正确顺序。

最后，TCP 通过控制拥塞（congestion）为整个网络提供服务：TCP 尝试在使用网络的所有 TCP 连接之间公平地划分网络容量。TCP 的拥塞控制机制非常复杂，Unit 4 将用整整一个单元来学习。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这张"服务契约表"值得用第一性原理重读一遍：前四条机制其实各自回答一个独立的问题——确认回答"对方知道我发到了吗"，校验和回答"数据坏了吗"，序列号回答"丢了吗、顺序对吗"，流量控制回答"对方还接得住吗"。注意第 2 条与第 3 条的分工：校验和只管**内容损坏**，序列号只管**缺失与乱序**，二者不可互相替代——数据"丢失"时校验和根本无事可做，数据"损坏"时序列号也无能为力。🎥 *McKeown 在视频中解释： "校验和在那里是为了检测，如果段在途中被损坏，例如，由于电线上的微小错误或路由器内部的内存故障"*（字幕来源：023 - p22 2-1 TCP service model.zh.srt）。另一个容易混淆的点：流量控制和拥塞控制都叫"控制"、都限制发送速率，但保护对象完全不同——前者保护**接收端主机**（缓冲区溢出），后者保护**网络本身**（路由器队列溢出）。本讲只交代了前者；后者要等 Unit 4，届时你会发现两者最终作用于发送端的同一个"在途字节上限"，但反馈信号一个来自对端（接收窗口），一个来自网络（丢包/时延）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 9：TCP 首部重要字段速览</span>

TCP 分段的头部比 IP 或以太网头部要长得多、复杂得多。这是因为 TCP 连接是可靠的——要让通信可靠，连接两端需要交换更多信息，才能知道哪些字节已到达、哪些缺失，以及连接的状态。这里快速总结 TCP 头部最重要的字段。你不需要记住头部的布局，但应当弄清每个字段的作用。需要参考时，推荐 Wikipedia 或 Kurose 与 Ross 的教科书。

**目的端口（destination port）**：告诉对端的 TCP 层这些字节应交付给哪个应用。新连接启动时，应用告诉 TCP 要与哪个服务建立连接。例如 TCP 承载 Web 数据时使用端口 80。端口号后面还会细讲，好奇的话可以在 IANA 网站查询知名端口号（搜索 IANA port numbers），那里定义了数千个不同知名服务的端口。例如连接 ssh 服务器用目的端口 22；SMTP（简单邮件传输协议，simple mail transfer protocol）按本讲讲稿的说法使用端口 23。使用知名端口号，主机 B 就能识别应与哪个应用建立连接。

**源端口（source port）**：告诉对端的 TCP 层应该往哪个端口把数据发回来。在本例中，主机 B 回复主机 A 时，应把 A 的源端口号填入目的端口字段，这样 A 的 TCP 层才能把数据交给正确的应用。新连接启动时，连接的发起方（这里是主机 A）生成一个唯一的源端口号，以区别于 A 与 B 之间到同一服务的其他连接。

**序列号（sequence number）**：指出 TCP 数据字段中第一个字节在字节流中的位置。例如初始序列号（initial sequence number）为 1,000 且这是第一段，则序列号为 1,000；若该段长 500 字节，下一段的序列号就是 1,500，依此类推。

**确认号（acknowledgment sequence number）**：告诉对方我们期望的下一个字节是哪个；同时也表明：到该编号之前（不含该编号）的每个字节我们都已成功收到。例如确认序列号为 751，意味着到 750 为止（含 750）的每个字节都已收到。注意每个分段中都同时有两个方向的序列号——TCP 以这种方式把确认"捎带"（piggyback）在反向传输的数据分段上。

**校验和（16 位 checksum）**：对整个头部与数据计算，帮助接收方发现损坏的数据——例如线路上的位错误，或路由器中故障的内存。差错检测与校验和将在后面的视频详细学习。

**首部长度（header length）**：指出 TCP 头部有多长。**TCP 选项（options）**字段是可选的，承载 TCP 标准制定之后才想到、才添加的额外新头部字段；首部长度字段告诉我们有多少个选项字段。通常没有任何选项。

最后是一组**标志位（flags）**，用于从连接一端向另一端传递信号：ACK 标志表示确认序列号有效、到该处为止的数据都得到确认；SYN 标志表示我们在发"同步"信号，是三次握手的组成部分；FIN 标志表示关闭连接的一个方向；PSH 标志要求对端的 TCP 层在数据到达后立即交付，而不是等待更多数据——这对承载时间敏感数据的短分段很有用，比如键盘按键：我们不希望 TCP 层为了攒满一段而推迟把按键交付给应用。

> <span style="color:#7f8c8d;">译注：讲稿原文称 SMTP 使用端口 23——此处为讲稿笔误：23 是 Telnet 的端口，SMTP 的知名端口是 25。按原文如实译出，特此说明以免误导。</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 10：连接的五元组标识与随机初始序列号</span>

一条 TCP 连接由 TCP 与 IP 头部中的五项信息唯一标识：IP 源地址与目的地址唯一确定两个端点，IP 协议号（protocol ID）标明这是 TCP 连接，TCP 源端口与目的端口标识两端主机上的应用进程。这 5 个字段合起来，在任一时刻在整个互联网范围内唯一标识这条 TCP 连接。

不过，这个"唯一性"只在若干条件下成立。首先，必须保证主机 A——连接发起方——选择的源端口是唯一的：不能碰巧选中它已用于与主机 B 上同一服务的另一条连接的源端口号。A 用一个简单方法把撞号概率降到最低：每建立一条新连接就把源端口号递增 1。该字段是 16 位，因此要建立约 64K 条新连接后编号才会回绕（wrap round）。仍然存在一点风险：如果 A 突然创建大量到 B 的新连接，编号可能回绕，并试图创建两条全局标识相同的连接。一旦发生，一条连接的字节就可能同另一条连接的字节混淆——例如某个 TCP 分段因滞留在路由器缓冲或陷入临时环路而在网络中存活了很久时，就可能出这种事。为降低混淆的概率，TCP 连接用一个**随机**的初始序列号来指代字节流中的字节：这并不完全万无一失，但确实能降低混淆概率。当 A 向 B 发起连接时，它带上自己将从 A 到 B 方向使用的初始序列号；B 回复并发起从 B 到 A 方向的连接时，则带上自己为该方向选定的初始序列号。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 五元组（源 IP、源端口、目的 IP、目的端口、协议号）你在 CSAPP 已经见过它的实现形态：内核的套接字表就是按五元组索引的哈希表，`accept()` 的匹配规则正是"先找精确五元组、再退回通配监听套接字"。这里值得算一笔概率账：源端口"递增法"确保短时间不撞号，但序列号回绕的问题更隐蔽——若两次连接都从 0 开始编号，网络里一条活了很久的旧分段就能带着"合法"的序列号混入新连接。随机初始序列号把两个不同连接的字节编号空间错开：设想编号是 32 位，一条旧分段恰好落进新连接当前窗口且校验和也通过的概率，粗略估计要乘上一个 $2^{-32}$ 量级的因子——按每秒处理 $10^6$ 个旧分段算，期望等待时间也在天量级（这正是概率论里"小概率事件在大量试验下的期望等待时间"的直接应用）。注意讲稿说得很克制：随机 ISN "并不完全万无一失"，它只是把冲突概率压到工程上可忽略——安全领域后来还发现可预测的 ISN 会被用于伪造连接（序列号攻击），那是 2-5 之外又一个"随机性换安全"的例子。

<span style="color:#7f8c8d;">（Slide 10/15）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 11：序列号工作机制小结</span>

总结一下序列号的工作方式：从 A 发往 B 的分段中，其序列号是"该段第一个字节的编号"，再偏移（offset）A 的初始序列号；从 B 发回 A 的分段中，确认序列号告诉我们 B 期望的下一个字节是哪个——同样按 A 的初始序列号偏移。

<span style="color:#7f8c8d;">（Slide 11/15）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Slide 12：端口号工作机制举例</span>

设想右边的主机 B 提供两项服务：Web 服务器和邮件（Mail）服务器。当 Web 客户端——例如主机 A 上的 Chrome 浏览器——想向 B 上的 Web 服务器请求一个页面时，它把数据交给 TCP。假设 TCP 已与 B 建立连接，现在只需发送数据：它创建一个分段，用目的端口 80 告诉 B 这份数据要交给 Web 服务器；同时 A 使用一个本地生成的源端口号，供 B 在回传数据和确认时使用。照例，TCP 分段被封装进 IP 数据报发往 B，IP + TCP 头部承载着这条 TCP 连接的唯一标识。IP 数据报到达 B 后，TCP 分段被取出；B 的 TCP 层看到该分段目的地是端口 80，就把数据交给 Web 服务器。
