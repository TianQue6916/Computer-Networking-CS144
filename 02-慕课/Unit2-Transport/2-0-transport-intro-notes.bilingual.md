### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Phil：本单元概览</span>

在这一单元中，我们将深入传输层（transport layer）。回想一下，<span style="color:#00838f;">传输层为应用程序之间的数据通信提供服务。</span>这种数据通信，在 UDP 的情况下可以是简单的、不可靠的数据报（datagram），在 TCP 的情况下则是可靠的双向字节流（reliable bidirectional byte stream）。你将学习这些传输层是如何工作的——它们的抽象（abstraction）与算法。你还将学到一条新的网络原则，叫做"端到端论断"（end-to-end argument）或端到端原则（end-to-end principle），它规定了你应当如何以及在何处实现某个功能，才能保证系统正确。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 传输层是四层模型中最贴近你编程经验的一层：在 CSAPP 第 11 章里，你写的每一个网络程序——无论是 echo 服务器还是 tiny Web 服务器——调用的 `socket()`/`connect()`/`read()`/`write()`，背后其实都是在与内核的传输层打交道：`SOCK_STREAM` 要到的就是 TCP 这套"可靠双向字节流"，`SOCK_DGRAM` 要到的则是 UDP 的"不可靠数据报"。当时 CSAPP 只告诉你这些调用能用，没有展开内核里究竟发生了什么；本单元正是要打开这个黑盒——三次握手、序列号、确认、重传、校验和，全部发生在两台主机的内核之间。还有一个拓扑上的关键事实：路由器只需要实现到网络层为止，它既不理解也不关心 TCP 的确认与重传。这使得传输层成为协议栈中第一个真正"活在整个路径两端"的层，也为本单元稍后的端到端原则埋下了伏笔。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Nick：本单元将回答的问题</span>

在这一单元中，我们将提出并回答这样一些问题："TCP 究竟是如何建立连接的？""TCP 分段（segment）长什么样？""两台计算机如何以高性能可靠地传输数据？"要可靠地传输数据，TCP 需要知道数据何时被损坏了——你将学习用三种算法来检测数据差错：校验和（checksum）、循环冗余校验（cyclic redundancy check，CRC）与消息认证码（message authentication code，MAC）。你还将学到网络协议设计的一种基本工具与方法——有限状态机（finite state machine，FSM），并逐项走过 TCP 所用状态机的全部细节。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> Nick 一口气报出的三个算法名词，其实是同一场博弈里的三种不同取舍：把 $n$ 比特的消息"蒸馏"成 $c$ 比特的校验信息。用你正在学的概率论语言说，任何把 $n$ 比特映射到 $c$ 比特的函数都必然有碰撞——随机两条消息撞出同一校验值的概率约为 $2^{-c}$，所以"检测能力"本质上是"用多少比特买多少检测保证"。三种算法的差别不在"快慢"与"强弱"的排序本身，而在**保证的结构**：校验和几乎不打任何包票；CRC 对特定错误类别（奇数个错、恰好两位错、长度不超过 $c$ 的突发）给出确定性保证；MAC 则根本不为随机错误设计、而为对抗恶意篡改设计。🎥 *McKeown 在视频中解释： "你将学习如何使用三种不同算法来检测数据错误：校验和、循环冗余检查和消息认证代码"*（字幕来源：022 - p21 2-0 Transport (intro).zh.srt）。2-5 会把这三种保证逐格填满，"保证"与"大概率"的区别正是那一讲的核心考点。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 有限状态机对你应该毫不陌生：6.042J 把"系统 = 状态 + 转移"当作贯穿全程的思想，图论部分你也已经在有向图上做过大量"给定起点，沿边行走"的推演。协议设计借用的正是同一套语言：状态是"系统此刻的全部记忆"（对 TCP 而言，比如"已发出 SYN、还没收到回应"），边由事件（收到某个报文、程序调用某个系统调用）触发，边上还可以挂动作（发送某个报文）。这套表示最大的好处是可以机械化地推理：任何一个报文到达序列，都对应状态图上一条确定的路径，正确性论证因此可以像 6.042J 的归纳证明一样按步进行——"若当前处于合法状态，则任何合法事件之后仍处于合法状态"。2-6 你会看到，TCP 规范的核心就是一张 12 个状态的状态图，"协议是什么"最终被还原为"这张图长什么样"。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Phil：学完本单元你将掌握什么</span>

到本单元结束时，你将完全理解 TCP 如何可靠地传输数据，以及为此如何建立连接。我们暂不讨论如何把 TCP 设计得跑得非常快——那要等到 Unit 4 才讲；本单元讲的是它如何跑得相当好，以及最重要的——如何跑得**正确**。你还将掌握 UDP 的全部细节，以及 ICMP（互联网控制消息协议，Internet Control Message Protocol），它在互联网中承载差错通知这类控制信息。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "先保证正确、再优化性能"这个次序值得单独强调，因为它与你在 CSAPP 中经历过的路径完全同构：CSAPP 前几章把 C 程序的语义（正确性）讲透，性能工程是后面的事，而且优化的大前提始终是"不改变程序可观察行为"。网络协议更是如此——重传、超时这些"让数据变快恢复"的设计，一旦与正确性冲突，代价就不只是慢，而是把损坏的数据当正确数据接受，这种错误在支付、存储场景是不可接受的。所以 Unit 2 把正确性部件（差错检测、可靠传输、连接管理）一次讲完，Unit 4 才回头处理"快"（拥塞控制）。做 Lab 时也建议沿用这个次序：先让重组器、接收端在小规模测试上严格正确，再谈吞吐——先跑对，再跑快，返工成本最低。
