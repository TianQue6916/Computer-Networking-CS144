# CS144: Introduction to Computer Networking（计算机网络导论，Stanford Fall 2019）

## <span style="color:#2471a3;">**[lecture]**</span> <span style="color:#c0392b">Transport Layer Security（传输层安全，TLS）</span>

> <span style="color:#7f8c8d;">副标题：RFC5246: you use it every day（RFC5246：你每天都在用）</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b">Slide 2 · 传输层安全（Transport Layer Security）</span>

- TLS 是架在 TCP 之上的 secure session layer（安全会话层）：
  - 提供与 TCP 相同的 stream abstraction（字节流抽象）；
  - 在其上叠加机密性（confidentiality）、完整性（integrity）、真实性（authenticity）。
- 最新版本是 TLS 1.2（RFC5246）；其前身是 Netscape 公司的 Secure Socket Layer（SSL，安全套接字层）。
- HTTPS 在使用它（浏览器地址栏上的锁）。

图示：分层栈——Application（应用层）/ Session (TLS)（会话层）/ Transport（传输层）/ Network（网络层）/ Link（链路层）/ Physical（物理层）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b">Slide 3 · 该用哪些密码（What Ciphers to Use）</span>

一个 TLS 会话要协商四种 cipher（密码算法）：

- 用于服务器认证（可选客户端认证）的密码：RSA、DSS；
- 用于 key exchange（密钥交换）的密码：RSA、DHE；
- 用于对称机密性的密码：RC4、AES、DES；
- 用于完整性的密码：HMAC-MD5、HMAC-SHA。

这些算法在一个 5 步的会话发起协议（session initiation protocol）中协商完成。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 为什么要"协商"而不是定死一套算法？历史原因是 1990 年代美国把强加密当军用品管制出口，SSL 被迫支持故意削弱的 40 位 export ciphers（出口级密码），协商机制因此保留下来。这成了密码学史上一堂昂贵的课：2015 年的 FREAK 与 Logjam 攻击证明，只要服务器还保留着弱算法支持，中间人就可以把协商结果篡改降级（downgrade）到出口级密钥，再用现代算力硬破 40/512 位的弱密钥——"曾经支持过的弱东西"本身就是攻击面。这个设计模式叫 algorithm agility（算法灵活性）：优点是某个算法被攻破后可平滑升级，缺点是协商消息本身成了可篡改的目标，必须把协商内容纳入后续的完整性保护（TLS 正是用握手消息的 MAC 作为最后两步来兜底）。你在 8-3 讲见过的 BGP"没有验证的灵活性"，在这里换上了密码学的马甲。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b">Slide 4–9 · TLS 密码协商（TLS Cipher Negotiation）</span>

这六页是同一次握手消息流的逐步展开（client 在左、server 在右，每页新增一条消息）：

1. （Slide 4–5）Client → Server：supported ciphers（支持的密码套件列表）与 client random（客户端随机数）——not confidential（不保密，明文传输）；
2. （Slide 5–6）Server → Client：chosen ciphers（选定的密码套件）、server random（服务器随机数）与 certificate（证书）——同样明文；
3. （Slide 6–7）Client → Server：encrypted pre-master secret（加密的预主密钥），用服务器的公钥加密；此时双方各自 compute keys（计算会话密钥）；
4. （Slide 7–8）Client → Server：MAC of handshake messages（握手消息的 MAC），用会话密钥加密；
5. （Slide 8–9）Server → Client：MAC of handshake messages，同样用会话密钥加密——握手闭环。

设计逻辑：前两条消息公开（算法选择与双方随机数）；第三条用公钥加密传秘密（预主密钥）；最后两条用新会话密钥验证整个握手未被篡改——把"协商了什么"也锁进完整性保护里。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b">Slide 10 · TLS 消息格式（TLS Message Format）</span>

- TLS 把应用层的字节流切成 record（记录）：长度 1–$2^{14}$ 字节；记录会被压缩（默认压缩算法是 null，即不压缩）；
- 记录通过 TCP 流发送（再被切成 segment 分段等）。

图示：应用层（如 HTTP）的字节流 → TLS 记录 → TCP 分段的封装关系示意（record 与 segment 交错出现，展示分层的多对多关系）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b">Slide 11 · 建立会话密钥（Establishing Session Keys）</span>

- 客户端与服务器双方都贡献随机数（randomness）；
- 客户端发送 pre-master secret（预主密钥），用服务器的公钥加密；
- 由随机数与预主密钥生成 master secret（主密钥）；
- 再由主密钥与随机数生成 session keys（会话密钥）：
  - Client to server write (encryption)（客户端→服务器写加密密钥）；
  - Client to server MAC；
  - Server to client write (encryption)；
  - Server to client MAC；
  - Client initialization vector（客户端初始向量）与 Server initialization vector；
- 支持会话恢复（resuming sessions）：复用同一 master secret，但生成新密钥。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b">Slide 12 · 会话密钥细节（Session Key Details）</span>

图示（数据流）：Client Random 与 Server Random 连同 48 字节的 Premaster Secret 一起送入 PRF（pseudo-random function，伪随机函数），得到 48 字节的 Master Secret；Master Secret 再经一次 PRF 展开出全部会话材料：Client/Server write 密钥、Client/Server MAC 密钥、Client/Server IV。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b">Slide 13–14 · 测验（Quiz）</span>

> <span style="color:#2471a3;">**[question]**</span> （测验题，保留英文原文；两页重复展示同一道题）TLS random values are 32 bytes long (a 4 byte timestamp and 28 bytes of randomness). The premaster secret is 48 bytes long, 2 bytes of protocol version and 46 bytes of randomness. The master secret is 48 bytes long.

> Suppose your TLS session uses these to generate 128 bytes of keys. What is the maximum number of tries an adversary might have to make to crack the session keys, assuming an exhaustive attack? Assume that the adversary can correctly recompute the output of a pseudo-random function from its input and it knows what version of TLS is being used.

> Write your answer as the base-2 exponent (i.e., if it would take $2^{31}$ tries, write 31).

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 译者补解：答案是 $2^{368}$（填 368）。关键是分清"哪些输入是秘密"：client random（28 字节随机 + 4 字节时间戳）与 server random 在握手时明文传输；协议版本号公开；题目又声明对手可以正确重算 PRF、也知道 TLS 版本——于是全部熵只来自 premaster secret 中未公开的 46 字节随机数，即 $46 \times 8 = 368$ 位。穷举攻击者逐个枚举 premaster 候选，对每个候选按确定性的 PRF 重算 master secret 与 128 字节会话密钥，再用记录层密文验证猜测，所以最大尝试次数是 $2^{368}$。这道题的教学点非常锋利：会话密钥虽有 128 字节（1024 位），安全强度却由熵最弱的输入决定——把 1024 位输出"吹"出来并不能凭空制造熵。这与 8-7 讲的 computational security 一脉相承：安全参数等于"最小熵源"，而不是"输出长度"。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b">Slide 15 · 分层的代价（The Costs of Layering）</span>

- TLS 握手发生在应用数据交换之前；
- Virtual hosts（虚拟主机）让一台 Web 服务器对映射到同一 IP 地址的不同主机名给出不同响应：
  - Host: sing.stanford.edu；
  - Host: tinyos.stanford.edu。
- 这可能破坏 TLS——怎么破坏的？受影响的环节：服务器认证（server authentication）、密钥交换（key exchange）、随机数生成（randomness generation）、握手消息的路由（routing handshake messages）、预主密钥生成（premaster secret generation）。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 图中的问号就是著名的"TLS 虚拟主机问题"：证书在握手的第 2 步就要出示，而决定"用哪张证书"的 Host 头是 HTTP 内容，要等握手结束才能加密传输——先有鸡还是先有蛋。工业界的补丁是 SNI（Server Name Indication，RFC 6066）：客户端在 ClientHello 里明文带上想要的主机名，服务器据此选证书。但它把域名以明文重演了一遍——审查者与广告商都能读到你要访问的站点，违反了 TLS 自己的机密性初衷；现代修复是 ECH（Encrypted Client Hello，2023 年起在主流浏览器与 Cloudflare 部署），用外层公共名（共享证书）加密内层 SNI。回看课程主线：这是 layering（分层）代价的又一实例——信息出现在"错误的层"，上一页虚拟主机的便利与本页服务器认证的安全需求在分层边界上直接冲突，每次修复都是在分层架构上再贴一层补丁。
