### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">David D. Clark 与互联网的架构原则</span>

- David D. Clark：1981–1989 年互联网的 chief protocol architect（首席协议架构师）。

**Architectural Principles（架构原则）：**

1. <span style="color:#00838f;">网络核心要 dumb and simple（哑而简单）：精简、快速、低成本、易维护、升级不频繁。</span>
2. <span style="color:#00838f;">可靠的按序交付可以构建在其上、在 end-points（端点）处完成：端点是智能的（计算机）。</span>
3. <span style="color:#00838f;">decentralized control（去中心化控制）：带来快速的 organic growth（有机增长）。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> Clark 的三条原则是理解整个互联网的钥匙，也和 CSAPP（Computer Systems: A Programmer's Perspective，《深入理解计算机系统》）呼应最深。第一条"哑核心"与第二条"智能端点"合起来就是 end-to-end principle（端到端原则）：网络只做一件事——尽力转发数据报；可靠按序交付由端点的 TCP 完成。你在 CSAPP 第 11 章的 socket（套接字）编程里已经站在这个设计的上层：connect/listen/accept 这些调用背后，是两台"智能端点"用 three-way handshake（三次握手）自建的可靠字节流，网络核心对此一无所知。fate sharing（命运共享）是同一思想的另一种表述：把与一条连接相关的所有状态（序列号、缓冲区）放在连接的两端，端挂了连接自然该终结，网络无需替它善后——这比把状态散布在中间路由器上健壮得多。第三条"去中心化控制"则解释了互联网为何能避开标准化机构的官僚流程：没有中央权威审批你的新应用。这三条在 1981–1989 年由 Clark 总结成文，其影响一直延续到今天关于 SDN（软件定义网络）的争论里。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Edsger Dijkstra（1930–2002）</span>

- 照片页（摄影师：Hamilton Richards）。
- 其著名算法（伪代码保留原文）——即 Dijkstra 最短路径算法：给定一个带权图和起点，算出起点到其余所有顶点的最短路径（single-source shortest paths，单源最短路径），路由器在掌握全网拓扑后正是用它来计算转发路径：

```
function Dijkstra(Graph, source):
    for each vertex v in Graph:
        dist[v] := infinity ;
        previous[v] := undefined;
    dist[source] := 0 ;
    Q := the set of all nodes in Graph ;
    while Q is not empty:
        // The main loop
        u := vertex in Q with smallest distance in dist[] ;
        remove u from Q ;
        if dist[u] = infinity:
            break ;
        for each neighbor v of u:
            alt := dist[u] + dist_between(u, v) ;
            if alt < dist[v]:
                dist[v] := alt ;
                previous[v] := u ;
                decrease-key v in Q;
    return dist[], previous[];
end function
```

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">路由器的两步工作</span>

- 转发规则示例（幻灯片原文引语，协议/引文保留原文）：

```
"If a packet is going to B, then send it to output 3"
```

（含义：如果分组要去 B，就把它从 3 号输出发出。）
- control plane（控制面）的两步：
  1. 弄清哪些路由器和链路存在；
  2. 运行 Dijkstra 算法寻找最短路径。
- 图示：data plane（数据面）只查表转发（占流量的约 95%），control plane（控制面）计算路由（约 5% 的"脑力"）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">构建可靠的分布式系统真的很难</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">到 2005 年为止（By 2005）</span>

- 互联网路由器非常复杂：超过 1 亿行源代码。
- 它们是封闭且专有的、vertically integrated（垂直集成）、昂贵的。
- 作为"一个网络"来管理或控制非常困难：没有干净的 API（Application Programming Interface，应用程序编程接口）。
- ISP（互联网服务提供商）感觉被路由器制造商"扼住了咽喉"（stranglehold）。
- 互联网研究社区感到沮丧：
  - 互联网已经 ossified（僵化）；
  - 发明新想法容易；但测试和部署很难。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">两股并行趋势（Two Parallel Trends）</span>

1. **研究社区**
   - 新项目：Clean Slate Program（白板计划）、NSF（National Science Foundation，美国国家科学基金会）项目；
   - 新研究：质疑封闭生态；
   - 新交换机 API（应用程序编程接口）：OpenFlow（开放流协议）；
   - 新开源项目：控制平面、交换机、模拟器。
2. **网络产业**
   - 数据中心的兴起：Linux 的兴起、merchant switch chips（商用交换芯片）的出现、disaggregation（分解化）；
   - ISP（互联网服务提供商）承压：消费价格下跌、需要差异化。

<span style="color:#00838f;">**总而言之：控制权需要从设备厂商手中，转移到网络拥有者与运营者手中。**</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">例：数据中心拥有者（Data Center Owner）</span>

- **Cost（成本）：**
  - 500,000 台服务器；25,000 台交换机；
  - \$10k/台 = \$2.5 亿；\$2k 的商用交换机 = \$5000 万；
  - 5 个数据中心合计节省 \$10 亿。
- **Control（控制）：**
  - 更灵活的流量控制；按需定制网络；快速改进与创新。
  - 例如：Google 的 B4 广域网（B4 是 Google 用软件定义方式集中调度的骨干广域网）利用率从 50% 提升到 95%。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这页的算术值得逐行读：同样 25,000 台交换机，专有设备 \$10k 一台要 \$2.5 亿，商用白盒 \$2k 一台只要 \$5000 万——五个数据中心就省下 \$10 亿。这不是普通的采购折扣，而是 disaggregation（分解化）的结构性后果：把软件（控制面）从硬件（转发芯片）剥离后，硬件变成标准化商品，竞争把它推向成本价；软件则变成用户自己的资产，可以按需迭代。Google B4 从 50% 到 95% 的链路利用率是另一维度的收益——传统网络按最坏情况预留带宽，集中调度能把"平均浪费"挤出来；对按带宽计费的广域网专线而言，利用率翻近一倍等于链路成本近乎减半。下一页 ISP 的剪刀差同理：流量年增 50% 而收入持平，唯一出路就是让单位成本下降速度追上流量增速。经济与技术的这对合力，正是末页"不可逆"判断的底气。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">例：互联网服务提供商（ISPs）</span>

- 全球 IP 流量每年增长 50%；
- 终端客户的月账单保持不变（\$30/月）；
- 因此，拥有成本需要每年、每 Gb/s 下降 50%；
- 但实际上每年下降不到 20%。
- 图示：收入（revenue）与总成本（total cost）随时间发散的剪刀差曲线。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">2006 年的研究社区</span>

1. 斯坦福 Clean Slate Program（白板计划）："如果我们（把互联网）从头再来一次，我们会怎么做？"
2. Martin Casado 与 Ethane 项目（Ethane 是斯坦福一个用集中式控制器管理网络的研究项目，是 SDN 的直接前身）。

**Ethane 要回答的问题：**

<span style="color:#00838f;">**在 datapath（数据通路）之外、用软件来定义所有网络操作，究竟有多难？**</span>

- 2006 年的斯坦福校园网规模：35,000 名用户；每秒 10,000 条新流；137 条网络策略；2,000 台交换机；2,000 个交换机 CPU。

**一个"疯狂"的问题：** 如果由软件来决定是否接受每一条流、以及如何路由它呢？

- controllers（控制器）：
  1. 按策略检查每条流；
  2. 为它挑选路由。
- （发表于 [Sigcomm '07, Kyoto]）
- 35,000 名斯坦福用户需要多少台 \$400 的服务器？**答案：不到一台！**

<span style="color:#00838f;">**"如果我们能在 datapath（数据通路）之外定义网络行为，那么最终我们就会这么做。"**</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "不到一台服务器"这个回答看似玩笑，其实是整套 SDN（软件定义网络）可行性的论证核心：集中式决策之所以付得起，是因为决策只发生在每条流的第一个包上——判决结果以 flow table（流表）形式下发到交换机硬件，之后的亿万分组走快路径，根本不再打扰控制器。这与 CPU 的异常处理模型异曲同工：慢路径只在事件首次出现时介入，快路径靠硬件缓存/表项撑住稳态流量。把控制逻辑从 2,000 台交换机的分布式协议搬进一台服务器的普通程序，还带来软件工程上的质变：路由策略变成了可以版本控制、单元测试、回滚的代码，而不是散落在亿级设备固件里的神秘状态机。Ethane（2006）是 SDN（软件定义网络）的直接前身，OpenFlow（开放流协议，2008）则是它标准化后的接口。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">软件定义网络（Software Defined Network, SDN）</span>

- 架构图：
  - 上层：Control Program（控制程序）们；
  - 中间：Network OS（网络操作系统）维护 Global Network Map（全局网络映射）；
  - 接口：OpenFlow（开放流协议）；
  - 下层：各交换机的 Packet Forwarding（分组转发）数据面。
- 在网络操作系统之上，Dijkstra、IS-IS（Intermediate System to Intermediate System，中间系统到中间系统协议）、BGP（Border Gateway Protocol，边界网关协议）、MPLS（Multiprotocol Label Switching，多协议标签交换）、防火墙……都只是可以运行（或替换）的普通程序。

- 随之迅速出现：OpenFlow（开放流协议）、SDN（软件定义网络）、Open vSwitch（开源虚拟交换机）、network virtualization（网络虚拟化）……
- 2005 年，每个数据中心和 ISP（互联网服务提供商）都是用封闭、专有的路由器构建的。
- 今天，前 10 大数据中心拥有者全部自己构建交换机、并编写自己的软件（或使用开源）。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> SDN（软件定义网络）的核心动作只有一个：把"决定往哪转发"（控制面）与"执行转发"（数据面）之间的接口标准化成 OpenFlow（开放流协议）——就像 x86 指令集把软件与 CPU 解耦一样。理解它最快的类比来自你熟悉的计算机体系：Windows/Linux 生态之所以繁荣，是因为应用与硬件之间有干净的操作系统抽象；2005 年前的网络里没有这一层——每台路由器把控制逻辑和转发硬件焊死在一个黑盒里，ISP 想改一个路由策略都要等厂商发版。"全局网络映射"是概念上最大的跳跃：控制器维护全网拓扑，Dijkstra 算法与 BGP（边界网关协议）降级为运行在网络操作系统上的普通程序，可替换、可组合、可测试——你甚至可以在仿真里先跑一遍再上线。控制面与数据面的分离自此成为数据中心的默认架构，这也是你以后读到 AWS/Google 数据中心论文时通用的词汇。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">类比：计算机产业与网络产业的解耦</span>

- **Computer Industry（计算机产业）：**
  - 专用 apps（应用）+ 专用操作系统（Windows 或 Linux 或 Mac）+ 专用硬件（微处理器）；
  - 关键在于两个 **open interface（开放接口）**：应用↔OS、OS↔微处理器——正因解耦，三个层次各自繁荣。
- **Networking Industry（网络产业）正在复制这条路：**
  - 专用特性 + 控制面框架（NOX、Beacon、ONIX、POX、ONOS、Trema、ODL、Ryu）+ switch chips（交换芯片）；
  - 两个 open interface（开放接口）：控制程序↔网络 OS、网络 OS↔交换芯片。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">网络功能虚拟化（Network Function Virtualization, NFV）</span>

- 以前：公共互联网路径上插着一堆专用 middlebox（中间盒）：firewalls（防火墙）、load-balancing（负载均衡）、NAT（Network Address Translation，网络地址转换）、boundary routers（边界路由器）、DPI（Deep Packet Inspection，深度包检测）、DDoS（Distributed Denial of Service，分布式拒绝服务）缓解——每个都是专有硬件盒子。
- NFV（网络功能虚拟化）之后：这些功能变成运行在通用服务器上的 VM（虚拟机），分组转发仍然留在快速路径上。

- 回头看，**分解化、SDN 与 NFV 是必然的**：这是更大趋势的一部分——网络的拥有者与运营者接管"网络如何工作"的控制权。

- 必然，是因为：
  1. Linux 的兴起；
  2. baremetal servers（裸金属服务器）与数据中心的兴起；
  3. SDN（软件定义网络）：merchant switch chips（商用交换芯片）的兴起；
  4. NFV（网络功能虚拟化）：计算机虚拟化的兴起。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> NFV（网络功能虚拟化）与 SDN（软件定义网络）是互补的两步：SDN（软件定义网络）把转发本身变成可编程的，NFV（网络功能虚拟化）把"挂在网络路径上的专用盒子"middlebox（中间盒）变成通用服务器上的软件。防火墙、NAT（网络地址转换）、负载均衡、DPI（深度包检测）在 2000 年代都以昂贵专有硬件的形式存在，各自垂直集成、难以扩容，还把网络拓扑切得七零八落。把它们装进 VM（虚拟机）后，"一个防火墙"变成"一段可以像应用一样部署、迁移、伸缩的代码"——这正是 CSAPP 里"进程是抽象机器"思想在网络设备上的复用。今天的云安全组、软件负载均衡器都是 NFV（网络功能虚拟化）的后裔；更进一步的 eBPF（扩展伯克利包过滤器）/XDP（快速数据路径）甚至把包处理下沉到内核可编程点。回头看，虚拟化不只是省钱，更是把网络功能纳入软件的版本控制、单元测试与 CI/CD（持续集成/持续交付）流程——网络终于可以像软件一样迭代了。
