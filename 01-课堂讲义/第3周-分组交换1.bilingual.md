# CS144: An Introduction to Computer Networks（计算机网络导论，Stanford Fall 2019）

## 分组交换（Packet Switching）

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">标题页</span>

- 课程：CS144, Stanford University — 《An Introduction to Computer Networks》
- 主题：什么是分组交换（packet switching）？
- 主讲：Nick McKeown、Stephen Ibanez（斯坦福大学电气工程与计算机科学教授）

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">大纲（Outline）</span>

1. 什么是电路交换（circuit switching）？
2. 什么是分组交换（packet switching）？
3. 为什么互联网使用分组交换？

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">电路交换（Circuit Switching）</span>

纯图示页（slide 3–4）：两台端点之间由"专用线路（dedicated wire）"直连；随后加入一台电路交换机（circuit switch）——每条通话各占一条专属线路，交换机负责把线路接通。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">电路交换：电话网络实例</span>

- <span style="color:#00838f;">每个电话呼叫（call）被分配 64 kb/s 的固定速率；一条 10 Gb/s 的干线（trunk line）可以承载超过 150,000 路呼叫。</span>
- 图示（slide 5）：源端"主叫方"（Caller）→ 中央局（Central Office, C.O.）→ 干线交换局（Trunk Exchange）→ 中央局 → 目的端"被叫方"（Callee）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">电路交换的特征</span>

- <span style="color:#00838f;">每个呼叫从端到端拥有自己的私有、有保证、相互隔离的数据速率。</span>
- 一个呼叫有三个阶段：
  1. 端到端建立电路（establish circuit，即"拨号" dialing）；
  2. 通信（communicate）；
  3. 关闭电路（close circuit，即"拆除" tear down）。
- 最初，电路就是一条端到端的物理导线。
- 如今，电路更像一条虚拟专线（virtual private wire）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">电路交换的问题（Problems）</span>

1. **低效（inefficient）。** 计算机通信往往非常突发（bursty）。例如在 ssh 连接上打字，或连续浏览网页。如果每次通信都独占一条专用电路，电路的利用率会非常低。
2. **速率多样（diverse rates）。** 计算机以许多不同的速率通信。例如以 6 Mb/s 流式传输视频的 Web 服务器，或以每秒 1 个字符的速度打字的"我"。固定速率的电路对此无能为力。
3. **状态管理（state management）。** 电路交换机要为每次通信维护状态，这些状态必须被管理。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 电路与分组之争的本质是复用（multiplexing）单位的选择：电路交换按"连接"预留资源，分组交换按"分组"逐个竞争资源。第 1、2 条问题可以合并成一句——计算机流量是突发的，突发流量放在一起做统计复用（statistical multiplexing）才划算。用概率论的语言：设 $n$ 个用户各自以概率 $p$ 活跃，电路交换必须按 $n$ 个峰值容量预留，而分组交换只需按 $np$ 加少量余量配置——这正是大数定律（law of large numbers）在带宽工程里的直接变现：$n$ 越大，总流量的相对波动越小，统计复用收益越高。第 3 条"状态管理"则为后面所有协议定调：电路交换机必须为每条连接保留一个表项，分组交换机的转发表只按目的地索引，规模与连接数无关。你在 CSAPP 第 11 章见到的"每条 TCP 连接一个套接字、内核维护连接状态"其实更接近电路交换的状态模型——互联网的设计把这种状态全部推到了端系统。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">分组交换（Packet Switching）</span>

纯图示页（slide 9–10）：分组 = 首部（header）+ 数据（data）；首部携带目的地址；分组交换机（packet switch）按本地的"地址 → 下一跳（next-hop）"表逐个转发分组（如 B 经 S2 → S4 前往 D）。图示还展示了拓扑 A、B、C、D 经交换机 S1、S2、S3、S4 互联。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">分组交换机有缓冲区</span>

- 图示：两个"数据 + 首部"的分组同时到达一台交换机。
- <span style="color:#00838f;">缓冲区（buffer）在以下情况持有分组：当两个或更多分组同时到达时；在拥塞（congestion）期间。</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">分组交换的工作方式</span>

图示（slide 12）：源 A 经路由器 R1、R2、R3、R4 到达目的 B，分组首部 H 随行。

- 分组被逐个独立路由：在每台路由器上查找本地转发表中的地址。
- 所有分组共享一条链路的全部容量。
- 路由器不维护任何按通信（per-communication）的状态。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">为什么互联网采用分组交换？</span>

- **高效利用昂贵的链路（efficient use of expensive links）**
  - 链路曾被假定为昂贵而稀缺的。
  - 分组交换让许多突发（bursty）流高效地共享同一条链路。
  - 引用 Bertsekas/Gallager（数据网络经典教材）的观点："电路交换很少用于数据网络，……因为对链路的利用非常低效。"
- **对链路与路由器故障的韧性（resilience to failure）**
  - 引用 Tanenbaum（《计算机网络》作者）的观点："为了高可靠性，……[互联网]应当是一个数据报子网（datagram subnet），这样即使一些线路和[路由器]被摧毁，报文仍可……改道重行。"

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">小结（Summary）</span>

1. 什么是电路交换？——按连接预留专用速率。
2. 什么是分组交换？——分组带地址、逐跳独立转发、共享链路容量、无每连接状态。
3. 为什么互联网用分组交换？——链路利用高效 + 对故障有韧性。

## 端到端时延（End to End Delay）

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">标题页</span>

- 主题：分组交换 —— 端到端时延（end-to-end delay）。
- 主讲：Nick McKeown、Stephen Ibanez，斯坦福大学，CS144。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">大纲</span>

1. 有用的定义（useful definitions）
2. 端到端时延（end-to-end delay）
3. 排队时延（queueing delay）

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">传播时延（Propagation Delay）</span>

<span style="color:#00838f;">**定义：传播时延 $t_l$：一个比特以传播速度 $c$ 走完一条长度为 $l$ 的链路所需的时间，即 $t_l = l/c$。**</span>

- 例子：在传播速度为 $2\times 10^8$ m/s 的光纤中，一个比特走行 1,000 km 需要 5 ms。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">打包时延（Packetization Delay）</span>

<span style="color:#00838f;">**定义：打包时延 $t_p$：从分组的第一个比特被发送，到最后一个比特被发送，所经历的时间，即 $t_p = p/r$（分组 $p$ 比特，链路速率 $r$ 比特/秒）。**</span>

- 例 1：一个 64 字节的分组被发送到 100 Mb/s 链路上，需要 5.12 µs。
- 例 2：一个 1 kbit 的分组被发送到 1 kb/s 链路上，需要 1.024 s。
- 注：打包时延有时也叫"串行化（serialization）时延"，因为它是把分组串行化到链路上所需的时间。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这三个定义值得放进排队论的框架里对照记忆。传播时延由物理常数决定（光纤中约 $2\times 10^8$ m/s，即真空中光速的 2/3），工程师无法优化它，只能优化路径长度；打包时延由链路速率决定，$t_p = L/R$，是把分组"推上"链路的时间；排队时延则是唯一不确定的成分——它取决于其他流量，本质上是随机变量。后面你会看到利特尔法则（Little's law）$Q = \lambda \cdot d$ 把平均队列占用、到达率与平均排队时延联系起来，它对任何排队系统成立、不依赖到达过程的具体分布。再来一个数量级直觉：1000 km 光纤传播 5 ms，跨太平洋一个往返超过 100 ms——这是任何加速手段都无法突破的物理下限，也是数据中心要把内容副本部署得"离用户更近"的物理原因。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">端到端时延：例题设置</span>

图示（slide 21）：源 A 经 4 段链路（$l_1,r_1$、$l_2,r_2$、$l_3,r_3$、$l_4,r_4$）与 3 台交换机 S1、S2、S3 到达 B。

问题：一个长度为 $p$ 的分组从 A 到 B，从第一个比特发出到最后一个比特到达，需要多长时间？假设交换机对分组进行存储转发（store-and-forward）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">端到端时延：时间线</span>

图示（slide 22–23）把全程画成时间轴：$p/r_1$（A 发上链路 1）→ $l_1/c$（链路 1 传播）→ $p/r_2$（S1 转发）→ $l_2/c$ → $p/r_3$ → $l_3/c$ → $p/r_4$ → $l_4/c$；若 S2 上还有其他分组的队列 $Q_2(t)$、$Q_3(t)$，则再叠加上排队段。

<span style="color:#00838f;">**端到端时延 = 各段传播项 $\sum_i l_i/c$ + 各跳传输项 $\sum_i p/r_i$ + 各队列排队项 $\sum_i Q_i(t)$。**</span>

- 小字注：*Queueing 是英式拼写，1960 年代由 UCLA 的 Kleinrock 采用；Queueing 与 queuing（美式拼写）如今都在广泛使用。*

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 存储转发（store-and-forward）是这个公式里最容易被忽略的关键假设：交换机必须收完整个分组才能开始向下一跳转发，因此每台交换机都额外贡献一个完整的 $p/r_i$ 传输时延——总传输项是"跳数 × 单跳传输时延"，而不是只有一次。这与"直通（cut-through）"转发相对：后者收够首部就转发，下一份讲义的例题会量化两者的差异。从第一性原理看，存储转发是被"差错检测需要整包校验和"与"链路共享需要整包缓冲"共同逼出来的设计。另外注意：公式中传播项与传输项都是固定的，唯独 $\sum_i Q_i(t)$ 随网络负载波动——这解释了为什么 ping 同一个地址每次 RTT 都不同：变化的从来不是光速，而是队列。CSAPP 第 11 章里"RTT 是常数"的直觉，在这里被精确地修正。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">分组时延变化（Packet Delay Variation）</span>

纯图示页（slide 25–26）：横轴为 RTT（ms），纵轴为累积分布函数 CDF（%）。两页各给一条 CDF 曲线，用于观察分组往返时延的分布及其变化幅度——时延不是单一数值，而是一个分布。

## 播放缓冲区（Playback Buffers）

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">标题页</span>

- 主题：分组交换 —— 播放缓冲区（playback buffers）。
- 主讲：Nick McKeown、Stephen Ibanez，斯坦福大学，CS144。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">实时应用的问题</span>

- <span style="color:#00838f;">实时应用（如 YouTube 和 Skype）必须应对可变的排队时延（variable queueing delay）。</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">播放缓冲区：原理图</span>

纯图示页（slide 30）：播放缓冲区中，"正在播放的位置（playing here）"落后于"已缓冲到的位置（buffered to here）"，视频从 youtube.com 经网络下载进缓冲区，播放点刻意滞后，以吸收到达时间的抖动。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">播放缓冲区：累计字节图</span>

纯图示页（slide 31）：服务器与笔记本都以 1 Mb/s 工作；纵轴为累计字节数，横轴为时间。"服务器已发送"曲线与"笔记本已接收"曲线之间的水平间距是可变时延（variable delay），缓冲区（buffer）把这段抖动抹平，让播放速率保持 1 Mb/s 恒定。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">播放缓冲区：数据通路</span>

纯图示页（slide 32）：服务器 →（网络）→ 播放缓冲区（playback buffer，其中有"播放点" playback point）→ 视频解码器（video decoder）→ 屏幕（screen）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">如果缓冲区太小</span>

图示（slide 33）：同样的累计字节曲线，但缓冲区过小，接收曲线追上了播放点——出现"重新缓冲"（rebuffering，即视频卡顿转圈）；解决办法：把缓冲区做大一点！

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">播放缓冲区的要点</span>

- 使用分组交换时，端到端时延是可变的。
- 我们用播放缓冲区来吸收这种变化。
- 我们可以把播放缓冲区做得非常大，但那样视频在开始时就会被延迟。
- 因此，应用会估计时延，据此设置播放缓冲区，并在时延变化时调整缓冲区大小。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">排队带来不可预测的时延</span>

图示（slide 35）：再次给出 A → B 的时间线图，并叠加其他分组造成的队列 $Q_2(t)$、$Q_3(t)$：排队增加了可变且不可预测的时延。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 播放缓冲区是一个漂亮的工程范例：它不消除随机性，而是用受控的固定启动延迟去"吸收"随机延迟。从概率论视角看，它做的就是把排队时延这个随机变量加上一个常数偏移，让"开始播放时刻 + 缓冲时长"以高概率大于任何分组的到达时刻——缓冲大小的选择本质上是在"启动延迟"与"断流概率"之间权衡分布的上分位数。前面两页的 CDF 图正是在度量这个分布：取纵轴 99% 对应的横坐标，就得到"99% 的分组会在多少毫秒内到达"。这与 TCP 的思想同构——TCP 也用缓冲把不可靠、乱序的字节流整形为有序流，只是发生在传输层；而视频应用经常放弃 TCP 的可靠有序交付（改用 UDP/QUIC 类方案），是因为"重传一个早已过期的视频帧"毫无意义：实时性比完整性更重要，宁可丢帧也不卡顿。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">小结</span>

- 端到端时延由三个主要成分构成：沿链路的传播时延（固定）、把分组放上链路的打包时延（固定）、路由器分组缓冲区中的排队时延（可变）。
- 实时应用使用播放缓冲区来吸收排队时延的变化。
