### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Network applications（网络应用）</span>

本讲列出构建在传输层之上的四类核心网络应用技术：

- DHCP（动态主机配置协议）——主机接入网络的"第一步"
- DNS（域名系统）——把域名翻译成 IP 地址的分布式数据库
- TLS（传输层安全协议，Transport Layer Security）——把字节流（ByteStream）变成加密且经过认证的字节流（encrypted ByteStream）
- HTTP（超文本传输协议）——Web 的请求/响应协议

课堂将对 DHCP、DNS、TLS 各做一次现场演示（demo）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">DHCP：接入网络（Getting started on the network）</span>

DHCP（Dynamic Host Configuration Protocol，动态主机配置协议）是主机刚连上网络时用来"开机自举"的协议。它通常提供三样东西：

- 一个 IP 地址；
- 一张简单的转发表（forwarding table，转发表）信息——即子网掩码（netmask，子网掩码）与下一跳路由器（next-hop router，下一跳路由器）；
- 可用的 DNS 服务器地址。

（课堂演示）

- 前身：Bootstrap Protocol（自举协议，RFC 951，1985 年）。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> DHCP 是把你已经学过的 CSAPP 第 11 章网络编程"接上电"的那一步：在 `socket()`、`bind()`、`connect()` 能工作之前，主机必须先拥有 IP 地址、子网掩码和默认网关——而 CSAPP 的程序默认这些已经配好。DHCP 干的正是这件事：主机刚接入时一无所知，通过广播"租赁"到一个 IP，并从服务器拿到子网掩码（netmask）和下一跳路由器（next-hop router），这样它才知道往哪里发包。想想 CSAPP 里 `getaddrinfo()` 返回的地址结构：没有 DHCP 先把本机地址和 DNS 服务器地址配好，这个调用根本无从谈起。它还有段历史：前身是 1985 年 RFC 951 定义的 Bootstrap Protocol（自举协议），DHCP 在其基础上扩展了可租赁的地址池与租期机制。一个有趣的递归：DHCP 服务器自己的地址怎么找？答案是靠链路层广播——这也是为什么 DHCP 必须设计成"无初始配置也能用"。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">DNS：分布式只读键值存储</span>

DNS（Domain Name System，域名系统）本质上是一个**分布式的只读键值存储（distributed read-only key-value store）**。

- 查询是可靠的（reliable），底层传输可以用 UDP（当有效载荷（payload）能装进一个数据报（datagram）时），也可以用 TCP（装不下时）。
- 最流行的用途：把域名转换为 IPv4 地址（A 记录）。
- 但它还有很多其他用途！IPv6 地址（AAAA 记录）、PTR（反向解析）、MX（邮件交换）等。
- （课堂演示）

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "分布式只读键值存储"这个定性值得用你熟悉的知识拆开看：它是键值对（你写的 `getaddrinfo("www.stanford.edu")` 就是按 key 查询），但存储被拆到全球成千上万台权威服务器上，按域名层次（如 `.edu` → `stanford.edu` → 具体 host）逐级委托，形成一个逻辑上的树——这与 6.042J 里树结构"从根到叶路径唯一"的性质对应，也解释了为什么全系统一致性问题被"只读"化解：数据几乎不变，各处缓存（cache，缓存）旧值只是短暂不一致。UDP 与 TCP 的选择是端到端原则的活教材：查询响应通常几十字节，装进一个 IP 数据报绰绰有余，此时在 UDP 上重传一个请求远比建 TCP 连接的三次握手便宜；只有区域传送（zone transfer）这类大负载才动用 TCP。你还可以用概率论算一笔账：设一次根/顶级域/权威域查询的期望时延为 $E[T]$，若本地缓存以概率 $p$ 命中，则期望时延变为 $p \cdot 0 + (1-p) E[T]$——这正是 CDN 与 DNS 缓存设计的核心权衡：提高 $p$ 比缩短 $E[T]$ 便宜得多。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">HTTP：无状态的请求/响应协议</span>

HTTP 是一个**无状态（stateless）请求/响应协议**：

- GET、HEAD 方法是幂等的（idempotent，幂等）——重复执行结果相同；
- POST/PUT/PATCH/DELETE 是非幂等的（non-idempotent）。

几个版本：

- HTTP/1.0：每条 TCP 连接只做一次请求/应答；
- HTTP/1.1：每条 TCP 连接可以承载多次请求/应答，但必须按顺序（in order）；
- HTTP/2：同上，但允许用并发流（concurrent streams）乱序返回应答——消除了"每请求"粒度的队头阻塞（head-of-line blocking，队头阻塞）；
- HTTP/3：运行在自定义的非 TCP 传输（QUIC）之上——消除了"每分组"粒度的队头阻塞。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> HTTP 的四次演进可以用"队头阻塞到底堵在哪一层"这条第一性原理串起来。HTTP/1.0 每请求开一条 TCP 连接，浪费但简单；HTTP/1.1 复用连接，可请求却必须按序应答——第一个慢请求会堵住后面所有请求，这是**应用层**的队头阻塞；HTTP/2 引入并发流，应用层不堵了，但 TCP 仍保证字节流按序交付，底层任何一个分组（packet，分组）丢失都会让所有流一起等重传——这是**传输层**的队头阻塞；HTTP/3 干脆抛弃 TCP、在 UDP 上自建可靠传输，让每个流独立做丢包恢复，堵点才真正消失。注意"幂等"（idempotent）这个词的分量：GET 重复执行结果不变，所以重试安全；POST 可能重复下单，所以非幂等请求的重试策略必须更小心——这是 TCP 与应用层责任划分（端到端原则）在 API 设计上的体现。对比你写过的 CSAPP echo 服务器：它处理的就是 HTTP/1.0 式的"一连接一请求"模型，如今浏览器却在用 HTTP/3，三十年间协议栈的每一层都被重新审视过。
