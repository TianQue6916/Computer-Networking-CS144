# CS144: Introduction to Computer Networking（计算机网络导论，Stanford Fall 2019）

## 可靠服务（Reliable Services）

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">互联网提供什么抽象？</span>

- 互联网在主机（host）之间提供的服务是：<span style="color:#00838f;">主机之间"尽力而为"（best-effort）的数据报（datagram）交付</span>。
- 那么，什么是"数据报"（datagram）？什么又叫"尽力而为"（best-effort）？
- 换个问法：我向你发送了一个数据报——它可能遭遇什么？

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 从 CSAPP 第 11 章的视角看，这个抽象的"弱"是刻意设计的结果。你在 socket 编程中调用 read/write 时享受的可靠字节流，并不是网络层白送的，而是传输层（TCP）在不可靠的数据报之上"制造"出来的。互联网的设计者把可靠性从网络核心搬到了端系统——这就是端到端原则（end-to-end principle）：网络只承诺"尽力而为"，想要更强保证的应用自己想办法。这样设计的好处是网络核心保持简单：路由器不需要为每条连接维护状态（state），新服务可以在端点上不断发明而无需改动网络本身。类比你在 6.042J 里熟悉的公理化思路：底层给出的保证越少、越正交，上层可组合出的服务空间反而越大。理解了这一层"故意不保证"，后面所有可靠性技术——序列号、确认、重传——才会显得有意义：它们全是端系统对网络"不作为"的补偿。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">一个数据报可能遭遇什么？</span>

理想情况只有一种，意外却有很多种：

1. 它被正确送达了目的地！
2. 它被送达了错误的目的地。
3. 开头部分送达了，结尾却没送到。
4. 它送达了，但其中一些比特（bit）翻转了。
5. 它被送达了不止一次。
6. 它在其他更早发送的数据报之后才送达（乱序交付）。
7. 它一年之后才送达。
8. 它永远没有送达。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">服务：提供给客户/调用者的抽象</span>

服务（service）就是提供给客户、顾客或调用者的抽象。先看几个常见的服务类型与对应动作：

- 复制一个字符串 / 二进制大对象（blob）/ 文件。
- 流式传输一个字节序列。
- 获取一份"足够新鲜"的数据（温度计、视频聊天、屏幕共享）。
- 就某件事达成一致（agree on something）。

再看三个"必须足够可靠才能回答"的查询问题：

- 你的子弹打中我的游戏角色了吗？
- 我真的付给你 200 美元了吗？
- 我们俩明天会一起进攻吗？

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这一页埋着一个重要伏笔：不同服务需要的"可靠性"强度完全不同。"复制一个文件"要求 exactly-once 的字节送达——少一个字节文件就坏了；"温度计读数"只要最新值，旧数据宁可丢弃（这正是实时音视频常用 UDP 的原因）；而"我是否付了 200 美元""我们明天是否一起进攻"这类问题涉及就某事达成一致（agreement），是分布式系统中最困难的问题之一——盲目重传可能导致"付两次钱"，这也是金融系统要靠幂等键（idempotency key）与确认回调来兜底的原因。你在 CSAPP 第 11 章用过的套接字（socket）只提供双向字节流这一种抽象，如何在其上构造这些不同强度的服务语义，正是应用层协议设计的核心工作。TCP 选择了"可靠字节流"作为自己的答案，本讲义随后几周会展示它如何一步步搭出来。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">当可靠服务遭遇故障时，会发生什么？</span>

四种失败模式：

- **fail-fast（快速失败）**：立即发出故障信号。
- **fail-safe（失效安全）**：转而做一件可接受的事。
- **fail-soft（失效柔性）**：继续运行，但以降级的形式。
- **fail-bad（失效恶化）**：悄悄破坏服务保证。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这四种失败模式是所有分布式系统设计的第一性权衡，绝不仅限于网络。fail-fast 的价值在于把故障暴露在离故障点最近的地方——你写 C 程序时遇到的段错误（segfault）、操作系统内核里的断言（assert），本质上都是 fail-fast：宁可立刻崩溃，也不带病运行污染后续数据。fail-safe 与 fail-soft 则对应数据库的降级读、CDN 返回过期缓存这类"兜底"策略。关键洞察是：fail-bad（悄悄违反保证）是最危险的模式，因为它把故障延迟到了下游更难定位的地方——这与调试经验一致：显式崩溃的 bug 好修，静默腐蚀数据的 bug 难查。再从概率论视角看：故障检测本身也有误报与漏报（相当于假设检验的第一类/第二类错误），后文出现的心跳（heartbeat）机制正是在这两类错误之间权衡——心跳太密浪费带宽、对瞬时抖动过敏；太疏则故障发现时间变长。CS144 后面讲的路由邻居检测与 TCP 保活，都是这套理论的直接应用。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">制造可靠性的技术</span>

补救手段（Remedies）清单：

- 序列号（sequence numbers）
- 确认（acknowledgments）
- 校验和 / MAC（checksums / MACs）
- FEC（前向纠错，forward error correction）
- 重传（retransmission）
- 心跳（heartbeats）

三个延伸话题：

- 关联故障（correlated failure）
- TCP 与 DNS
- 飞机悖论（paradox of airplanes）

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这张清单几乎就是 TCP 的"配料表"：序列号解决乱序与重复，确认 + 超时 + 重传构成闭环反馈，校验和与 MAC 分别对付比特损坏与恶意篡改，FEC 前向纠错则用冗余开销换取更少的重传延迟。"关联故障"值得用概率论单独说一句：如果两台服务器的故障是相互独立事件（independent events），同时故障的概率可以相乘，冗余备份就显得极其有效；但现实中故障高度相关——同一机房的断电、同一个软件里的同一个 bug——独立性假设失效，"复制三份就万事大吉"的直觉随之破产，这正是高可用设计中"副本不是越多越可靠"的根源。"飞机悖论"指的则是：飞机的事故率远低于汽车，不是因为飞机部件天然更可靠，而是整个航空业采用了远超汽车行业的冗余设计、维护流程与检查制度——可靠性是被制造出来的属性，而非天然禀赋，这正是本讲标题 "manufacture reliability"（制造可靠性）的含义。至于 TCP 与 DNS 被点名，是因为它们分别是在不可靠网络上"制造"可靠通信与可靠目录查询的两个最成功实例。
