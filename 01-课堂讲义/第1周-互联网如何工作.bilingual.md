### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">开场：我的程序、别人的程序与数据</span>

slides 用一个寄信类比开场：屏幕一侧是 My Program（我的程序），另一侧是 Someone else's Program（别人的程序），中间流动的是 Data（数据）。数据被打包成一个个分组（packet，分组），就像信件——信封上有 From Address（寄件人地址）与 To Address（收件人地址）。

A more accurate model（一个更精确的模型）：寄件地址写成完整的 postal address（邮政地址）——Nick McKeown, Gates 344, Stanford University, Stanford, CA 94305-9030 USA（"Me"，我），收件地址是"你"（You）。网络上的地址与之对应，这就是 IP 地址的雏形。

Multiple packets in pipeline at same time（多份分组同时在管道中流动）：多封信可以同时在路上，一封接一封排成流水线，每封都带着同样的地址。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">分组在网络上会遭遇什么</span>

四张连续的 slide 展示了分组（packet，分组）可能遭遇的四种命运：

1. Packets may be damaged（分组可能被损坏）——图示中数据变成了 "?!%%*"。
2. Packets may arrive out of order（分组可能乱序到达）——图示中标号 12 的分组先到。
3. Packets may be duplicated（分组可能被重复投递）——同一份数据出现了两份。
4. They may not arrive at all!（它们可能根本不到达！）——图示中缓冲区显示 "Full"（满了），数据被丢弃。

Summary so far（到这里的小结）：应用程序以分组为单位收发数据……而承载它们的互联网是不可靠的（unreliable）。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这个寄信类比是理解"分组交换"最省力的入口，而且它在两个方向上都精确。正向看：一封信（分组）只需要携带收件地址，不需要提前给邮局"打电话预约路线"——这正是与电路交换（circuit switching，电路交换）的本质区别，邮局从不为你的信保留一条专用通道。反向看：类比同样解释了互联网为什么"天生不可靠"——现实中的信确实会丢、会被水泡、会晚到，邮政系统也从不承诺任何一条；它只提供"尽力而为"（best-effort，尽力而为）的投递。你读 CSAPP 第 11 章时调用 `socket()` 建立连接，其实是在这个不可靠的投递系统之上套了一层可靠的壳——套壳的工作交给 TCP，后面几节会讲。记住这个顺序：先有不可靠的 IP，再有可靠的 TCP，可靠性是"制造"出来的，不是网络送的。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">分组如何找到穿越互联网的路</span>

How packets find their way across the Internet（分组如何找到穿越互联网的路）。

Internet Addresses（互联网地址）：所有互联网分组都携带一个目的 IP 地址（destination IP address）。我们通常把 IP 地址写成这样：

```
171.64.74.58
```

Routers forward packets one at a time（路由器逐个转发分组）：路由器查看 IP 地址，然后把分组发往离目的地更近的下一个路由器。

IP Addresses（IP 地址）：IP 地址告诉路由器下一步把分组送往哪里。IP 地址是有结构的（IP addresses have structure）——本页源文字符层互相叠印，按可辨识的残片与图示语义复原为两行说明：一个由斯坦福大学管理的网络（A network operated by Stanford University.），对应地址 171.64.74.58；一个由 RIPE NCC 管理的网络（An address managed by RIPE NCC — European IP Networks），对应地址 88.255.96.208。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">亲眼看路径：ping 与 traceroute</span>

Can we see the path our packets take?（我们能看见分组走的路径吗？）能！在你的电脑上试试：

```
ping yuba.stanford.edu
traceroute yuba.stanford.edu
```

（Windows 下命令为 "tracert yuba.stanford.edu"。）

ping：从 yuba 出发到日本再回来，大约需要 115 ms——即往返时延（round-trip-time，RTT 往返时延）。

一张地图 slide 标出 Stanford（斯坦福）与 Kyoto（京都）两地，距离 8,637 km。下一页在两地之间做了时延推算（源文公式符号乱码，按可辨识数字复原）：光在光纤中的传播速度约为 $2\times 10^{8}$ m/s，单程传播时延 $t = \frac{8.637\times 10^{6}\ \text{m}}{2\times 10^{8}\ \text{m/s}} \approx 0.043\ \text{s} = 43\ \text{ms}$，于是 RTT $\approx 86\ \text{ms}$（与图中标注 RTT = 86ms 一致）。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这组 traceroute 输出比任何教科书都能说明"逐跳转发"的含义：你的分组自己不带路线图，每一台路由器只负责回答"下一步去哪"。注意两条路径的差异——校内出发走的是 Internet2/GEANT 学术网（研究教育的专线），家里出发走的是 Comcast→Cogent 商业骨干网；同一目的地，路径可以完全不同，这正是数据报（datagram，数据报）网络的特征。那两条 `*` 行也有含义：traceroute 的原理是故意发 TTL（生存时间）归零的探测包、让中途路由器回 ICMP 报文来"自曝"，某些路由器不回应就显示 `*`，路径照样能继续测。再看时延数字：跨越大西洋到伦敦那一跳把 RTT 从 68 ms 拉到 143 ms——物理距离带来的传播时延下限是光速决定的，任何算法都压缩不了；而同一地点前后两跳之间 0.2 ms 的波动则来自排队。用你概率课的语言：传播时延是相对确定的"均值"，排队时延才是方差的主要来源。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">互联网不可信！</span>

The Internet cannot be trusted!!（互联网不能被信任！！）

- 互联网不承诺按序投递分组。
- 它不承诺快速投递，也不承诺准时投递。
- 它甚至不承诺投递！
- 它只做"尽力而为"（best-effort）的尝试。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">在不可靠的互联网上可靠地传数据</span>

Sending data reliably over an Internet that is unreliable（在一个不可靠的互联网上可靠地发送数据）。

How Network Applications Communicate（网络应用如何通信）。最常见的方式：

- 通信是双向的（bidirectional）。
- 通信是可靠的——只要两台计算机之间存在可用路径。
- 它就像一根无格式的管道：你把数据从一端推入，它会正确地从另一端冒出来；至于数据在管道内部如何组织格式，由应用程序自己决定。

Byte Stream Model（字节流模型）三连 slide：

1. Setup connection（建立连接）：主机 A 与 B 通过互联网建立连接。
2. Stream of bytes（字节流）：A 向连接中推入字节流，B 在另一端原样收到字节流。
3. Close connection（关闭连接）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">实例：万维网（HTTP）</span>

World Wide Web (HTTP)：

1. Client（客户端）向 www.stanford.edu 服务器 Setup connection（建立连接）。
2. 客户端送出字节流 `GET/HTTP/1.1`；服务器回送字节流 `HTTP/1.1 200 OK <...contents of index.html...>`（即 index.html 的内容）。
3. Close connection（关闭连接）。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">TCP 与 IP 的分工</span>

Your Application（你的应用，例如 Chrome、Skype）→ "TCP" → "IP" → Data；服务器一侧（例如 Google、Facebook）同样堆着 "TCP" 与 "IP"。TCP 确保所有数据都被送达（TCP makes sure all the data is delivered）。

TCP's job（TCP 的职责）：

- 确保所有数据被正确送达。
- 按正确的顺序把数据交给应用程序。

怎么做到（How?）？

- 给每个分组加上序列号（sequence number，序列号），让接收方能检查是否有缺失，并把它们排回正确顺序。
- 当分组到达时，接收方向发送方回送一个送达确认（acknowledgment，ACK 确认）。
- 如果没有等到确认，就重发数据（resend）。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> "TCP 的职责"这三条机制看起来朴素，但请注意它们各自的分工：序列号解决"乱序与缺失的检测"，ACK 解决"让发送方知道结果"，重传解决"补救"。三者组合成一个闭环，缺一不可——没有序列号，重传就会重复投递；没有定时器，一次丢包就让整条连接卡死。这正是慕课 2-7/2-8 节停等协议（stop-and-wait）与滑动窗口（sliding window）的全部要点，本堂课只是把它们放回了真实协议的语境。还有一个容易忽略的细节：TCP 交付给应用的是"按正确顺序的无格式字节流"，意味着分组与分组的边界、每个分组的含义都被 TCP 抹掉了——你写 echo 服务器时从 `recv()` 拿到的数据没有"消息"概念，必须自己定界。管道类比里"格式由应用决定"说的就是这件事。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">封装：一个 HTTP 请求的旅程</span>

http client（e.g. Chrome）（HTTP 客户端，例如 Chrome）一页展示了完整协议栈：Application（应用层）→ TCP → IP → Ethernet（以太网）。HTTP 请求 `GET index.html` 逐层被包上首部：

- TCP 首部带上 HTTP 交付说明：`(http) "Deliver to the http server"（交付给 HTTP 服务器）`，以及 IP address (TCP)（IP 地址）——`"...at this destination"（送到这个目的地）`。
- IP 首部带上目的 IP 地址：IP Address (TCP)。
- Ethernet 首部带上 "MAC" address（MAC 地址）(IP)——`"...starting with this link"（先走这段链路）`。

于是线上跑的是 Ethernet data IP data TCP data（以太网帧包着 IP 包着 TCP 包着 HTTP 数据）——Here it goes....（出发！）

http server（e.g. www.google.com）（HTTP 服务器）一页展示反方向的拆包：Ethernet 交给 IP，IP 说 "Deliver to TCP"（交付给 TCP），TCP 说 "Deliver to the http server"（交付给 HTTP 服务器），最后应用层拿到 `GET file`。

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这两页是分层（layering，分层）与封装（encapsulation，封装）最直观的演示，每个首部都回答一个不同层次的问题：以太网首部只关心"这一跳走哪段链路"（MAC 地址），IP 首部只关心"最终目的地是谁"（IP 地址），TCP 首部只关心"交给主机上哪个程序"（端口号）。注意 MAC 地址的说明文字是 "starting with this link"——它在每一跳都会被换掉，而 IP 地址端到端不变，这个"谁全程、谁逐跳"的对比是理解网络分层的第一把钥匙。你可以在 CSAPP 里找到对应物：socket 地址结构 `sockaddr_in` 里装的是 IP+端口（TCP 层的事），而把比特送上线缆是以太网驱动的事，应用程序完全不用管。分层的代价是每层都加首部、有效载荷占比下降，收益是每一层可以独立演进——这套"接口不变、实现随便换"的思想，和操作系统里虚拟内存把物理地址藏起来是同一个套路。

Summary（最后的小结）：

- 应用程序以分组为单位收发数据……
- ……在一个不可靠的互联网之上。
- 分组使用 IP 目的地址逐跳转发。
- 我们的应用程序使用 TCP 来确保数据被送达并恢复正确顺序。
