### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">I. Stop-n-Wait-n-Answer（停等问答）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 1 [10 points]

（题干英文原文见题目卷。）

**Part (i)**：<span style="color:#00838f;">若网络不丢弃、不重复、不损坏任何分组，传输需要多长时间（秒）？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**5** seconds（秒）。
> >
> > 需要的帧数 = $100\text{KB} / 1\text{KB} = 100$ 个。由于这是停等协议（stop-and-wait），所需时间 = $100 \times 50 = 5000$ ms = 5s。
>
> <span style="color:#7f8c8d;">核算：$100 \times 50\text{ms} = 5000\text{ms} = 5.00$s ✓（每段一个完整 RTT 周期，含最后一段的 ACK 往返；若把"传输完成"定义为最后一数据段发出即止则为 4.95s，官方答案取 5s 的口径。）</span>

**Part (ii)**：<span style="color:#00838f;">若网络以 10% 的概率独立丢弃每个分段（数据与确认都可能丢），传输的期望时长是多少？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**9.69** seconds（秒）。
> >
> > 成功发送一个分组所需的时间是随机变量 $X = 200 \cdot Y + 50$，其中 $Y$ 是首次成功传输之前的尝试失败次数。这里 $Y$ 服从几何分布（geometric distribution），成功概率 $p = 0.9 \times 0.9 = 0.81$（数据段与 ACK 都必须成功到达）。因此发送一个分组的期望时间为
> >
> > ```math
> > E[X] = 200 \cdot E[Y] + 50 = 200\left(\frac{1}{p} - 1\right) + 50 = 96.9\text{ ms}
> > ```
> >
> > 乘以 100 个分段，即得最终答案：$100 \times 96.9\text{ms} = 9.69$s。
>
> <span style="color:#7f8c8d;">核算：$E[Y] = \frac{1-p}{p} = \frac{0.19}{0.81} = 0.23457$；$200 \times 0.23457 = 46.91$；$46.91 + 50 = 96.91$ms；$100 \times 96.91\text{ms} = 9.691$s ≈ **9.69s** ✓（原提取文本 "p = 109 × 109" 为上标丢失，应为 $0.9 \times 0.9$。）</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这道题是概率论与网络时延模型结合的范本，把建模过程拆开看：一次"尝试"由"发数据段 + 等确认"组成，任一环丢失即整次尝试失败，起 200ms 定时器重来——所以失败尝试的成本恒为 200ms，最后成功的尝试成本为 50ms（一个 RTT）。把"到第 $k$ 次尝试才成功"写成 $X = 200k + 50$，其中 $k$ 恰是几何分布（failures before first success，首次成功前的失败次数）：$P(Y = k) = (1-p)^k p$，期望 $E[Y] = \frac{1-p}{p}$。两个易错点值得强调：其一，$p$ 不是 0.9 而是 $0.9^2 = 0.81$，因为数据段和 ACK 任一丢失都算失败——两个独立事件"与"起来，概率相乘；其二，停等下 100 个分段是串行独立重复，期望可直接线性相加（期望的线性性，6.042J 与概率论都强调过），不需要考虑任何耦合。若换成滑动窗口，段与段不再独立，这个漂亮的线性分解就不成立了——这也是停等协议在考试里"好算"、在现实里"慢"的同一个原因。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">II. Without TCP The Internet Ain't Nuthin'（分裂 TCP 连接）</span>

（背景题干与公式、近似值表见题目卷：吞吐量近似为 $\frac{1.22 \cdot MSS}{RTT \cdot \sqrt{p}}$，$MSS \cdot \sqrt{3/2} = 13{,}717$ bits，$\sqrt{0.1} = 0.32$，$\sqrt{0.19} = 0.44$。）

#### <span style="color:#2471a3;">**[exercise]**</span> Question 2 [5 points]

<span style="color:#00838f;">B 不分裂连接时，A→C 的 TCP 吞吐量是多少？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**428–434 kbps**。
> >
> > $RTT\sqrt{p} = 0.1 \times 0.32 = 0.032$，$MSS \cdot \sqrt{3/2} = 13{,}717$ bits，所以
> >
> > ```math
> > \frac{13{,}717}{0.032} = 428{,}656 \text{ b/s} \approx 429 \text{ kbps}
> > ```
> >
> > 434 kbps 是使用更多有效数字（$\sqrt{0.1} = 0.31623$）得到的更精确计算结果。
>
> <span style="color:#7f8c8d;">核算：$13717/0.032 = 428{,}656$ b/s ✓；用精确 $\sqrt{0.1}$：$13717/(0.1 \times 0.31623) = 433{,}801$ ≈ 434 kbps ✓。题目允许的近似 $\sqrt{0.1}=0.32$ 给出下界，精确值给出上界，区间 428–434 合理。注意：若把分子取 $1.22 \times 1400 \times 8 = 13664$ bits（$1.22$ 与 $\sqrt{3/2} = 1.2247$ 的微小差异），结果为 427,000 b/s ≈ 427 kbps，与官方给的 428,656 相差约 0.4%——官方答案以 $MSS\sqrt{3/2} = 13717$ 为准。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 3 [5 points]

<span style="color:#00838f;">B 分裂连接（A–B 段 10% 数据段丢失、不丢 ACK；B–C 段不丢包）时，A→C 的吞吐量是多少？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**856–888 kbps**。
> >
> > B–C 之间的连接受 A–B 之间连接的限制（后者丢包率更高）。A–B 段的速率与上一题相同，只是 RTT 从 100ms 减半为 50ms，所以其吞吐量是不分裂情形的两倍。更精确地：$RTT\sqrt{p} = 0.05 \times 0.32 = 0.016$，$MSS\sqrt{3/2} = 13{,}717$ bits，所以
> >
> > ```math
> > \frac{13{,}717}{0.016} = 857{,}313 \text{ b/s} \approx 857 \text{ kbps}
> > ```
>
> <span style="color:#7f8c8d;">核算：$13717/0.016 = 857{,}313$ b/s ✓（原提取文本 "0.01583/2" 为排版残片，应为 $0.05 \times 0.32 = 0.016$ 或 $\sqrt{0.1}/2 = 0.158/10$，两种读法结果一致）。区间上限 888 kbps 对应更精确的 $\sqrt{0.1}$。要点：分裂连接后 A–B 段用 50ms 的 RTT 跑同样的 Mathis 公式，吞吐量 ×2；B 代理立即确认使 B–C 段永远不成为瓶颈。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 4 [5 points]

<span style="color:#00838f;">B 分裂连接，且 A–B、B–C 两段各丢 10% 分组时，A→C 的吞吐量是多少？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**856–888 kbps**。
> >
> > 与上一题相同。B–C 段路径的吞吐量与 A–B 段相同（两段丢包率都是 10%、RTT 都是 50ms），端到端吞吐量由两段中较慢者决定，仍是 857 kbps 量级。
>
> <span style="color:#7f8c8d;">核算：与 Q3 完全相同 ✓。关键洞察：分裂把"两段损失叠加"（Q5 的 19%）变成"两段各跑各的"，每段只看到自己 10% 的丢失率和 50ms 的 RTT。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 5 [5 points]

<span style="color:#00838f;">B 不分裂连接，A–B 段丢 10% 数据段、B–C 段也丢 10% 数据段时，A→C 的吞吐量是多少？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**312–315 kbps**。
> >
> > A–B 与 B–C 的丢失相互影响，端到端丢弃率为 19%：成功率为 $0.9^2 = 0.81$，即 81%，所以 $p = 19\%$。$RTT\sqrt{p} = 0.1 \times 0.44 = 0.044$，$MSS\sqrt{3/2} = 13{,}717$ bits，所以
> >
> > ```math
> > \frac{13{,}717}{0.044} = 311{,}750 \text{ b/s} \approx 312 \text{ kbps}
> > ```
> >
> > 315 kbps 是使用更多有效数字的更精确计算结果。
>
> <span style="color:#7f8c8d;">核算：$1 - 0.9 \times 0.9 = 0.19$ ✓（原提取文本 "The success rate is 0.92, or 81%" 为上标丢失，应为 $0.9^2 = 0.81$）；$13717/0.044 = 311{,}750$ ✓；精确 $\sqrt{0.19} = 0.43589$ 给 $13717/0.043589 = 314{,}781$ ≈ 315 kbps ✓。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> Q2–Q5 是一绝妙的受控实验，四问恰好构成 2×2 矩阵：分裂与否 × 一段丢还是两段丢。所有结论都从 Mathis 公式 $\frac{1.22 \cdot MSS}{RTT\sqrt{p}}$ 的三个自变量读出来：MSS 固定，能变的只有 RTT 与 p。分裂连接的价值在于**同时**改善两个自变量——RTT 从 100ms 砍到 50ms（B 本地确认），p 从合成 19% 隔离回 10%（每段只看到自己的丢失），两项相乘吞吐量从 312 涨到 857 kbps，接近 2.75 倍。用概率论的话说：不分裂时一个分组要活着穿过两段链路，存活概率 $0.9 \times 0.9 = 0.81$，端到端丢失率 $p_{e2e} = 1 - (1-p_1)(1-p_2)$ 是两段丢失率的"卷积"；分裂后每段的 TCP 控制环只对自己的丢失负责，隔离了故障域。代价也明显：B 必须缓存两端流、伪造 ACK 与源地址（中间盒破坏端到端语义），而且拥塞信息在 B 处断裂——A 永远不知道 C 侧的拥塞。现实中 CDN、蜂窝网关的 PEP（性能增强代理）用的正是这套分裂技术，这个 2×2 矩阵就是它们的收益证明书。

<span style="color:#00838f;">为"Your Router"写出在互联网与 400 台服务器之间正确转发所需的路由表项（尽可能少的表项）。</span>

（题干英文原文见题目卷。）

> > <span style="color:#2471a3;">**[solution]**</span> 答案（三条表项）：
> >
> > | destination prefix（目的前缀） | net mask（子网掩码） | next hop（下一跳） | interface（接口） |
> > |---|---|---|---|
> > | 107.21.41.0 | 255.255.255.0 | 107.21.41.1 | eth3 |
> > | 107.21.17.0 | 255.255.255.0 | 107.21.17.1 | eth2 |
> > | 0.0.0.0 | 0.0.0.0 | 54.112.78.116 | eth1 |
>
> <span style="color:#7f8c8d;">核对：Router A 侧 200 台主机占据 107.21.41.2–107.21.41.255，聚合为一个 /24 前缀 107.21.41.0/24 ✓；Router B 侧同理 107.21.17.0/24 ✓；去往其余一切目的地的流量走默认路由 0.0.0.0/0.0.0.0 指向互联网侧下一跳 54.112.78.116 ✓。接口编号（eth3/eth2/eth1）来自题目原图中各链路的标注。三行即最少表项数：两个 /24 聚合 + 一条默认路由。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 8 [5 points]

<span style="color:#00838f;">把 107.21.17.50 这台服务器挪到 Router A 后面且不改 IP 时，"Your Router"的路由表要怎么改？</span>

（题干英文原文见题目卷。）

> > <span style="color:#2471a3;">**[solution]**</span> 答案——新增一条表项：
> >
> > | destination prefix（目的前缀） | net mask（子网掩码） | next hop（下一跳） | interface（接口） |
> > |---|---|---|---|
> > | 107.21.17.50 | 255.255.255.255 | 107.21.41.1 | eth3 |
> >
> > 解释：由于路由器使用最长前缀匹配（longest prefix match），一条只针对这一个目的 IP 地址的 /32 路由表项会把去往它的流量改道到 Router A，而不会影响去往 Router B 后面任何其他服务器的流量。
>
> <span style="color:#7f8c8d;">核对：107.21.17.50/32 比 107.21.17.0/24 更长、前缀匹配更具体 ✓；原 /24 表项保持不动（B 后面其余 199 台服务器仍走 eth2）✓；这是 LPM 原则的标准应用——更长的前缀永远赢。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> Q7+Q8 这对姊妹题把 Unit 1 的最长前缀匹配（LPM）从"查表规则"升级成了"设计工具"。Q7 的核心是路由聚合（route aggregation）：200 台主机不需要 200 条表项，只要它们在同一个 /24 里，一条前缀就把它们打包——这与 1-10 节"前缀即拓扑"的思想一致：前缀的粒度反映的是网络拓扑的粒度，而不是主机数量。Q8 则展示了 LPM 灵活性的另一面：当拓扑事实（这台机器物理上在 A 后面）与编址事实（它的 IP 还在 B 的 /24 里）冲突时，一条 /32 主机路由就能精确覆盖例外。可以把它类比成 CLRS 里散列表的冲突处理：/24 是"桶"，/32 是"桶内精确键"，LPM 的匹配顺序相当于先散列再精确比较——最具体者胜。这类"例外条目"在真实运营商路由表里无处不在（更长的前缀通常是流量工程或黑洞路由），考试之外它每天都在互联网的转发表里发生。也注意题目顺手带出的工程约束：改路由的人（你）与管理服务器 IP 的人（管理员）可以解耦工作，前提是协议（LPM）给了你一个确定的语义。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">V. Playback Buffers and Queues（播放缓冲与队列）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 9 [10 points]

（题干：4 台路由器、1Mb/s 链路、3000km、1500 字节分组、传播速度 $2 \times 10^8$ m/s；1KB = 1024 字节但 1Mb/s = $10^6$ 比特/秒。英文原文见题目卷。）

**Part (i)**：<span style="color:#00838f;">无排队、忽略处理时间时的最小 RTT？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**150** milliseconds（毫秒）。
> >
> > $RTT = 2 \times (\text{prop} + \text{packetization} \times 5\ \text{hops})$。每跳打包时延 = $1500 \times 8 \text{ bits} / 10^6 \text{ b/s} = 12$ms；5 跳共 60ms。传播时延 = $3000\text{km} / 2 \times 10^8 \text{ m/s} = 15$ms。因此 $RTT = 2 \times 75\text{ms} = 150$ ms。
>
> <span style="color:#7f8c8d;">核算：$1500 \times 8 = 12000$ bits；$12000/10^6 = 0.012$s = 12ms/跳 ✓（原提取文本 "1500B/1e6" 漏写了 ×8，结果 12ms 只有按比特算才成立，已修复）；4 台路由器 → 5 条链路（5 hops）✓；$5 \times 12 = 60$ms；$3 \times 10^6 / (2 \times 10^8) = 0.015$s = 15ms；单程 $60 + 15 = 75$ms；RTT = 150ms ✓。</span>

**Part (ii)**：<span style="color:#00838f;">仅本小节假设路径上一台路由器有 5 个分组的稳定队列占用，端到端时延（单程）是多少？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**135** milliseconds（毫秒）。
> >
> > 平均排队时延 = 5 个分组 × 12ms/分组 = 60ms。所以总端到端时延为 $60 + 75\text{ms} = 135$ ms。
>
> <span style="color:#7f8c8d;">核算：新到达分组须等队列中既有 5 个分组依次发送完毕，$5 \times 12 = 60$ms ✓（原提取文本 "5 packets / (1 packet) * 12 ms" 为分数线残留，实为乘法）。</span>

**Part (iii)**：<span style="color:#00838f;">假设每台路由器的队列占用上限都是 5 个分组，最大端到端时延？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**315** milliseconds（毫秒）。
> >
> > 最大排队时延为 $4 \times 60 = 240$ms。所以最大端到端时延为 $240 + 75\text{ms} = 315$ms。
>
> <span style="color:#7f8c8d;">核算：4 台路由器各贡献最多 60ms（ii 的结果），$4 \times 60 = 240$ ✓；$240 + 75 = 315$ms ✓。</span>

**Part (iv)**：<span style="color:#00838f;">(iii) 条件下，若每个分组都成功到达，播放缓冲应为多长（字节）？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**30,000** bytes（字节）。
> >
> > 最小端到端时延是 75ms，最大是 315ms。因此需要 $315 - 75 = 240$ms 的缓冲。换句话说，播放缓冲需要吸收排队时延造成的变化。在 1Mb/s 下，240ms 对应 240,000 比特，即 30,000 字节（或 29.3KB）。
>
> <span style="color:#7f8c8d;">核算：$240\text{ms} \times 10^6 \text{b/s} = 240{,}000$ bits；$240000/8 = 30{,}000$ bytes ✓；$30000/1024 = 29.3$ KB ✓（题目特意提示 1KB = 1024B、1Mb/s = $10^6$ b/s 的单位混用陷阱）。</span>

**Part (v)**：<span style="color:#00838f;">(iii) 条件下，若每个分组要么首次发送即成功、要么首次被丢后重传成功（发送方在"2 倍最大端到端时延"之后才知晓丢包），播放缓冲应为多长（比特）？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**870,000** bits（比特）。
> >
> > 最小端到端时延仍是 75ms。一个分组到达所需的最长时间是 $2 \times 315$ms（发送并发现它失败了）$+ 315$ms（重传成功）。回忆：播放缓冲绝不能跑空，才能提供流畅的播放体验。因此它应当吸收这个变化，最多需要 $3 \times 315 - 75 = 870$ms 的缓冲。在 1Mb/s 下对应 870,000 比特。
>
> <span style="color:#7f8c8d;">核算：最坏时间线 = 首次发送 315ms + 发现超时 2×315ms + 重传 315ms = 945ms = $3 \times 315$ ✓；播放起点按最快分组 75ms 锚定，缓冲 = $945 - 75 = 870$ms ✓；$870\text{ms} \times 10^6 \text{b/s} = 870{,}000$ bits ✓。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这道 VoIP 大题是 Unit 3 时延模型的一次完整体检，五个小问恰好构成"逐层加料"的递进：先纯传播+打包（最小 RTT），再加单点稳态排队（平均），再加全网队列上限（最大），最后问"如何用播放缓冲把时延抖动（jitter）熨平"。播放缓冲的本质是一个解耦器：应用按固定节奏取分组播放，网络按乱七八糟的节奏送分组到达，缓冲把两者隔离。设计准则是"缓冲量 = 最大到达时刻 − 最小到达时刻"（iv 问），而 (v) 问把重传也计入"到达时刻分布"，最坏情形变成 3 段 315ms 的串联——注意发现丢包要等 $2 \times 315$ms 的原因：发送方要等超时定时器，而定时器必须覆盖"分组还在路上 + ACK 在回来路上"的最坏情形，恰好是 2 倍单程最大时延。这个"定时器 = 2× 时延界"的设计在 TCP 超时计算（Unit 4 的 RTT 估计）里换了个更统计的版本（EWMA + 4×DevRTT），思想同源：宁可多等，不可提前重传造成重复分组。把 (v) 的 870ms 和 (iv) 的 240ms 一对比，就能直观看到"可靠性（重传）是拿时延抖动换来的"。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">Question 10 [10 points]：漏桶与队列时延</span>

（题干：$(\sigma, \rho)$ 漏桶约束的源，队列以速率 $R$ 排空、缓冲无限大。英文原文见题目卷。）

**Part (i)**：<span style="color:#00838f;">哪些选项正确？（多选）</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**C 与 D 正确**（A、B 错误）。
> >
> > (c) 正确，因为到达率小于离开率（$\rho < R$），队列不会无界增长；$\sigma$ 有限，所以队列的最大占用保持有界，每个比特的时延有上界 $\sigma/R$，有限。
> >
> > (d) 正确，因为穿过队列的最大时延被 $\sigma/R = 10/600$ s（约 16.7ms）所约束，小于 100ms。
>
> <span style="color:#7f8c8d;">核算：D 中 $\sigma/R = 10/600\text{s} = 16.7\text{ms} < 100\text{ms}$ ✓；C 中聚合漏桶 $(\sum\sigma_i, \sum\rho_i)$ 仍是漏桶约束（两个漏桶流的并仍是漏桶流），时延上界 $\sum\sigma_i / R$ 有限 ✓。A 错误：上界是 $\sigma/R$ 而非 $2\sigma$——$\sigma/R < 2\sigma$ 只在 $R > 1/2$（且注意量纲，$\sigma$ 的单位是比特、$R$ 是比特/秒，$2\sigma$ 与 $\sigma/R$ 量纲本就不同）时碰巧成立，一般不成立。B 错误："仅当 $\rho < R$" 过强——$\rho = R$ 时队列占用被漏桶约束钳制在 $\sigma$ 以内，时延仍有界（至多 $\sigma/R$）；"only when" 把充分条件错说成了必要条件。原文 A 选项的 "always less than 2" 在 pdftotext 提取中丢失了符号，按题目原意为 $2\sigma$。</span>
