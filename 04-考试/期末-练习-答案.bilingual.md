### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">I. The Link Less Travelled（链路之旅）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 1 [4 points]

<span style="color:#00838f;">圈出所有为真的陈述（零个、一个或多个都可能为真）。</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**A 与 B 为真**（C、D 为假）。
>
> <span style="color:#7f8c8d;">逐项核对：A 真——输出排队交换机中分组已经到达输出端口队列，只要队列非空，出链路立刻可以发送，不会闲置；B 真——输入排队交换机受队头阻塞（HOL blocking）与匹配失败影响，即便输入队列有分组，出链路也可能闲置；C 假——输入排队通常平均时延更高（HOL 阻塞），而非更低；D 假——虚拟输出队列（VOQ）正是为了消灭队头阻塞而设，每个输入端口为每个输出方向单设队列，队列内分组全部去往同一输出，不会被"去往不同输出的分组"挡住。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 2 [6 points]

<span style="color:#00838f;">1000 比特分组从 A 到 B（A —100Mb/s— 交换机 —1Gb/s— 交换机 —1Gb/s— B，链路各 200m，存储转发），从第一个比特离开 A 到最后一个比特到达 B 需要多久？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：Time: **15 × 10⁻⁶ seconds**（15μs）。
> >
> > 传播时延为 $600\text{m}/(2 \times 10^8\text{ m/s}) = 3\mu s$。打包时延为 $1000\left(\frac{1}{100 \times 10^6} + \frac{1}{1 \times 10^9} + \frac{1}{1 \times 10^9}\right) = 12\mu s$。因此端到端时延为 $15\mu s$。
>
> <span style="color:#7f8c8d;">核算：3 条链路各 200m，传播 $3 \times (200/2\times10^8) = 3\mu s$ ✓；打包：1000 bits 在 100Mb/s 链路占 $1000/10^8 = 10\mu s$，在两条 1Gb/s 链路各占 $1000/10^9 = 1\mu s$，合计 $10 + 1 + 1 = 12\mu s$ ✓（源文括号 "1/(1 × 109 + 1/(1 × 109)" 有排版错误，少了一个右括号且应为加号连接；总时延 $3 + 12 = 15\mu s$ ✓。存储转发意味着交换机必须收完整个分组才能在下一链路重新打包，三段打包串行、不重叠。）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 3 [5 points]

<span style="color:#00838f;">p1、p2 出发间隔 10μs、首比特到达间隔仅 1μs，哪些陈述为真？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**C 与 D 为真**（A、B、E 为假）。
>
> <span style="color:#7f8c8d;">逐项核对：A 假——若网络中除 p1、p2 外无其他分组，两条流的时延差无法凭空产生（p2 后出发，不可能被 p1 挡住首比特），到达间隔应仍为 10μs；B 假——"唯一可能的解释"不成立，C、D 都是其他解释（这正是 B 的陷阱：绝对化表述）；C 真——p1 在交换机缓冲里被其他发往 Host B 的分组压了 9μs，而 p2 到达时那批分组已经清空，p2 未被延迟；D 真——两者都被别的分组延迟、但 p1 被延迟得更多（9μs 之差）；E 假——C、D 为真。关键直觉：到达间隔 = 出发间隔 + (d₁ − d₂)，需要 p1 比 p2 恰好多延迟 9μs，而"谁挡了谁"必须来自题面之外的其他流量或时序巧合。</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">II. Hold to Your Principles（坚守原则）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 4 [10 points]

<span style="color:#00838f;">路由器剥离链路层首部、验证 IP 首部校验和再重新封装转发——为什么这不违反强/弱端到端原则？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：IP 路由器使用校验和来确保分组被转发到正确的路由器。这并不违反弱端到端原则（weak end-to-end principle），因为每台路由器都必须使用 IP 首部，它就是这些信息的"端点"（endpoint）。它也不违反强端到端原则（strong end-to-end principle），因为 IP 首部校验和的功能没有超出分组转发的范畴。
>
> <span style="color:#7f8c8d;">要点核对：弱原则允许中间节点做"使用该信息的必需功能"，路由器转发必须读 IP 首部、校验它是为了自己不被喂坏数据——路由器正是这些信息的功能端点 ✓；强原则反对的是"把功能放进网络、靠应用补救"，而校验和只保护转发这一步，不承担可靠性（可靠性由端侧 TCP 保证）✓。</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">III. The AIMD Saw Cuts Congestion（AIMD 锯齿）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 5 [5 points]

<span style="color:#00838f;">单条 AIMD 流的锯齿频率是固定的还是可变的？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**B 正确——锯齿频率是固定的。**
> >
> > 锯齿的高度由发送方花多久填满缓冲区并引发丢弃决定。整个过程是确定性的：到下一次丢包的时间等于重新填满缓冲区所需的轮数（每次加性增 1 个分组，缓冲从 $\frac{1}{2}W_{max}$ 涨回 $W_{max}$ 所需的轮数恒定）。
>
> <span style="color:#7f8c8d;">核算：从 $\frac{1}{2}W_{max}$ 线性增长到 $W_{max}$ 需要 $\frac{1}{2}W_{max}$ 轮，每轮一个 RTT，缓冲足够大（$\ge C \cdot RTT$）时该轮数与起点都固定 ✓。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 6 [5 points]

<span style="color:#00838f;">加性增的斜线（锯齿的斜边）是直的还是弯的？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**B 正确——斜边不是直的。**
> >
> > 窗口每增加 1 个分组，RTT 也随之增加 1 个分组的时间（分组在路由器队列里排队）。因此每次迭代的时间变长，加性增长之间的间隔也随之变长。
>
> <span style="color:#7f8c8d;">核对：窗口 +1 → 队列占用 +1 → 排队时延 +1 个打包时延 → RTT 变长 → "每轮"耗时递增 → 以时间为横轴的曲线向下弯（斜率递减）✓。若以"轮数"为横轴它才是直线——本题横轴是时间。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 7 [5 points]

<span style="color:#00838f;">写出该流的吞吐量关于瓶颈链路线速 $C$ 的表达式。</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：Throughput = $C$。若网络中只有一条流，吞吐量恒定：瓶颈链路总是满载着分组。
>
> <span style="color:#7f8c8d;">核对：单流独占瓶颈，缓冲 $\ge C \cdot RTT$ 保证窗口永远能填满管道（带宽时延积），瓶颈 100% 被利用，平均吞吐量恰为 $C$ ✓。注意这与 Mathis 公式 $\frac{1.22 \cdot MSS}{RTT\sqrt{p}}$ 不矛盾——后者是存在随机丢包时的平均，本题丢包由确定性填满缓冲触发、且瓶颈永远满载。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 8 [5 points]

<span style="color:#00838f;">多条不同步的流共享网络时，每条流的锯齿频率还固定吗？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**B 正确——有些流的锯齿将不再具有固定频率。**
> >
> > 锯齿的周期不再固定。如果网络中有很多流，缓冲区的占用由多条流的分组共同贡献；任何一条流的分组都可能成为压垮缓冲、引发溢出的最后一根稻草。某个特定分组是否导致缓冲溢出，取决于它到达时缓冲有多满。鉴于这取决于所有其他流，我们无法预测哪个分组会触发溢出；因此锯齿的周期不固定。
>
> <span style="color:#7f8c8d;">核对：确定性消失的根源是"谁触发丢包"变成了多条流的耦合事件 ✓。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> Q5–Q8 是一整个"从确定论走向统计论"的思想实验，值得串起来消化。单流世界里 AIMD 是一台确定性的钟表：缓冲、窗口、RTT 全是精确可算的状态机，每 $\frac{1}{2}W_{max}$ 轮精确丢一次包——这本质是个离散动力系统，初值决定一切。可一旦第二条流进入，系统的状态空间里多了别人的窗口，丢包触发者从"我"变成"我们中最快的那位"，单流的锯齿立刻从周期函数退化成随机过程。这个跃迁与概率论里"大数定律"的适用条件截然不同：大数定律靠多次独立平均消掉随机性，而共享拥塞的各流之间恰恰不独立（都在响应同一个缓冲）。Unit 4 用"AIMD 收敛到等带宽分享"的相图分析过这个系统，那时你看到的是均值行为；本 quiz 揭示的是单条轨迹的统计性质——周期不再可预测，但长期平均仍趋向公平。这种"个体不可预测、集体有规律"的现象，正是热力学与统计物理的原型问题，也是网络数学最迷人的地方。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">IV. Scrambled Eggs and Bits（纠错编码）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 9 [10 points]

<span style="color:#00838f;">只用 Level 1 编码（(32,28) RS 码）时，能损坏一个块的最短连续 chip 错误串是多少？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：Shortest string: **10 consecutive chips**（10 个连续 chip）。
> >
> > 10 个连续 chip 错误可以让 3 个编码字节出错：字节 $n$ 上 1 比特错、字节 $n+1$ 上 8 比特错、字节 $n+2$ 上 1 比特错。如果这 3 个字节恰好在同一个 chunk 里，那么 Reed-Solomon 码将无法恢复该 chunk。例如，若 $\bar{a}_0$、$\bar{a}_1$、$\bar{a}_2$ 都有 chip 错误，物理层将无法恢复 chunk $a$。
>
> <span style="color:#7f8c8d;">核算：(32,28) RS 码可纠 $(n-k)/2 = 2$ 个未知位置错误，故同一 chunk 内出错字节 ≥ 3 即不可恢复 ✓；最短突发构造：从字节 $n$ 的最后 1 个 chip 开始，盖住字节 $n+1$ 的全部 8 个 chip，再顶到字节 $n+2$ 的第 1 个 chip，$1+8+1 = 10$ chips 恰好跨 3 字节 ✓（起始位置若不在字节边界，更短的串只能覆盖 2 个字节：例如从字节中间开始的 9 chips 最多波及 2 字节，RS 仍可纠 2 字节错）。源文答案末句 "1 bit error on byte n + 1" 重复了 $n+1$，按上下文应为字节 $n+2$——已修正并在此说明。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 10 [5 points]

<span style="color:#00838f;">加上 Level 2 交织后，能损坏一个 Level 2 编码块的最短连续 chip 错误串是多少？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：Shortest string: **378 consecutive chips**（378 个连续 chip）。
> >
> > 损坏一个 Level 2 编码的块，需要让某个 Level 1 chunk 的 3 个字节出错。这需要打中第一个 chunk 里的 1 个 chip、最后一个 chunk 里的 1 个 chip，以及两者之间的全部 chip。以打坏 $\bar{a}_0$、$\bar{a}_1$、$\bar{a}_2$ 为例：两者之间的 chip 数为 $\bar{a}_0$ 与 $\bar{a}_1$ 之间的 23 个字节、$\bar{a}_1$ 这一个字节、以及 $\bar{a}_1$ 与 $\bar{a}_2$ 之间的 23 个字节，共计 47 字节即 376 chips。所以一串 378 个 chip 错误可以损坏一个 Level 2 编码块。
>
> <span style="color:#7f8c8d;">核算：交织后 chunk 0 = ($\bar{a}_0, \bar{b}_0, \ldots, \bar{x}_0$)，$\bar{a}_0$ 在 chunk 0 的位置 0、$\bar{a}_1$ 在 chunk 1 的位置 0、$\bar{a}_2$ 在 chunk 2 的位置 0。突发从 $\bar{a}_0$ 的最后 1 chip 开始：+ chunk 0 剩余 23 字节（184 chips）+ $\bar{a}_1$ 全部 8 chips + chunk 1 剩余 23 字节（184 chips）+ $\bar{a}_2$ 的第 1 chip = $1 + 184 + 8 + 184 + 1 = 378$ chips ✓（官方答案的"47 字节 = 376 chips + 首尾各 1 chip"口径与之一致）。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 10 对 378，这道题用两个数字说清了交织（interleaving）的全部价值与全部代价。先说价值：物理信道的错误天然成串（一次深衰落、一个划痕毁掉一大段连续比特），而 RS 码只能纠"散装"的错——Level 1 单独使用时，10 个连续 chip 就能让 3 个字节出错、废掉一个 chunk（RS 只能纠 2 个未知位置错）；交织把"时间上连续"重排成"空间上分散"，同一个 chunk 的相邻字节在信道上相距 24 字节，要凑齐 3 个同 chunk 错误，突发长度必须从 10 拉长到 378——抗突发能力提升近 40 倍。再说代价：接收端必须收齐整个交织块才能反交织，译码时延从 32 字节涨到 768 字节，存储与延迟开销都是实打实的。这个"用延迟换鲁棒性"的权衡你在别处也见过：TCP 的乱序重排在接收端是纯收益（ 无额外延迟），而物理层的交织延迟直接挂在端到端时延上。Wi-Fi、光盘（CD 的 CIRC 编码正是"交织+RS"的同款架构）、5G NR 都在用这套组合拳——本 quiz 就是把 CIRC 拆成两个简化问答。

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">V. With a Side of Hashes（哈希与 DNS）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 11 [10 points]

<span style="color:#00838f;">朋友的 DNS 防伪方案（TXT 记录 + HMAC-SHA-256）在家用网络里校验失败——你同意"ISP 欺骗 DNS"的结论吗？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**B——No, something else is happening（不对，是别的事情在发生）。**
> >
> > 更可能的情况是：他处在一台 NAT 之后。NAT 改写了 DNS 响应的目的地址（还可能改写端口），却没有（也没法）更新 MAC——它没有那把私钥——因此 MAC 自然不再正确。
>
> <span style="color:#7f8c8d;">要点核对：HMAC 覆盖 DNS payload + UDP 伪首部（含 IP 地址）✓；NAT 改地址/端口 → 报文比特变了 → 但私钥只在服务器与笔记本两端，中间盒无从重签 ✓；在斯坦福校园网测试成功是因为校园网内地址未被改写；在家失败恰好说明路径上有 NAT。这正是"端到端认证"的教案：只有密钥持有者能产生/验证 MAC，任何中间改动都会暴露——好事是防篡改，坏事是把合法中间盒（NAT）也误伤了。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 这道题是 Unit 5 NAT 与 Unit 8 认证思想的完美交叉火力，两边知识点都得懂才做得出来。朋友的方案本质上是给 DNS 响应加盖"防伪火漆"：HMAC-SHA-256 只能由持有私钥的两端计算与验证，任何中间节点改一个比特都会让校验失败——安全上这是对的，问题在于他忘了这个世界里还有"合法的篡改者"。NAT 改写 IP 首部的目的地址、UDP 首部的端口号（他甚至聪明地把 UDP 伪首部纳入了 MAC 覆盖范围，等于把 NAT 的手脚也纳入了校验），于是 NAT 的正常工作与端到端认证正面相撞。历史总是押韵：这套困境的正解就是后来标准化的 TSIG（RFC 2845，DNS 事务签名）与 DNSSEC——它们要么在两条 NAT 边界内协商，要么只对 DNS 数据本身签名而不覆盖传输层地址。第一性原理的教训：设计端到端安全机制时，必须枚举"路径上谁会合法地改动报文"——IPsec 的隧道模式、TLS 不保护 IP 首部，都是对这个问题的回答。知识若只学到"HMAC 能防篡改"，就只知其一；知道"它会把 NAT 也当成敌人"，才算把第五单元和第八单元焊在了一起。

#### <span style="color:#2471a3;">**[exercise]**</span> Question 12 [15 points]

<span style="color:#00838f;">两级 Feistel 网络加密：已知输入 0⁶⁴ 的输出，能否不解密地推出某些其他输入的输出？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**B——Yes, it is possible to determine some outputs（能，可以确定某些输出）。**
> >
> > $L_2$ 是"对 $R_0$ 应用 $F$ 再与 $L_0$ 异或"的结果：$L_2 = L_0 \oplus F(k_1, R_0)$。如果 $R_0$ 不变，那么 $L_0$ 的任何变化都会直接反映在 $L_2$ 上。已知输入 0⁶⁴（即 $L_0 = 0, R_0 = 0$）的输出，就等于拿到了 $F(k_1, 0)$ 的值；此后对任何 $R_0 = 0$ 的输入（$L_0$ 任意），其输出的 $L_2$ 分量都等于 $L_0 \oplus F(k_1, 0)$，无需知道密钥即可计算。
>
> <span style="color:#7f8c8d;">核算：按标准两轮 Feistel 轮函数 $R_1 = L_0 \oplus F(k_1, R_0)$、$L_2 = R_1$（第二轮把第一轮输出整体左移），所以 $L_2 = L_0 \oplus F(k_1, R_0)$ ✓；输入 0⁶⁴ 给出 $F(k_1, 0)$ 的"泄露" ✓；所有 $R_0 = 0$ 的输入（如 $1 \cdot 2^{32}$ 与 $2 \cdot 2^{32}$……即仅高 32 位不同的任意输入对）之间输出的 $L_2$ 分量可直接互相推出 ✓——一个已知明文就泄露了一整族输入的半个输出。</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">VI. A Stack of Protocols（协议栈全流程）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 13 [20 points]

<span style="color:#00838f;">新笔记本第一次插入有线以太网口：写出直到它发出一个发往 128.30.2.1 的 IP 分组为止、链路上发生的全部分组交换（含 DHCP 与 ARP，尽量给出 IP 与以太网地址）。</span>

（题干与六条假设的英文原文见题目卷。）

> > <span style="color:#2471a3;">**[solution]**</span> 答案：
> > - 你的笔记本从 00:11:22:33:44:55 广播一条 DHCP discover（发现）消息。
> > - DHCP 服务器向 00:11:22:33:44:55 发送 DHCP offer（提供），给出 171.64.7.22。
> > - 客户端从 00:11:22:33:44:55 广播一条 DHCP request（请求），请求 171.64.7.22。
> > - DHCP 服务器向 00:11:22:33:44:55 发送 DHCP ack（确认）。
> > - 你的笔记本以 171.64.7.22 / 00:11:22:33:44:55 发出 ARP 请求，目的为 171.64.7.1（以太网目的地址 ff:ff:ff:ff:ff:ff）。
> > - 网关以 171.64.7.1 / 00:66:77:88:99:00 回应 ARP 应答，发往 171.64.7.22 / 00:11:22:33:44:55。
> > - 笔记本发出 IP 分组：源 171.64.7.22 / 00:11:22:33:44:55，目的 IP 128.30.2.1，以太网目的地址 00:66:77:88:99:00。
>
> <span style="color:#7f8c8d;">核对：DHCP 四步（discover/offer/request/ack）全部为广播或"请求式广播"✓；ARP 请求是链路层广播（ff:ff:ff:ff:ff:ff）、只问网关（目的 IP 128.30.2.1 不在本子网 171.64.7.0/24，按最长前缀匹配走网关）✓；最后一步以太网帧的目的 MAC 是网关而非最终主机、IP 目的仍是最终目的地——这正是"IP 端到端、MAC 逐跳"的铁律 ✓。源文有两处提取/拼写噪声已修正："reponds"（应为 responds）与 ARP 应答目的地址缺失的尾字节 "55"。</span>

### <span style="color:#2471a3;">**[section]**</span> <span style="color:#c0392b;">VII. Are Two TCPs Better Than One?（分裂 TCP 连接）</span>

（背景题干、吞吐量公式与近似值表与期中卷完全相同：$\frac{1.22 \cdot MSS}{RTT \cdot \sqrt{p}}$，$MSS\sqrt{3/2} = 13{,}717$ bits，$\sqrt{0.1} = 0.32$，$\sqrt{0.19} = 0.44$。）

#### <span style="color:#2471a3;">**[exercise]**</span> Question 14 [5 points]

<span style="color:#00838f;">B 不分裂连接（A–B 丢 10% 数据段、不丢 ACK；B–C 不丢包），A→C 的 TCP 吞吐量？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**428–434 kbps**。
> >
> > $RTT\sqrt{p} = 0.1 \times 0.32 = 0.032$，$MSS\sqrt{3/2} = 13{,}717$ bits，所以 $\frac{13{,}717}{0.032} = 428{,}656$ b/s，即约 429 kbps。434 kbps 是使用更多有效数字的更精确计算。
>
> <span style="color:#7f8c8d;">核算：$13717/0.032 = 428{,}656$ ✓；精确 $\sqrt{0.1}$ 给 433,801 ≈ 434 kbps ✓。（与期中 Q2 同题同解。）</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 15 [5 points]

<span style="color:#00838f;">B 分裂连接（A–B 丢 10% 数据段、不丢 ACK；B–C 不丢包），A→C 的吞吐量？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**856–888 kbps**。
> >
> > B–C 之间的连接受 A–B 之间连接的限制（后者丢包率更高）。A–B 段的速率与上一题相同，只是 RTT 从 100ms 减半为 50ms，所以其吞吐量是不分裂情形的两倍。更精确地：$RTT\sqrt{p} = 0.05 \times 0.32 = 0.016$，$MSS\sqrt{3/2} = 13{,}717$ bits，所以 $\frac{13{,}717}{0.016} = 857{,}313$ b/s，即约 857 kbps。
>
> <span style="color:#7f8c8d;">核算：$13717/0.016 = 857{,}313$ ✓（与期中 Q3 同题同解）。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 16 [5 points]

<span style="color:#00838f;">B 分裂连接，且 A–B、B–C 两段各丢 10% 分组，A→C 的吞吐量？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**856–888 kbps**。
> >
> > 与上一题相同。B–C 段路径的吞吐量与 A–B 段相同，端到端吞吐量由两段中较慢者决定。
>
> <span style="color:#7f8c8d;">核算：与 Q15 相同，857 kbps 量级 ✓（与期中 Q4 同题同解）。</span>

#### <span style="color:#2471a3;">**[exercise]**</span> Question 17 [5 points]

<span style="color:#00838f;">B 不分裂连接，A–B 与 B–C 两段各丢 10% 数据段，A→C 的吞吐量？</span>

> > <span style="color:#2471a3;">**[solution]**</span> 答案：**312–315 kbps**。
> >
> > A–B 与 B–C 的丢失相互影响，端到端丢弃率为 19%：成功率为 $0.9^2 = 0.81$，即 81%，所以 $p = 19\%$。$RTT\sqrt{p} = 0.1 \times 0.44 = 0.044$，$MSS\sqrt{3/2} = 13{,}717$ bits，所以 $\frac{13{,}717}{0.044} = 311{,}750$ b/s，即约 312 kbps。315 kbps 是使用更多有效数字的更精确计算结果。
>
> <span style="color:#7f8c8d;">核算：$1 - 0.9 \times 0.9 = 0.19$ ✓；$13717/0.044 = 311{,}750$ ✓；精确值 314,781 ≈ 315 kbps ✓（与期中 Q5 同题同解）。</span>

> <span style="color:#1e8449;">**[note] Note（译者注）:**</span> 期末卷把期中的分裂 TCP 大题原封不动又考了一遍（Q14–Q17 ↔ 期中 Q2–Q5），这不是偷懒而是出题人的信号：这个 2×2 受控实验（分裂与否 × 单段丢/两段丢）是整门课"多约束分析"能力的试金石，而且它是真实世界的技术——卫星链路、蜂窝网关里的性能增强代理（PEP）、CDN 边缘节点都在分裂连接。做题之外，值得补一个期中没提的视角：分裂连接在工程上其实有三种"代价账单"。其一是正确性：B 伪造 A 的地址与 C 通信、伪造 C 的地址给 A 发 ACK，破坏了端到端语义（TCP 的端到端校验和、TLS 的端到端加密都会被中间终止打断——这也是为什么 HTTPS 时代的 PEP 只能对未加密流量做分裂）；其二是资源：B 要为两端各维护一条完整的 TCP 状态机，中间盒成了状态集中的故障点；其三是公平性：分裂后每段各自跑 AIMD，吞吐量公式各算各的，但如果 B 与 A 之间是无线链路（本来丢包就不代表拥塞），分裂反而能把"无线丢包误判为拥塞"的伤害隔离掉——这是分裂技术最正当的存在理由。同一个机制，既可以是性能救星也可以是架构祸害，判据只在"你把它用在哪一段链路上"。
